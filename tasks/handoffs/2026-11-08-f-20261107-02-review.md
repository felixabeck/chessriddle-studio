### plan-r1.md

# Plan: f-20261107-02 — additive migrations stop blocking the library listing on the content check

## Goal

Opening a database whose schema is 2.0.0 or 2.1.0 in a 2.2.0 build no longer holds the library
listing for the full-database `integrity_check` and `foreign_key_check`. The additive migration
commits after the cheap schema contract, and the existing background content scan validates the
migrated file exactly as it validates every current-version database without a passing stamp.

## MANDATE

Finding f-20261107-02 (verbatim):

> **Defect:** the first time a new build opens a database whose schema version is older, the listing
> migrates it and then runs the existing full `integrity_check` and `foreign_key_check` before
> returning. For an 11.4M-game database that is about 60 s in a release build, and the library shows
> only "Loading games databases…" for every database during that time, with no hint that a one-time
> upgrade is running or which database it is.
>
> **Failure scenario:** release build 50fdcc36, throwaway profile seeded with a 2.1.0 copy of Mega
> Database 2025 (3 GB): the library listed the database after 62 s (73 s in an earlier run);
> screenshot `00-library-loading.png` of the run shows the generic text only. Felix's own Mega
> database will hit this once after the 2.2.0 schema update.
>
> **Open question:** should the listing show a per-database "upgrading database (one time)" state
> with progress, or should the content check after an additive migration move to the existing
> background content validation (d-20261107-13 kept it inline)?

Request: `/next-finding --pin f-20261107-02 full auto` (drain, plan-only).

## Threat model and non-goals

* Input adversary: a user-supplied or user-selected SQLite file in the database folder — possibly
  corrupt (bad pages, stored CHECK violations, dangling foreign keys), possibly a different schema
  version, possibly very large (Mega Database 2025, 11.4M games, 3 GB). No hostile process races
  the file beyond what the existing identity/stamp checks already handle.
* Environments: Linux, Windows, macOS desktop builds; release and `.dev` identifiers.
* The safety property that must survive: a database whose content fails `integrity_check` or
  `foreign_key_check` is never presented as usable beyond the already-accepted window of
  d-20261002-05 ("a corrupt file may show its stored title until the scan fails"), and the failure
  reaches the user through the existing error card (`DatabaseContentFailure` event →
  `useDatabaseContentValidation` → list revalidation → `inspect` returns the stored verdict).
* Non-goals: changing the 1.0.0 legacy migration (it rewrites rows and tables, not additive);
  changing database creation (empty file, check is instant); changing the background scanner,
  its stamp format, its slot/gateway policy or its event; any new renderer state, event or copy.

## Traced premises

# Plan: f-20261107-02 — additive migrations stop blocking the library listing on the content check

## Goal

Opening a database whose schema is 2.0.0 or 2.1.0 in a 2.2.0 build no longer holds the library
listing for the full-database `integrity_check` and `foreign_key_check`. The additive migration
commits after the cheap schema contract, and the existing background content scan validates the
migrated file exactly as it validates every current-version database without a passing stamp.

## MANDATE

Finding f-20261107-02 (verbatim):

> **Defect:** the first time a new build opens a database whose schema version is older, the listing
> migrates it and then runs the existing full `integrity_check` and `foreign_key_check` before
> returning. For an 11.4M-game database that is about 60 s in a release build, and the library shows
> only "Loading games databases…" for every database during that time, with no hint that a one-time
> upgrade is running or which database it is.
>
> **Failure scenario:** release build 50fdcc36, throwaway profile seeded with a 2.1.0 copy of Mega
> Database 2025 (3 GB): the library listed the database after 62 s (73 s in an earlier run);
> screenshot `00-library-loading.png` of the run shows the generic text only. Felix's own Mega
> database will hit this once after the 2.2.0 schema update.
>
> **Open question:** should the listing show a per-database "upgrading database (one time)" state
> with progress, or should the content check after an additive migration move to the existing
> background content validation (d-20261107-13 kept it inline)?

Request: `/next-finding --pin f-20261107-02 full auto` (drain, plan-only).

## Threat model and non-goals

* Input adversary: a user-supplied or user-selected SQLite file in the database folder — possibly
  corrupt (bad pages, stored CHECK violations, dangling foreign keys), possibly a different schema
  version, possibly very large (Mega Database 2025, 11.4M games, 3 GB). No hostile process races
  the file beyond what the existing identity/stamp checks already handle.
* Environments: Linux, Windows, macOS desktop builds; release and `.dev` identifiers.
* The safety property that must survive: a database whose content fails `integrity_check` or
  `foreign_key_check` is never presented as usable beyond the already-accepted window of
  d-20261002-05 ("a corrupt file may show its stored title until the scan fails"), and the failure
  reaches the user through the existing error card (`DatabaseContentFailure` event →
  `useDatabaseContentValidation` → list revalidation → `inspect` returns the stored verdict).
* Non-goals: changing the 1.0.0 legacy migration (it rewrites rows and tables, not additive);
  changing database creation (empty file, check is instant); changing the background scanner,
  its stamp format, its slot/gateway policy or its event; any new renderer state, event or copy.
