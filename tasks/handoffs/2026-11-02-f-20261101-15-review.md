## Decided autonomously (to record through `findings.py record-decision` on adoption)

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** does `NormalizedGame.stamp` become required? **Chosen:** optional on the DTO, always
  filled natively. **Rejected:** required, which forces invented stamps on renderer-built Lichess
  rows that never reach `write_db_game`. **Reason:** a missing stamp already fails safe under O4.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

# Plan: database game saves refuse a stale tab (f-20261101-15)

## Goal

A database-backed analysis tab can overwrite its stored game only when the stored row still equals
the row the tab was loaded from or last saved. Otherwise the save is refused as `stale-game` and the
tab shows the existing conflict panel, with its edits preserved. Closes f-20261101-15.

## MANDATE

f-20261101-15, verbatim:

## Approach

### O1 — Row stamp: a content hash of the stored `games` row

The revision is a stored-content stamp: SHA-256 hex of a canonical, length-delimited encoding of
every column of the `Game` row, computed natively by one function. No migration and no new column.
Two rows with equal stored content have equal stamps. That is correct, because a save over equal
content loses nothing. Any in-app change to the row (another tab's save, a player merge that
rewrites `white_id`) changes the stamp. A safe refusal over a change that did not touch the movetext
is accepted, as in `d-20260925-10`. The encoding must distinguish `None` from an empty string and
must not let adjacent fields collide.

### O2 — The stamp travels with the row it describes

`NormalizedGame` gains a required `stamp` field, filled by `normalize_games` from the same row it
normalizes. Every producer (`get_games`, position search, and any linked/annotated path that builds
or copies `NormalizedGame`) therefore carries a stamp matching its own displayed content, including
cached search results (they are stale and self-consistent, so a save from them is refused, never
lost). `databaseGameSeed` passes the stamp, and `createTab` sets `sourceStamp` on the seeded tree for
a `database` origin. Duplicate tab copies the tree, and with it the stamp, so the first save wins
and the second is refused.

### O3 — Compare-and-swap inside the write transaction

`write_db_game` takes the expected stamp and returns the new stamp. Inside the existing
`with_validated_mutation` closure, `write_parsed_db_game` selects the full row for the id, compares
its stamp with the expected one, and returns `Error::StaleGame` on mismatch before any write. A
missing row stays `GameNotFound`. After the update it reads the row back in the same transaction and
returns the new row's stamp. `insert_db_game` returns the inserted id together with the inserted
row's stamp, read in the same transaction. No `unwrap` on these paths.

### O4 — Renderer save contract for database tabs

The database branch of `saveToFileNow` sends the tree's `sourceStamp`. A `null` stamp (a database
tab persisted before this change, or a tree whose stamp is unknown) is refused as `sourceChanged`
without a write, exactly as the file branch does (`tabs.ts:1190`). The branch sets
`writingCurrentOrigin`, so a `stale-game` refusal reaches `sourceChanged` through the existing catch.
On success it passes the returned stamp through the existing `finishWrite` semantics: `save(stamp)`
when the tree is unchanged since serialization, `setSourceStamp(stamp)` when it changed meanwhile.
`storeToDatabase` installs the stamp returned by `insertDbGame` instead of `null`.

### O5 — The conflict panel for database tabs

`DatabaseOriginGate` reads `useFileFreshness(tabId)`. In `conflict` it renders the existing panel
shape (same layout, class and `data-file-freshness` marker) with two actions, and the board is
unmounted while it shows:

* **Reload from database** reads the current row by id through a new read command
  `get_db_game(file, game_id, ticket) -> NormalizedGame` (registered in `collect_commands!`, a
  ticketed native read like `get_games`, added to `NativeReadCommandName` and
  `NATIVE_READ_ARITY`, reading through the same `normalize_games`). The reload is bound to the
  panel's tab, origin and tree store and aborts on unmount, like `reloadFromDisk`. It installs the parsed tree with that row's stamp
  through the existing tree-install sequence and sets freshness `verified`. A missing row shows the
  existing `FileFreshness.GameNoLongerInFile`-style error without discarding the tree.
* **Save my version as a new game** inserts the tab's tree into the same database through the
  existing `storeToDatabase` insert-and-admit path (no second insert implementation), moving the tab
  to the new game id with its stamp, and sets freshness `verified`. The action is registered through
  `registerFileConflictSave`, so the close modal's Save works for a conflicted database tab.

Copy reuses the file panel's keys where the wording fits ("Save my version as a new game…").
New keys only where "disk" would be false: `FileFreshness.ChangedInDatabase` ("This game changed in
the database while you were editing.") and `FileFreshness.ReloadFromDatabase` ("Reload from
database"), added to every locale per `docs/localization.md` and extracted with
`pnpm i18n:extract`. A collection-indexed database keeps its existing `RetiredOriginRecovery`
precedence.

### O6 — Verification

Rust tests in `src-tauri/src/db/mod.rs`'s test module: a write with the loaded stamp succeeds and
returns the new row's stamp; a second write carrying the first stamp is refused with
`Error::StaleGame` and leaves the row byte-identical; a write to a missing id stays `GameNotFound`;
the stamp distinguishes `None` from `""` and changes when any single column changes; `insert_db_game`
returns the stamp equal to what `get_games` reports for that row. Vitest: the two-tab scenario from
the MANDATE (two trees with the same origin and stamp; the second save returns `"conflict"`, freshness
`conflict`/`save-refused`, `writeDbGame` called with the stale stamp); a `null` stamp refuses without
calling `writeDbGame`; a success installs the returned stamp; `databaseGameSeed`/`createTab` seed the
stamp; the database conflict panel renders on `conflict`, Reload installs the row's tree and stamp,
Save as new game routes through `storeToDatabase` and is registered for the close modal. Bindings are
regenerated and checked.

## Decisions and trade-offs

### Decided autonomously

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

## Risks / open questions

* `NormalizedGame` gains a required field, so every renderer fixture constructing one must add it.
  Typecheck finds them.
* Hashing is per returned row. Page sizes are small and the moves blob is already decoded per row,
  so the added cost is negligible.

transaction rolls back, no data revision bump). A missing row stays `GameNotFound`. After the update
it reads the row back in the same transaction and returns the new row's stamp. `insert_db_game`
returns one named Specta struct `InsertedDbGame { id, stamp }`, the stamp read from the inserted row
in the same transaction. A read command `get_db_game(file, game_id, ticket) -> NormalizedGame`
reads one row by id through `normalize_games`, as a ticketed native read like `get_games`
(`crate::native_read_operation`), registered in `collect_commands!`. A missing id is `GameNotFound`.
No `unwrap`/`expect` on these paths. Bindings are regenerated, never hand-edited.

### O4 — Renderer save contract for database tabs

The database branch of `saveToFileNow` sends the tree's `sourceStamp`. A `null` stamp (a database
tab persisted before this change, or a tree whose stamp is unknown) is refused through
`sourceChanged` without a write, exactly as the file branch does (`tabs.ts:1190`). The branch sets
`writingCurrentOrigin`, so a `stale-game` refusal reaches `sourceChanged` through the existing catch.

A successful write installs the returned stamp with the existing unchanged/changed rule:
`save(stamp)` when the serialized tree is unchanged since the write started, `setSourceStamp(stamp)`
when it changed meanwhile (that result stays `"superseded"`). This success path does not go through
the file-only null-`revision` check of `finishWrite` and records no `verifiedRevision`. A database
row has no file revision. It sets freshness `verified`.

`storeToDatabase` reads `InsertedDbGame` and installs its `stamp` on the admitted `database` origin
instead of `null`.

`BoardAnalysis`'s user-save `"conflict"` toast `Tab.SaveMayHaveBeenWritten` stays for a tab without
any origin it can show a panel for, and is not shown for a `database` origin. That tab's refusal
shows the O5 panel instead, because nothing was written.

### O5 — The conflict panel for database tabs

`DatabaseOriginGate` receives `closeTab` and reads `useFileFreshness(tabId)`. A collection-indexed
database keeps its existing `RetiredOriginRecovery` precedence. Every freshness state except
`conflict` and `unavailable` renders the board, including the default `unverified` of a freshly
opened or reloaded tab. A database tab has no reconcile, and its CAS runs at save time. In
`conflict` and `unavailable` the board is unmounted (which stops auto-save repeating) and the panel
renders in the existing shape (layout, `classes.panel`, `data-file-freshness` marker):

* `conflict`: text `FileFreshness.ChangedInDatabase`, buttons **Reload from database** and
  **Save my version as a new game…**.
* `unavailable` (the row is gone): text `FileFreshness.GameNoLongerInDatabase`, buttons **Save my
  version as a new game…** and **Close**, as the file panel offers.

**Reload from database** calls `getDbGame` bound to the panel's tab, origin and tree store, and

`throwOnFailure` the error is rethrown to the caller. The action is registered through
`registerFileConflictSave`, which the close modal uses in `unavailable`. In `conflict` the close
modal keeps its file behaviour: it retries the save, which is refused, then activates the tab and
cancels the close, so the panel is visible with the edits intact.

Copy: reuse `FileFreshness.SaveAsNewGame` and `Tab.Close`. New keys only where "disk"/"file" would be

## Decisions and trade-offs

### Decided autonomously

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** does `NormalizedGame.stamp` become required? **Chosen:** optional on the DTO, always
  filled natively. **Rejected:** required, which forces invented stamps on renderer-built Lichess
  rows that never reach `write_db_game`. **Reason:** a missing stamp already fails safe under O4.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

# Plan: database game saves refuse a stale tab (f-20261101-15)

## Goal

A database-backed analysis tab can overwrite its stored game only when the stored row still equals
the row the tab was loaded from or last saved. Otherwise the save is refused as `stale-game` and the
tab shows the existing conflict panel, with its edits preserved. Closes f-20261101-15.

## MANDATE

f-20261101-15, verbatim:

* **Where:** `src/utils/tabs.ts` `saveToFileNow` database branch (`tauri.writeDbGame(databaseOrigin.database, databaseOrigin.gameId, pgn)`, around line 1184, no stamp or revision), `src-tauri/src/db/mod.rs:4106-4220` (`write_db_game` / `write_parsed_db_game` update by id unconditionally), auto-save in `src/components/boards/BoardAnalysis.tsx` (default on), `src/utils/databaseGame.ts` (opening a game always builds a new tab), Duplicate tab in `BoardsPage.tsx` copying `gameOrigin`.
* **Defect:** file-backed saves are compare-and-swap on a range stamp and go through `fileFreshness`; database saves have no revision at all, so a stale tab's whole tree overwrites newer content written by another tab.
* **Failure scenario:** open game #812 in tab A and add a variation (auto-saved); open #812 again into tab B, add comments (auto-saved); return to A and play one move: A's older tree overwrites the row and B's comments are gone, with no conflict shown. Duplicate tab on a database game reproduces it immediately.
* **Open question:** which row revision does a database tab carry (stored-content hash or an update counter column, which needs a migration), how is it returned on load and checked inside the write transaction, and how does a `stale-game` refusal reach the existing conflict panel for database tabs?

## Threat model and non-goals

The adversary is ordinary concurrency inside one app process: two or more tabs (opened separately
or through Duplicate tab) editing the same `games` row with auto-save on, plus any other in-app
writer of that row (merge players, a second save path). The one-process-per-root instance lock
(`async-resource-invariants.md`) covers the rest. A second process writing the same SQLite file
through a user-picked shared directory is outside it, but the check still runs inside the write
transaction under SQLite's write lock, so it also refuses such a writer's stale save. Hand edits to
the SQLite file with external tools are not modelled beyond that. Non-goal: three-way merging of
two tabs' edits. The conflict panel lets the user choose a version, as it does for files.

## Approach

### O1 — Row stamp: a content hash of the stored `games` row

The revision is a stored-content stamp: SHA-256 hex of a canonical, length-delimited encoding of
every column of the `Game` row, computed natively by one function. No migration and no new column.
Two rows with equal stored content have equal stamps. That is correct, because a save over equal
content loses nothing. Any in-app change to the row (another tab's save, a player merge that
rewrites `white_id`) changes the stamp. A safe refusal over a change that did not touch the movetext
is accepted, as in `d-20260925-10`. The encoding must distinguish `None` from an empty string and
must not let adjacent fields collide.

### O2 — The stamp travels with the row it describes and lands on the seeded tree

`NormalizedGame` gains an optional `stamp` field (`Option<String>`, `#[specta(optional)]`), always
filled by `normalize_games` from the same row it normalizes. Every native producer (`get_games`,
position search, `get_db_game`) therefore carries a stamp matching its own displayed content,
including cached search results (stale and self-consistent, so a save from them is refused, never
lost). Renderer-built `NormalizedGame` values that are not database rows (Lichess explorer) carry
none. A database tab without a stamp fails safe under O4.

The open path sets the row stamp on `TreeState.sourceStamp` of the seeded tree before
`tabStorage.seed`, only when the final origin is `database`. When `resolveLinkedGame` turns the open
into a file-backed tab, the linked branch keeps `linked.game.stamp` (a PGN-range stamp). The row
stamp is never copied from `NormalizedGame.linked.stamp` or from headers. Duplicate tab copies the
persisted tree, and with it the stamp, so the first save wins and the second is refused.

The conversion from a `NormalizedGame` to a tree (parse `moves` from the row's `fen`, assign the
row's fields as headers, set the row stamp) exists once and is used by both opening a game and the
O5 reload.

### O3 — Compare-and-swap inside the write transaction

`write_db_game` takes the expected stamp and returns the new stamp. Inside the existing
`with_validated_mutation` closure, `write_parsed_db_game` selects the full row for the id, compares
its stamp with the expected one, and returns `Error::StaleGame` on mismatch before any write (the
transaction rolls back, no data revision bump). A missing row stays `GameNotFound`. After the update
it reads the row back in the same transaction and returns the new row's stamp. `insert_db_game`
returns one named Specta struct `InsertedDbGame { id, stamp }`, the stamp read from the inserted row
in the same transaction. A read command `get_db_game(file, game_id, ticket) -> NormalizedGame`
reads one row by id through `normalize_games`, as a ticketed native read like `get_games`
(`crate::native_read_operation`), registered in `collect_commands!`. A missing id is `GameNotFound`.
No `unwrap`/`expect` on these paths. Bindings are regenerated, never hand-edited.

### O4 — Renderer save contract for database tabs

The database branch of `saveToFileNow` sends the tree's `sourceStamp`. A `null` stamp (a database
tab persisted before this change, or a tree whose stamp is unknown) is refused through
`sourceChanged` without a write, exactly as the file branch does (`tabs.ts:1190`). The branch sets
`writingCurrentOrigin`, so a `stale-game` refusal reaches `sourceChanged` through the existing catch.

A successful write installs the returned stamp with the existing unchanged/changed rule:
`save(stamp)` when the serialized tree is unchanged since the write started, `setSourceStamp(stamp)`
when it changed meanwhile (that result stays `"superseded"`). This success path does not go through
the file-only null-`revision` check of `finishWrite` and records no `verifiedRevision`. A database
row has no file revision. It sets freshness `verified`.

`storeToDatabase` reads `InsertedDbGame` and installs its `stamp` on the admitted `database` origin
instead of `null`.

`BoardAnalysis`'s user-save `"conflict"` toast `Tab.SaveMayHaveBeenWritten` stays for a tab without
any origin it can show a panel for, and is not shown for a `database` origin. That tab's refusal
shows the O5 panel instead, because nothing was written.

### O5 — The conflict panel for database tabs

`DatabaseOriginGate` receives `closeTab` and reads `useFileFreshness(tabId)`. A collection-indexed
database keeps its existing `RetiredOriginRecovery` precedence. Every freshness state except
`conflict` and `unavailable` renders the board, including the default `unverified` of a freshly
opened or reloaded tab. A database tab has no reconcile, and its CAS runs at save time. In
`conflict` and `unavailable` the board is unmounted (which stops auto-save repeating) and the panel
renders in the existing shape (layout, `classes.panel`, `data-file-freshness` marker):

* `conflict`: text `FileFreshness.ChangedInDatabase`, buttons **Reload from database** and
  **Save my version as a new game…**.
* `unavailable` (the row is gone): text `FileFreshness.GameNoLongerInDatabase`, buttons **Save my
  version as a new game…** and **Close**, as the file panel offers.

**Reload from database** calls `getDbGame` bound to the panel's tab, origin and tree store, and
aborts on unmount, as `reloadFromDisk` is. It installs the tree from the shared O2 conversion
(row FEN, row headers, row stamp) through the existing tree-install sequence and sets freshness
`verified`. `GameNotFound` (`missing-resource`) sets `unavailable` without touching the tree. Any
other failure shows its message in the panel and keeps the tree.

**Save my version as a new game…** inserts the tab's tree into the same database through the
existing `storeToDatabase` insert-and-admit path (no second insert implementation). It moves the tab
to the new game id with the inserted stamp and sets freshness `verified`. Failures follow the file
panel's `appendAsNewGame` contract: a `failed` result shows its message as the panel error, an
uncertain store shows the existing uncertain-store message, the tree is kept, and with
`throwOnFailure` the error is rethrown to the caller. The action is registered through
`registerFileConflictSave`, which the close modal uses in `unavailable`. In `conflict` the close
modal keeps its file behaviour: it retries the save, which is refused, then activates the tab and
cancels the close, so the panel is visible with the edits intact.

Copy: reuse `FileFreshness.SaveAsNewGame` and `Tab.Close`. New keys only where "disk"/"file" would be
false: `FileFreshness.ChangedInDatabase` ("This game changed in the database while you were
editing."), `FileFreshness.ReloadFromDatabase` ("Reload from database") and

## Decisions and trade-offs

### Decided autonomously

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** does `NormalizedGame.stamp` become required? **Chosen:** optional on the DTO, always
  filled natively. **Rejected:** required, which forces invented stamps on renderer-built Lichess
  rows that never reach `write_db_game`. **Reason:** a missing stamp already fails safe under O4.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

# Plan: database game saves refuse a stale tab (f-20261101-15)

## Goal

A database-backed analysis tab can overwrite its stored game only when the stored row still equals
the row the tab was loaded from or last saved. Otherwise the save is refused as `stale-game` and the
tab shows the existing conflict panel, with its edits preserved. Closes f-20261101-15.

## MANDATE

f-20261101-15, verbatim:

* **Where:** `src/utils/tabs.ts` `saveToFileNow` database branch (`tauri.writeDbGame(databaseOrigin.database, databaseOrigin.gameId, pgn)`, around line 1184, no stamp or revision), `src-tauri/src/db/mod.rs:4106-4220` (`write_db_game` / `write_parsed_db_game` update by id unconditionally), auto-save in `src/components/boards/BoardAnalysis.tsx` (default on), `src/utils/databaseGame.ts` (opening a game always builds a new tab), Duplicate tab in `BoardsPage.tsx` copying `gameOrigin`.
* **Defect:** file-backed saves are compare-and-swap on a range stamp and go through `fileFreshness`; database saves have no revision at all, so a stale tab's whole tree overwrites newer content written by another tab.
* **Failure scenario:** open game #812 in tab A and add a variation (auto-saved); open #812 again into tab B, add comments (auto-saved); return to A and play one move: A's older tree overwrites the row and B's comments are gone, with no conflict shown. Duplicate tab on a database game reproduces it immediately.
* **Open question:** which row revision does a database tab carry (stored-content hash or an update counter column, which needs a migration), how is it returned on load and checked inside the write transaction, and how does a `stale-game` refusal reach the existing conflict panel for database tabs?

## Threat model and non-goals

The adversary is ordinary concurrency inside one app process: two or more tabs (opened separately
or through Duplicate tab) editing the same `games` row with auto-save on, plus any other in-app
writer of that row (merge players, a second save path). The one-process-per-root instance lock
(`async-resource-invariants.md`) covers the rest. A second process writing the same SQLite file
through a user-picked shared directory is outside it, but the check still runs inside the write
transaction under SQLite's write lock, so it also refuses such a writer's stale save. Hand edits to
the SQLite file with external tools are not modelled beyond that. Non-goal: three-way merging of
two tabs' edits. The conflict panel lets the user choose a version, as it does for files.

## Approach

### O1 — Row stamp: a content hash of the stored `games` row

The revision is a stored-content stamp: SHA-256 hex of a canonical, length-delimited encoding of
every column of the `Game` row, computed natively by one function. No migration and no new column.
Two rows with equal stored content have equal stamps. That is correct, because a save over equal
content loses nothing. Any in-app change to the row (another tab's save, a player merge that
rewrites `white_id`) changes the stamp. A safe refusal over a change that did not touch the movetext
is accepted, as in `d-20260925-10`. The encoding must distinguish `None` from an empty string and
must not let adjacent fields collide.

### O2 — The stamp travels with the row it describes and lands on the seeded tree

`NormalizedGame` gains an optional `stamp` field (`Option<String>`, `#[specta(optional)]`), always
filled by `normalize_games` from the same row it normalizes. Every native producer (`get_games`,
position search, and the existing `get_db_game`, which shares `load_games` with `get_games`)
therefore carries a stamp matching its own displayed content,
including cached search results (stale and self-consistent, so a save from them is refused, never
lost). Renderer-built `NormalizedGame` values that are not database rows (Lichess explorer) carry
none. A database tab without a stamp fails safe under O4.

The open path (`openDatabaseGame` → `databaseGameSeed` → `createTab`, which every database open
path including the Recent Files reopen uses) sets the row stamp on `TreeState.sourceStamp` of the
seeded tree before `tabStorage.seed`, only when the final origin is `database`. When `resolveLinkedGame` turns the open
into a file-backed tab, the linked branch keeps `linked.game.stamp` (a PGN-range stamp). The row
stamp is never copied from `NormalizedGame.linked.stamp` or from headers. Duplicate tab copies the
persisted tree, and with it the stamp, so the first save wins and the second is refused.

The conversion from a `NormalizedGame` to a tree (parse `moves` from the row's `fen`, assign the
row's fields as headers, set the row stamp) exists once and is used by both opening a game and the
O5 reload.

### O3 — Compare-and-swap inside the write transaction

`write_db_game` takes the expected stamp and returns the new stamp. Inside the existing
`with_validated_mutation` closure, `write_parsed_db_game` selects the full row for the id, compares
its stamp with the expected one, and returns `Error::StaleGame` on mismatch before any write (the
transaction rolls back, no data revision bump). A missing row stays `GameNotFound`. After the update
it reads the row back in the same transaction and returns the new row's stamp. `insert_db_game`
returns one named Specta struct `InsertedDbGame { id, stamp }`, the stamp read from the inserted row
in the same transaction. The O5 reload uses the existing `get_db_game` unchanged in shape: it
returns the stamp through `load_games`, so no new read command is added. No `unwrap`/`expect` on
these paths. Bindings are regenerated, never hand-edited.

### O4 — Renderer save contract for database tabs

The database branch of `saveToFileNow` sends the tree's `sourceStamp`. A `null` stamp (a database
tab persisted before this change, or a tree whose stamp is unknown) is refused through
`sourceChanged` without a write, exactly as the file branch does (`tabs.ts:1190`). The branch sets
`writingCurrentOrigin`, so a `stale-game` refusal reaches `sourceChanged` through the existing catch.

A successful write installs the returned stamp with the existing unchanged/changed rule:
`save(stamp)` when the serialized tree is unchanged since the write started, `setSourceStamp(stamp)`
when it changed meanwhile (that result stays `"superseded"`). This success path does not go through
the file-only null-`revision` check of `finishWrite` and records no `verifiedRevision`. A database
row has no file revision. It sets freshness `verified`.

`storeToDatabase` reads `InsertedDbGame` and installs its `stamp` on the admitted `database` origin
instead of `null`.

`BoardAnalysis`'s user-save `"conflict"` toast `Tab.SaveMayHaveBeenWritten` stays for a tab without
any origin it can show a panel for, and is not shown for a `database` origin. That tab's refusal
shows the O5 panel instead, because nothing was written.

### O5 — The conflict panel for database tabs

`DatabaseOriginGate` receives `closeTab` and reads `useFileFreshness(tabId)`. A collection-indexed
database keeps its existing `RetiredOriginRecovery` precedence. Every freshness state except
`conflict` and `unavailable` renders the board, including the default `unverified` of a freshly
opened or reloaded tab. A database tab has no reconcile, and its CAS runs at save time. In
`conflict` and `unavailable` the board is unmounted (which stops auto-save repeating) and the panel
renders in the existing shape (layout, `classes.panel`, `data-file-freshness` marker):

* `conflict`: text `FileFreshness.ChangedInDatabase`, buttons **Reload from database** and
  **Save my version as a new game…**.
* `unavailable` (the row is gone): text `FileFreshness.GameNoLongerInDatabase`, buttons **Save my
  version as a new game…** and **Close**, as the file panel offers.

**Reload from database** calls the existing `getDbGame(origin.database, origin.gameId, null)`
bound to the panel's tab, origin and tree store, and aborts on unmount, as `reloadFromDisk` is.
`linked` is `null` because a collection-indexed database never reaches this panel
(`RetiredOriginRecovery` precedence), so `gameId` is a row id of an ordinary database. `found`
installs the tree from the shared O2 conversion (row FEN, row headers, row stamp) through the
existing tree-install sequence and sets freshness `verified`. `{ kind: "missing" }` sets
`unavailable` without touching the tree. Any error shows its message in the panel and keeps the
tree.

**Save my version as a new game…** inserts the tab's tree into the same database through the
existing `storeToDatabase` insert-and-admit path (no second insert implementation). It moves the tab
to the new game id with the inserted stamp and sets freshness `verified`. Failures follow the file
panel's `appendAsNewGame` contract: a `failed` result shows its message as the panel error, an
uncertain store shows the existing uncertain-store message, the tree is kept, and with
`throwOnFailure` the error is rethrown to the caller. The action is registered through
`registerFileConflictSave`, which the close modal uses in `unavailable`. In `conflict` the close
modal keeps its file behaviour: it retries the save, which is refused, then activates the tab and
cancels the close, so the panel is visible with the edits intact.

Copy: reuse `FileFreshness.SaveAsNewGame` and `Tab.Close`. New keys only where "disk"/"file" would be
false: `FileFreshness.ChangedInDatabase` ("This game changed in the database while you were
editing."), `FileFreshness.ReloadFromDatabase` ("Reload from database") and
`FileFreshness.GameNoLongerInDatabase` ("This game is no longer in the database."). They are added to
every locale per `docs/localization.md` and extracted with `i18next-cli`.

## Decisions and trade-offs

### Refresh to `062c84e2` (drift from `7cea140f`)

The base gained `get_db_game` and `openDatabaseGame` (Recent Files, `c3680f10`) and the quit gate
(`dbf8ef28`). The plan reuses the existing `get_db_game` instead of adding a second single-game
read (async-resource-invariants: one operation type, one facade), maps its `missing` result to
`unavailable`, seeds the stamp through `openDatabaseGame`, and moves Phase 2 to renderer only.
Phase proofs add the push skill's new related-tests form.

### Decided autonomously

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** does `NormalizedGame.stamp` become required? **Chosen:** optional on the DTO, always
  filled natively. **Rejected:** required, which forces invented stamps on renderer-built Lichess
  rows that never reach `write_db_game`. **Reason:** a missing stamp already fails safe under O4.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

## Threat model and non-goals

The adversary is ordinary concurrency inside one app process: two or more tabs (opened separately
or through Duplicate tab) editing the same `games` row with auto-save on, plus any other in-app
writer of that row (merge players, a second save path). The one-process-per-root instance lock
(`async-resource-invariants.md`) covers the rest. A second process writing the same SQLite file
through a user-picked shared directory is outside it, but the check still runs inside the write
transaction under SQLite's write lock, so it also refuses such a writer's stale save. Hand edits to
the SQLite file with external tools are not modelled beyond that. Non-goal: three-way merging of
two tabs' edits. The conflict panel lets the user choose a version, as it does for files.

## Approach

### O1 — Row stamp: a content hash of the stored `games` row

The revision is a stored-content stamp: SHA-256 hex of a canonical, length-delimited encoding of
every column of the `Game` row, computed natively by one function. No migration and no new column.
Two rows with equal stored content have equal stamps. That is correct, because a save over equal
content loses nothing. Any in-app change to the row (another tab's save, a player merge that
rewrites `white_id`) changes the stamp. A safe refusal over a change that did not touch the movetext
is accepted, as in `d-20260925-10`. The encoding must distinguish `None` from an empty string and
must not let adjacent fields collide.

### O2 — The stamp travels with the row it describes and lands on the seeded tree

`NormalizedGame` gains an optional `stamp` field (`Option<String>`, `#[specta(optional)]`), always
filled by `normalize_games` from the same row it normalizes. Every native producer (`get_games`,
position search, and the existing `get_db_game`, which shares `load_games` with `get_games`)
therefore carries a stamp matching its own displayed content,
including cached search results (stale and self-consistent, so a save from them is refused, never
lost). Renderer-built `NormalizedGame` values that are not database rows (Lichess explorer) carry
none. A database tab without a stamp fails safe under O4.

The open path (`openDatabaseGame` → `databaseGameSeed` → `createTab`, which every database open
path including the Recent Files reopen uses) sets the row stamp on `TreeState.sourceStamp` of the
seeded tree before `tabStorage.seed`, only when the final origin is `database`. When `resolveLinkedGame` turns the open
into a file-backed tab, the linked branch keeps `linked.game.stamp` (a PGN-range stamp). The row
stamp is never copied from `NormalizedGame.linked.stamp` or from headers. Duplicate tab copies the
persisted tree, and with it the stamp, so the first save wins and the second is refused.

The conversion from a `NormalizedGame` to a tree (parse `moves` from the row's `fen`, assign the
row's fields as headers, set the row stamp) exists once and is used by both opening a game and the
O5 reload.

### O3 — Compare-and-swap inside the write transaction

`write_db_game` takes the expected stamp and returns the new stamp. Inside the existing
`with_validated_mutation` closure, `write_parsed_db_game` selects the full row for the id, compares
its stamp with the expected one, and returns `Error::StaleGame` on mismatch before any write (the
transaction rolls back, no data revision bump). A missing row stays `GameNotFound`. After the update
it reads the row back in the same transaction and returns the new row's stamp. `insert_db_game`
returns one named Specta struct `InsertedDbGame { id, stamp }`, the stamp read from the inserted row
in the same transaction. The O5 reload uses the existing `get_db_game` unchanged in shape: it
returns the stamp through `load_games`, so no new read command is added. No `unwrap`/`expect` on
these paths. Bindings are regenerated, never hand-edited.

### O4 — Renderer save contract for database tabs

The database branch of `saveToFileNow` sends the tree's `sourceStamp`. A `null` stamp (a database
tab persisted before this change, or a tree whose stamp is unknown) is refused through
`sourceChanged` without a write, exactly as the file branch does (`tabs.ts:1190`). The branch sets
`writingCurrentOrigin`, so a `stale-game` refusal reaches `sourceChanged` through the existing catch.

A successful write installs the returned stamp with the existing unchanged/changed rule:
`save(stamp)` when the serialized tree is unchanged since the write started, `setSourceStamp(stamp)`
when it changed meanwhile (that result stays `"superseded"`). This success path does not go through
the file-only null-`revision` check of `finishWrite` and records no `verifiedRevision`. A database
row has no file revision. It sets freshness `verified`.

`storeToDatabase` reads `InsertedDbGame` and installs its `stamp` on the admitted `database` origin
instead of `null`.

`BoardAnalysis`'s user-save `"conflict"` toast `Tab.SaveMayHaveBeenWritten` stays for a tab without
any origin it can show a panel for, and is not shown for a `database` origin. That tab's refusal
shows the O5 panel instead, because nothing was written.

### O5 — The conflict panel for database tabs

`DatabaseOriginGate` receives `closeTab` and reads `useFileFreshness(tabId)`. A collection-indexed
database keeps its existing `RetiredOriginRecovery` precedence. Every freshness state except
`conflict` and `unavailable` renders the board, including the default `unverified` of a freshly
opened or reloaded tab. A database tab has no reconcile, and its CAS runs at save time. In
`conflict` and `unavailable` the board is unmounted (which stops auto-save repeating) and the panel
renders in the existing shape (layout, `classes.panel`, `data-file-freshness` marker):

* `conflict`: text `FileFreshness.ChangedInDatabase`, buttons **Reload from database** and
  **Save my version as a new game…**.
* `unavailable` (the row is gone): text `FileFreshness.GameNoLongerInDatabase`, buttons **Save my
  version as a new game…** and **Close**, as the file panel offers.

**Reload from database** calls the existing `getDbGame(origin.database, origin.gameId, null)`
bound to the panel's tab, origin and tree store, and aborts on unmount, as `reloadFromDisk` is.
`linked` is `null` because a collection-indexed database never reaches this panel
(`RetiredOriginRecovery` precedence), so `gameId` is a row id of an ordinary database. `found`
installs the tree from the shared O2 conversion (row FEN, row headers, row stamp) through the
existing tree-install sequence and sets freshness `verified`. `{ kind: "missing" }` sets
`unavailable` without touching the tree. Any error shows its message in the panel and keeps the
tree.

**Save my version as a new game…** inserts the tab's tree into the same database through the
existing `storeToDatabase` insert-and-admit path (no second insert implementation). It moves the tab
to the new game id with the inserted stamp and sets freshness `verified`. Failures follow the file
panel's `appendAsNewGame` contract: a `failed` result shows its message as the panel error, an
uncertain store shows the existing uncertain-store message, the tree is kept, and with
`throwOnFailure` the error is rethrown to the caller. The action is registered through
`registerFileConflictSave`, which the close modal uses in `unavailable`. In `conflict` the close
modal keeps its file behaviour: it retries the save, which is refused, then activates the tab and
cancels the close, so the panel is visible with the edits intact.

Copy: reuse `FileFreshness.SaveAsNewGame` and `Tab.Close`. New keys only where "disk"/"file" would be
false: `FileFreshness.ChangedInDatabase` ("This game changed in the database while you were
editing."), `FileFreshness.ReloadFromDatabase` ("Reload from database") and
`FileFreshness.GameNoLongerInDatabase` ("This game is no longer in the database."). They are added to
every locale per `docs/localization.md` and extracted with `i18next-cli`.

## Decisions and trade-offs

### Refresh to `062c84e2` (drift from `7cea140f`)

The base gained `get_db_game` and `openDatabaseGame` (Recent Files, `c3680f10`) and the quit gate
(`dbf8ef28`). The plan reuses the existing `get_db_game` instead of adding a second single-game
read (async-resource-invariants: one operation type, one facade), maps its `missing` result to
`unavailable`, seeds the stamp through `openDatabaseGame`, and moves Phase 2 to renderer only.
Phase proofs add the push skill's new related-tests form.

### Decided autonomously

* **Question:** which row revision does a database tab carry? **Chosen:** a SHA-256 content stamp of
  the full stored `games` row, computed natively. **Rejected:** an update counter column, because it
  needs a schema migration of every user database and the strict existing-database validation for
  no added protection inside one process; the per-file `data_revision`, because any write to any
  other game or an import would refuse every open tab's save. **Reason:** it matches the file path's
  content stamp (`pgn.rs:1242`), needs no persisted-schema change (`sourceStamp` already persists
  64-hex values), and is checked atomically in the existing write transaction. **Reversal path:**
  replace `game_row_stamp` with a counter column read; the IPC and renderer contract (opaque stamp)
  stays.
* **Question:** how is the stamp returned on load? **Chosen:** as a field of `NormalizedGame` from the
  same row read, following `d-20260925-10`. **Rejected:** a separate stamp-fetch at tab open, which
  can observe a newer row than the text the tab shows.
* **Question:** what does a database tab with no stamp (persisted before this change) do on save?
  **Chosen:** refuse as `sourceChanged`, showing the conflict panel with its edits kept.
  **Rejected:** an unconditional legacy write, which keeps the data-loss path for every restored tab.
  **Reason:** same semantics as the file branch's `null` stamp; the panel's Reload/Save-as-new
  resolve it in one click.
* **Question:** does `NormalizedGame.stamp` become required? **Chosen:** optional on the DTO, always
  filled natively. **Rejected:** required, which forces invented stamps on renderer-built Lichess
  rows that never reach `write_db_game`. **Reason:** a missing stamp already fails safe under O4.
* **Question:** which actions does the database conflict panel offer? **Chosen:** Reload from
  database and Save my version as a new game in the same database. **Rejected:** appending to a
  picked PGN file (the file panel's action), because the tab's home is the database; "Keep these
  edits as a new game" (origin `none`), because it drops the tab's persistent origin and auto-save.
  **Reason:** mirrors the file panel's two choices on the tab's own store (precedent: the file
  conflict panel and `d-20261017-12`'s reuse of one append/admit path).

* Hashing is per returned row. Page sizes are small and the moves blob is already decoded per row,
