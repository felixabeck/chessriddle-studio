# Plan: Account sync must import correspondence and daily games that finish after a newer game started

## Goal

Every rated standard-variant game an account finishes is imported by a later account sync, on the
linked path (Linux, macOS) and on the unlinked path (Windows), for Lichess and Chess.com. Games
already lost by the old cursor are recovered once.

## MANDATE

Finding f-20261101-23 (db-search, entry=build, impact data-loss), verbatim:

> * **Where:** Lichess linked path: `src-tauri/src/db/linked_collections.rs:865-877` (cursor = newest game start time), `db/linked_collections/batch.rs:521-531` (`coverage_cursor_ms`), `src/components/home/AccountCard.tsx:316-322` (`sinceMs`), `src-tauri/src/fs.rs:1398-1407` (Lichess `since=`). Unlinked path (Windows, both providers): `getLatestGameTimestamp` (`db/mod.rs:2109-2121`) and `end_headers` skipping start ≤ cursor (`db/mod.rs:571-573`).
> * **Defect:** the cursor is a game start time. Lichess `since` filters on creation time (lila master: `inCreatedAtRange`, `g.createdAt.isAfter`), and the unlinked importer drops games that started before the stored newest start. Chess.com on the linked path is not affected (archives by end month, dedup by provider id).
> * **Failure scenario:** a correspondence game starts 1 Oct, the user syncs after a 10 Oct blitz game, the correspondence game ends 20 Oct: every later sync sends `since=<10 Oct>` and the finished game is never imported. On Windows a Chess.com daily game started 5 Sep and ended 3 Oct is dropped because the newest stored game started 19 Sep.
> * **Open question:** how far back must the Lichess cursor reach (longest correspondence time control, or a separate query for games ongoing at the last sync), and should the unlinked path dedup by provider game id (Site/Link) instead of filtering by start time?

## Threat model and non-goals

Inputs: provider HTTP responses (Lichess export stream, Lichess ongoing-games stream, Chess.com
archives), the user's existing account database or linked collection, and the persisted
linked-collection registry. The adversary is an ordinary malformed or surprising provider
response (missing header, unparseable timestamp, truncated stream) and an existing install whose
cursor was written by the old code. No hostile provider is assumed. Clock skew on the user's
machine is real and must not move a cursor.

Non-goals: which games are imported (rated, standard perf types) does not change; Chess.com
variant handling (f-20261101-07 and siblings) is not touched; the co-located findings
f-20261101-07 and f-20261101-10 are not part of this plan.

## Approach

### O1 — Lichess coverage floor from the games ongoing at sync time

Answers the open question with "a separate query for games ongoing at the last sync" (MANDATE).
A fixed correspondence lookback is rejected: a Lichess correspondence game has no maximum
duration, so no window is complete.

Before the export request, `download_lichess_games_runtime` makes one authenticated request for
the account's ongoing games (`/api/games/user/<player>?ongoing=true&finished=false`, NDJSON, no
`perfType`/`rated`, so lila takes the Mongo `nowPlaying` branch). It keeps only games that the
export itself would return (rated, perf in the same perf set `lichess_games_url` sends; one shared
constant, rule 11). From the response it derives a **coverage floor**:
`floor = min(earliest kept ongoing createdAt − 1 ms, server Date header − 60 s)`.
The Date cap covers games created between the ongoing snapshot and the export; it uses the
server's clock, never the local clock.

Failure semantics: a failed or rejected ongoing request, an unparseable NDJSON line, a missing
`createdAt`, or a missing/unparseable `Date` header fails the download with the same typed error
mapping the export uses (no bearer token or raw body in the error). A download never proceeds with
an unknown floor. The query runs only in the Lichess runtime path, so both the account workflow
and the plain `download_lichess_games` command get it.

The floor travels with the download result (`RuntimeDownload`) into both receipt paths (O2, O3).
Chess.com has no floor (`None`), because archives are keyed by end month.

### O2 — Linked cursor is the newest start that is safe to skip, and may move backwards

`record_download` takes the floor. The receipt's `through_ms` becomes
`min(max(since, newest start in the batch), floor)` when a floor is present. `through_ms` may be
lower than `since` (an ongoing game older than the cursor).

Receipt application in `batch.rs` replaces the cursor with `through_ms` instead of taking
`max(cursor, through)`. The existing contiguity guard (`receipt.since` none or `<= cursor`) stays;
a stale receipt can only lower the cursor, which only re-fetches more and is harmless because the
merge dedups by provider id. The cursor never advances past a floor recorded by the receipt being
applied.

Legacy recovery: a Lichess record whose cursor was written by the old semantics is reported with
`fetch_since_ms = None` once, so the next sync re-exports full history and the dedup merge adds
exactly the games the old cursor lost. A new persisted marker distinguishes new-semantics cursors
(`#[serde(default)]`, so old registries load); Chess.com records keep their cursor (not affected,
MANDATE). Registry compatibility: an older build reading a newer registry must still load it or the
change must follow the registry's existing versioning rule — the executor checks
`deny_unknown_fields` on the record and the registry version handling and uses whichever the
existing schema rule requires.

### O3 — Unlinked import dedups instead of filtering by start time, with a stored cursor

The account import's start-time skip (`Importer` `timestamp`) is removed. An unlinked account
import skips a game only when the target database already contains a game with the same identity
key: ASCII-lowercased White name, Black name, Date and UTCTime (the header part of
`semantic_fingerprint`; one shared normalisation helper, rule 11). Moves are not part of the key:
the stored encoding cannot be compared cheaply and two games with the same players and start
second do not occur for one account. Games inside one batch are deduplicated by the same key.

The unlinked cursor is stored in the target database's `Info` table (one row per database,
name `AccountSyncCursor`, value = cursor in milliseconds), written in the same transaction as the
imported games. Its value follows O2's rule: `min(max(since, newest start seen in the file), floor)`
for Lichess, `max(since, newest start seen)` for Chess.com. "Seen" includes games skipped as
duplicates.

The cursor is native authority: the account workflow reads it from the target database for an
unlinked target and uses it as `since_ms` for the download, instead of trusting the renderer's
value. A database without the row (every database written by the old code, and every new one)
has no cursor, so the first sync is full history and the dedup recovers the lost games.
`get_latest_game_timestamp` and `convert_pgn`'s `timestamp` parameter lose their only callers and
are removed together with the generated bindings and the renderer code that passed them
(`AccountCard.tsx`, `tauri.ts`, tests).

The floor for an unlinked Lichess import comes from O1's download result and is retained with the
account completion snapshot so a retried import uses the same value. If an import runs without a
floor for a Lichess download (any path where it is unavailable), the cursor is not advanced past
`since`.

## Approach

### O1 — Lichess coverage holds from a consistent second stream

Answers the open question with "a separate query for games ongoing at the last sync" (MANDATE),
widened so it also covers a game that finished but is not yet in the export's search index.
A fixed correspondence lookback is rejected: a Lichess correspondence game has no maximum
duration, so no window is complete.

After the export request completes, `download_lichess_games_runtime` makes one authenticated
**coverage request** for the same account and the same `since`:
`/api/games/user/<player>?since=<since>&ongoing=true&moves=false&tags=false&clocks=false&evals=false&opening=false`
with `Accept: application/x-ndjson` and no `perfType`/`rated`, so lila serves it from Mongo
(`exportByUser` Mongo branch, `Query.createdBetween`, no `Query.finished` filter): every game
created after `since`, ongoing or finished. Each line carries `id`, `rated`, `perf`, `status`,
`createdAt`, `lastMoveAt` (lila `GameApiV2.toJson`, probed 2026-11-03). Order matters: the
coverage request runs after the export, so a game created during or after the export appears here.

A line is **eligible** when it is a game the export is meant to return: `rated` and `perf` in the
perf set `lichess_games_url` sends (one shared constant, rule 11), and `status` not `aborted` or
`noStart`. An eligible line becomes a **coverage hold** `(id, createdAt)` when its status is
`created` or `started` (ongoing), or when it is finished and its `lastMoveAt` is within
`INDEX_LAG_WINDOW` (10 minutes) of the coverage response's server `Date` header (a just-finished
game the export's search index may not contain yet). Holds are bounded by a named maximum count;
exceeding it fails the download.

Failure semantics: a failed or rejected coverage request, an unparseable NDJSON line, a line
missing one of the fields above, a missing or unparseable `Date` header, or more holds than the
bound fails the download with the same typed error mapping the export uses (no bearer token or
raw body in the error). A download never proceeds without its holds. The request runs only in the
Lichess runtime path, so the account workflow and the plain `download_lichess_games` command both
get it.

`RuntimeDownload` (`src-tauri/src/infra/operations.rs`) carries `coverage_holds:
Option<Vec<CoverageHold>>`: `Some` for Lichess, `None` for Chess.com (archives are keyed by end
month, MANDATE).

### O2 — One cursor rule, applied on both receipt paths

One shared function computes the next cursor from `since`, the games actually present in the
downloaded file, and the holds (rule 11: O2 and O3 call it):

* `newest = max(since, newest UTCDate/UTCTime start among games in the file)`;
* for Lichess, `floor = min(createdAt − 1 ms)` over holds that are ongoing **or** whose id is not among the file's provider game ids (`provider_game_id`); a finished hold that is in the file is covered and does not hold;
* `cursor = min(newest, floor)` for Lichess, `newest` for Chess.com. Holds are created after `since` (the coverage request uses the same `since`), so the cursor never falls below `since`.
* A Lichess download without holds (`None`) never advances the cursor past `since`.

Linked path: `record_download` takes the holds and stores the result as the receipt's
`through_ms`. Receipt application in `batch.rs` replaces the cursor with `through_ms` instead of
taking `max(cursor, through)`. The existing contiguity guard (`receipt.since` none or `<= cursor`)
stays; a stale receipt can only lower the cursor, which only re-fetches more and is harmless
because the merge dedups by provider id. If holds must be persisted with a pending receipt, the
receipt keeps its computed `through_ms` instead of the hold list.

Legacy recovery (linked): a Lichess record whose cursor was written by the old semantics is
reported with `fetch_since_ms = None` once, so the next sync re-exports full history and the
dedup merge adds exactly the games the old cursor lost. A new persisted marker distinguishes
new-semantics cursors (`#[serde(default)]`, so old registries load); Chess.com records keep their
cursor (not affected, MANDATE). The executor checks `deny_unknown_fields` and the registry's
existing version handling and follows whichever compatibility rule that schema already uses.

### O3 — Unlinked import dedups by game identity, with a stored cursor

The account import's start-time skip (`Importer` `timestamp`) is removed. An unlinked account
import skips a game only when the target database already contains the same game, or the same
game occurred earlier in the same file. **Same game** means equal ASCII-lowercased White and Black
names, Date and UTCTime, equal starting FEN, and equal encoded move sequence: the fields
`semantic_fingerprint` uses, compared against stored rows (candidate rows selected by players,
date and time, then compared on FEN and the encoded moves the importer produces). Two different
games collide only if they share players, start second, start position and every move, which is
the same game. No provider id is needed, so Chess.com games (id only in `Link`, which the database
does not store) are covered.

A game with a missing or unparseable Date/UTCTime is imported as before (the unlinked importer
already accepts it, and dedup compares the absent fields as absent). It does not contribute to
the cursor. No game is dropped because of its headers.

The unlinked cursor is stored in the target database's `Info` table (row `AccountSyncCursor`,
value = cursor in milliseconds), written in the same transaction as the imported games, using
O2's shared cursor rule. "Games in the file" includes games skipped as duplicates.

The cursor is native authority: the account workflow reads it from the target database for an
unlinked target and uses it as the download's `since_ms`, instead of the renderer's value. A
database without the row (every database written by the old code, and every new one) has no
cursor, so the first sync is full history and the dedup recovers the lost games.
`get_latest_game_timestamp` and `convert_pgn`'s `timestamp` parameter lose their only callers and
are removed with the generated bindings and the renderer code that passed them (`AccountCard.tsx`,
`tauri.ts`, tests).

`adopt_account_download` keeps the holds instead of discarding them, and the account completion
snapshot retains them so a retried conversion uses the same holds. Wherever a Lichess conversion
runs without them, O2's `None` rule applies.

Decided autonomously (full auto), to be recorded by the adopter:

# Plan: Account sync must import correspondence and daily games that finish after a newer game started

## Goal

Every rated standard-variant game an account finishes is imported by a later account sync, on the
linked path (Linux, macOS) and on the unlinked path (Windows), for Lichess and Chess.com. Games
already lost by the old cursor are recovered once.

## MANDATE

Finding f-20261101-23 (db-search, entry=build, impact data-loss), verbatim:

> * **Where:** Lichess linked path: `src-tauri/src/db/linked_collections.rs:865-877` (cursor = newest game start time), `db/linked_collections/batch.rs:521-531` (`coverage_cursor_ms`), `src/components/home/AccountCard.tsx:316-322` (`sinceMs`), `src-tauri/src/fs.rs:1398-1407` (Lichess `since=`). Unlinked path (Windows, both providers): `getLatestGameTimestamp` (`db/mod.rs:2109-2121`) and `end_headers` skipping start ≤ cursor (`db/mod.rs:571-573`).
> * **Defect:** the cursor is a game start time. Lichess `since` filters on creation time (lila master: `inCreatedAtRange`, `g.createdAt.isAfter`), and the unlinked importer drops games that started before the stored newest start. Chess.com on the linked path is not affected (archives by end month, dedup by provider id).
> * **Failure scenario:** a correspondence game starts 1 Oct, the user syncs after a 10 Oct blitz game, the correspondence game ends 20 Oct: every later sync sends `since=<10 Oct>` and the finished game is never imported. On Windows a Chess.com daily game started 5 Sep and ended 3 Oct is dropped because the newest stored game started 19 Sep.
> * **Open question:** how far back must the Lichess cursor reach (longest correspondence time control, or a separate query for games ongoing at the last sync), and should the unlinked path dedup by provider game id (Site/Link) instead of filtering by start time?

## Threat model and non-goals

Inputs: provider HTTP responses (Lichess export stream, Lichess ongoing-games stream, Chess.com
archives), the user's existing account database or linked collection, and the persisted
linked-collection registry. The adversary is an ordinary malformed or surprising provider
response (missing header, unparseable timestamp, truncated stream) and an existing install whose
cursor was written by the old code. No hostile provider is assumed. Clock skew on the user's
machine is real and must not move a cursor.

Non-goals: which games are imported (rated, standard perf types) does not change; Chess.com
variant handling (f-20261101-07 and siblings) is not touched; the co-located findings

## Approach

### O1 — Lichess coverage holds from a consistent second stream

Answers the open question with "a separate query for games ongoing at the last sync" (MANDATE),
widened so it also covers a game that finished but is not yet in the export's search index.
A fixed correspondence lookback is rejected: a Lichess correspondence game has no maximum
duration, so no window is complete.

After the export request completes, `download_lichess_games_runtime` makes one authenticated
**coverage request** for the same account and the same `since`:
`/api/games/user/<player>?since=<since>&ongoing=true&moves=false&tags=false&clocks=false&evals=false&opening=false`
with `Accept: application/x-ndjson` and no `perfType`/`rated`, so lila serves it from Mongo
(`exportByUser` Mongo branch, `Query.createdBetween`, no `Query.finished` filter): every game
created after `since`, ongoing or finished. The request goes through `state.http_transport` like
the export, so tests observe it. Each line carries `id`, `rated`, `perf`, `status` and
`createdAt` (lila `GameApiV2.toJson`, probed 2026-11-03); those five are required. Order matters: the
coverage request runs after the export, so a game created during or after the export appears here.

A line is **eligible** when it is a game the export is meant to return: `rated` and `perf` in the
perf set `lichess_games_url` sends (one shared constant, rule 11), and `status` not `aborted` or
`noStart`. Every eligible line becomes a **coverage hold** `(id, createdAt, ongoing)`, where
`ongoing` means `status` is `created` or `started`. No time window decides whether a finished
game is covered: `lastMoveAt` is `g.movedAt`, which lila leaves unchanged when a game ends on
time or by resignation, so it says nothing about when the game finished or entered the search
index. Whether a finished hold is covered is decided only by its presence in the downloaded file
(O2). Holds are bounded by a named maximum count; exceeding it fails the download.

Failure semantics: a failed or rejected coverage request, an unparseable NDJSON line, a line
missing one of the fields above, or more holds than the bound fails the download with the same typed error mapping the export uses (no bearer token or
raw body in the error). A download never proceeds without its holds. The request runs only in the
Lichess runtime path, so the account workflow and the plain `download_lichess_games` command both
get it.

`RuntimeDownload` (`src-tauri/src/infra/operations.rs`) carries `coverage_holds:
Option<Vec<CoverageHold>>`: `Some` for Lichess, `None` for Chess.com (archives are keyed by end
month, MANDATE).

### O2 — One cursor rule, applied on both receipt paths

One shared function computes the next cursor from `since`, the games actually present in the
downloaded file, and the holds (rule 11: O2 and O3 call it):

* `newest = max(since, newest UTCDate/UTCTime start among games in the file)`;
* for Lichess, `floor = min(createdAt − 1 ms)` over holds that are ongoing **or** whose id is not among the file's provider game ids (`provider_game_id`); a finished hold that is in the file is covered and does not hold. A finished eligible game the export omitted therefore holds the cursor until an export contains it, however long ago its last move was;
* `cursor = min(newest, floor)` for Lichess, `newest` for Chess.com. Holds are created after `since` (the coverage request uses the same `since`), so the cursor never falls below `since`.
* A Lichess download without holds (`None`) never advances the cursor past `since`.

Linked path: `record_download` takes the holds and stores the result as the receipt's
`through_ms`. Receipt application in `batch.rs` replaces the cursor with `through_ms` instead of
taking `max(cursor, through)`. The existing contiguity guard (`receipt.since` none or `<= cursor`)
stays; a stale receipt can only lower the cursor, which only re-fetches more and is harmless
because the merge dedups by provider id. If holds must be persisted with a pending receipt, the
receipt keeps its computed `through_ms` instead of the hold list.

Legacy recovery (linked): a Lichess record whose cursor was written by the old semantics is
reported with `fetch_since_ms = None` once, so the next sync re-exports full history and the
dedup merge adds exactly the games the old cursor lost. A new persisted marker distinguishes
new-semantics cursors (`#[serde(default)]`, so old registries load); Chess.com records keep their
cursor (not affected, MANDATE). The executor checks `deny_unknown_fields` and the registry's
existing version handling and follows whichever compatibility rule that schema already uses.

### O3 — Unlinked import dedups by game identity, with a stored cursor

The account import's start-time skip (`Importer` `timestamp`) is removed. An unlinked account
import decides whether a game is already present by the same identity rule the linked merge uses
(`batch.rs`): the **provider game id** (`provider_game_id`: Lichess `Site`, Chess.com `Link`)
decides when the game has one; the **semantic fingerprint** (`semantic_fingerprint`: players,
Date, UTCTime, starting FEN, mainline moves) is used only to reconcile a stored row that has no
recorded provider id. Both functions are shared with the linked path, not copied (rule 11).

The account database records provider ids in a new table created on first account import
(`CREATE TABLE IF NOT EXISTS`, one row per imported game: provider, provider game id, `Games.ID`),
written in the import transaction. Older builds ignore the table. For each incoming game:

* id already recorded → skip;
* id not recorded, and an unclaimed stored row without a recorded id has the same fingerprint → skip and record the id for that row (each stored row is claimed by at most one id);
* otherwise → import and record the id;
* no provider id → skip only when a stored row or an earlier game in the same file has the same fingerprint.

Two distinct provider games are never merged because of equal fingerprints, including equal moves
and absent UTCTime. If one incoming id matches several unclaimed fingerprint-equal stored rows,
one of them is claimed and the rest stay unclaimed; no game is dropped by that choice.

A game with a missing or unparseable Date/UTCTime is imported as before (the unlinked importer
already accepts it). Its identity follows the rule above. It does not contribute to the cursor. No game is dropped because of its headers.

The unlinked cursor is stored in the target database's `Info` table (row `AccountSyncCursor`,
value = cursor in milliseconds), written in the same transaction as the imported games, using
O2's shared cursor rule. "Games in the file" includes games skipped as duplicates.

The cursor is native authority: the account workflow reads it from the target database for an
unlinked target and uses it as the download's `since_ms`, instead of the renderer's value. A
database without the row (every database written by the old code, and every new one) has no
cursor, so the first sync is full history and the dedup recovers the lost games.
`get_latest_game_timestamp` and `convert_pgn`'s `timestamp` parameter lose their only callers and
are removed with the generated bindings and the renderer code that passed them (`AccountCard.tsx`,
`tauri.ts`, tests).

`adopt_account_download` keeps the holds instead of discarding them, and the account completion
snapshot retains them so a retried conversion (after a failed conversion, using the retained
publication) uses the same holds. Wherever a Lichess conversion
runs without them, O2's `None` rule applies.

## Decisions and trade-offs

Decided autonomously (full auto), to be recorded by the adopter:

* **D1 — Lichess cursor reach.** Chosen: after the export, a Mongo-served coverage stream for the same `since` yields holds for ongoing and just-finished games, and the cursor stops before the oldest hold the export did not cover (O1, O2). Rejected: a fixed lookback of the longest correspondence time control (incomplete: a correspondence game has no maximum duration); an ongoing-only query (`finished=false`, the r1 plan), which loses a game that finished seconds before the query while still missing from the export's search index; replacing the export with the Mongo stream (the PGN cannot tell rated from casual for arena games, so local filtering would change which games are imported); dropping `since` and re-exporting full history every sync (minutes per sync for large accounts); storing ongoing ids and fetching them by id next sync (`POST /api/games/export/_ids`), which needs a second download into the same staging artefact and still misses a just-finished new game. Trade-off: the coverage stream doubles the per-game transfer time of a sync (60 games/s for one's own games, without moves), and while a rated correspondence game is open every sync re-exports the games started since it began; dedup discards them. Reversal path: the ids approach plus a delay, if the cost is observed to matter.
* **D2 — Unlinked dedup key.** Chosen: the linked merge's identity rule — provider game id decides, fingerprint only reconciles stored rows without a recorded id — with ids recorded in a new account-database table (O3). Rejected: header identity without moves (r1; collapses two daily games with the same players and start second); fingerprint alone including moves (r2; still collapses distinct games with identical moves or absent UTCTime, which the linked path deliberately keeps apart); writing Chess.com's `Link` into `Site` (changes what the database shows for every Chess.com game); keeping the start-time filter with a lookback (incomplete, same reason as D1).
* **D6 — Holds for finished games.** Chosen: every eligible finished game absent from the export holds, with no time window. Rejected: a `lastMoveAt` recency window (r2), because `lastMoveAt` does not change when a game ends on time or by resignation and is measured after a possibly long export. Reversal path: if a stuck hold is observed, fetch the held finished games by id (`POST /api/games/export/_ids`) into the batch.
* **D3 — Legacy cursors.** Chosen: one full-history sync for Lichess linked records and for every unlinked account database, deduplicated. Rejected: trusting old cursors (keeps the lost games lost); a partial lookback (incomplete). Cost: one longer sync per affected account after the update.
* **D4 — Coverage-request failure.** Chosen: fail the download with the existing typed error. Rejected: proceeding without holds and freezing the cursor (silent, and every later sync would re-export the same window without telling the user why).
* **D5 — Unlinked games without a start time.** Chosen: import them and leave them out of the cursor, as the unlinked importer does today. Rejected: rejecting the whole import (the linked receipt's behaviour), which would block every later sync of that account on one malformed provider game.

## Risks / open questions

* A rated game that lila's search index never returns holds the cursor at its start indefinitely: every later sync re-exports from there. That costs transfer time, never a game. The hold bound turns a widespread index failure into a typed download error rather than unbounded growth.
* The one-time full-history sync after the update (D3) re-imports a legacy game the user deleted from an unlinked account database, because no recorded id or stored row remembers it.
* The coverage stream is one extra request per Lichess sync and counts against Lichess rate limits; its transfer time equals the export's game count at 60 games/s without moves.

# Plan: Account sync must import correspondence and daily games that finish after a newer game started

## Goal

Every rated standard-variant game an account finishes is imported by a later account sync, on the
linked path (Linux, macOS) and on the unlinked path (Windows), for Lichess and Chess.com. Games
already lost by the old cursor are recovered once.

## MANDATE

Finding f-20261101-23 (db-search, entry=build, impact data-loss), verbatim:

> * **Where:** Lichess linked path: `src-tauri/src/db/linked_collections.rs:865-877` (cursor = newest game start time), `db/linked_collections/batch.rs:521-531` (`coverage_cursor_ms`), `src/components/home/AccountCard.tsx:316-322` (`sinceMs`), `src-tauri/src/fs.rs:1398-1407` (Lichess `since=`). Unlinked path (Windows, both providers): `getLatestGameTimestamp` (`db/mod.rs:2109-2121`) and `end_headers` skipping start ≤ cursor (`db/mod.rs:571-573`).
> * **Defect:** the cursor is a game start time. Lichess `since` filters on creation time (lila master: `inCreatedAtRange`, `g.createdAt.isAfter`), and the unlinked importer drops games that started before the stored newest start. Chess.com on the linked path is not affected (archives by end month, dedup by provider id).
> * **Failure scenario:** a correspondence game starts 1 Oct, the user syncs after a 10 Oct blitz game, the correspondence game ends 20 Oct: every later sync sends `since=<10 Oct>` and the finished game is never imported. On Windows a Chess.com daily game started 5 Sep and ended 3 Oct is dropped because the newest stored game started 19 Sep.
> * **Open question:** how far back must the Lichess cursor reach (longest correspondence time control, or a separate query for games ongoing at the last sync), and should the unlinked path dedup by provider game id (Site/Link) instead of filtering by start time?

## Threat model and non-goals

Inputs: provider HTTP responses (Lichess export stream, Lichess ongoing-games stream, Chess.com
archives), the user's existing account database or linked collection, and the persisted
linked-collection registry. The adversary is an ordinary malformed or surprising provider
response (missing header, unparseable timestamp, truncated stream) and an existing install whose
cursor was written by the old code. No hostile provider is assumed. Clock skew on the user's
machine is real and must not move a cursor.

Non-goals: which games are imported (rated, standard perf types) does not change; Chess.com
variant handling (f-20261101-07 and siblings) is not touched; the co-located findings
f-20261101-07 and f-20261101-10 are not part of this plan.

## Approach

### O1 — Lichess coverage holds from a consistent second stream

Answers the open question with "a separate query for games ongoing at the last sync" (MANDATE),
widened so it also covers a game that finished but is not yet in the export's search index.
A fixed correspondence lookback is rejected: a Lichess correspondence game has no maximum
duration, so no window is complete.

After the export request completes, `download_lichess_games_runtime` makes one authenticated
**coverage request** for the same account and the same `since`:
`/api/games/user/<player>?since=<since>&ongoing=true&moves=false&tags=false&clocks=false&evals=false&opening=false`
with `Accept: application/x-ndjson` and no `perfType`/`rated`, so lila serves it from Mongo
(`exportByUser` Mongo branch, `Query.createdBetween`, no `Query.finished` filter): every game
created after `since`, ongoing or finished. The request goes through `state.http_transport` like
the export, so tests observe it. Each line carries `id`, `rated`, `perf`, `status` and
`createdAt` (lila `GameApiV2.toJson`, probed 2026-11-03); those five are required. Order matters: the
coverage request runs after the export, so a game created during or after the export appears here.

A line is **eligible** when it is a game the export is meant to return: `rated` and `perf` in the
perf set `lichess_games_url` sends (one shared constant, rule 11), and `status` not `aborted` or
`noStart`. Every eligible line becomes a **coverage hold** `(id, createdAt, ongoing)`, where
`ongoing` means `status` is `created` or `started`. No time window decides whether a finished
game is covered: `lastMoveAt` is `g.movedAt`, which lila leaves unchanged when a game ends on
time or by resignation, so it says nothing about when the game finished or entered the search
index. Whether a finished hold is covered is decided only by its presence in the downloaded file
(O2). Holds are bounded by a named maximum count; exceeding it fails the download.

Failure semantics: a failed or rejected coverage request, an unparseable NDJSON line, a line
missing one of the fields above, or more holds than the bound fails the download with the same typed error mapping the export uses (no bearer token or
raw body in the error). A download never proceeds without its holds. The request runs only in the
Lichess runtime path, so the account workflow and the plain `download_lichess_games` command both
get it.

`RuntimeDownload` (`src-tauri/src/infra/operations.rs`) carries `coverage_holds:
Option<Vec<CoverageHold>>`: `Some` for Lichess, `None` for Chess.com (archives are keyed by end
month, MANDATE).

### O2 — One cursor rule, applied on both receipt paths

One shared function computes the next cursor from `since`, the games actually present in the
downloaded file, and the holds (rule 11: O2 and O3 call it):

* `newest = max(since, newest UTCDate/UTCTime start among games in the file)`;
* for Lichess, `floor = min(createdAt − 1 ms)` over holds that are ongoing **or** whose id is not among the file's provider game ids (`provider_game_id`); a finished hold that is in the file is covered and does not hold. A finished eligible game the export omitted therefore holds the cursor until an export contains it, however long ago its last move was;
* `cursor = min(newest, floor)` for Lichess, `newest` for Chess.com. Holds are created after `since` (the coverage request uses the same `since`), so the cursor never falls below `since`.
* A Lichess download without holds (`None`) never advances the cursor past `since`.

Linked path: `record_download` takes the holds and stores the result as the receipt's
`through_ms`. Receipt application in `batch.rs` replaces the cursor with `through_ms` instead of
taking `max(cursor, through)`. The existing contiguity guard (`receipt.since` none or `<= cursor`)
stays; a stale receipt can only lower the cursor, which only re-fetches more and is harmless
because the merge dedups by provider id. If holds must be persisted with a pending receipt, the
receipt keeps its computed `through_ms` instead of the hold list.

Legacy recovery (linked): a Lichess record whose cursor was written by the old semantics is
reported with `fetch_since_ms = None` once, so the next sync re-exports full history and the
dedup merge adds exactly the games the old cursor lost. A new persisted marker distinguishes
new-semantics cursors (`#[serde(default)]`, so old registries load); Chess.com records keep their
cursor (not affected, MANDATE). The executor checks `deny_unknown_fields` and the registry's
existing version handling and follows whichever compatibility rule that schema already uses.

### O3 — Unlinked import dedups by game identity, with a stored cursor

The account import's start-time skip (`Importer` `timestamp`) is removed. An unlinked account
import decides whether a game is already present by the same identity rule the linked merge uses
(`batch.rs`): the **provider game id** (`provider_game_id`: Lichess `Site`, Chess.com `Link`)
decides when the game has one; the **semantic fingerprint** (`semantic_fingerprint`: players,
Date, UTCTime, starting FEN, mainline moves) is used only to reconcile a stored row that has no
recorded provider id. Both are shared with the linked path, not copied (rule 11). Today
`semantic_fingerprint` refuses a game whose White, Black, Date or UTCTime is absent (linked
validation). Phase 1 therefore splits it into a shared fingerprint over the same fields that
encodes an absent field as absent, and the linked-path check that keeps refusing incomplete
games before calling it; linked behaviour and fingerprint values for complete games do not change.
The unlinked path calls the shared fingerprint directly, so a game or stored row without UTCTime
can still be reconciled.

The account database records provider ids in a new table created on first account import
(`CREATE TABLE IF NOT EXISTS`, one row per imported game: provider, provider game id, `Games.ID`),
written in the import transaction. Older builds ignore the table. For each incoming game:

* id already recorded → skip;
* id not recorded, and an unclaimed stored row without a recorded id has the same fingerprint → skip and record the id for that row (each stored row is claimed by at most one id);
* otherwise → import and record the id;
* no provider id → skip only when a stored row or an earlier game in the same file has the same fingerprint.

Two distinct provider games are never merged because of equal fingerprints, including equal moves
and absent UTCTime. If one incoming id matches several unclaimed fingerprint-equal stored rows,
one of them is claimed and the rest stay unclaimed; no game is dropped by that choice.

A game with a missing or unparseable Date/UTCTime is imported as before (the unlinked importer
already accepts it). Its identity follows the rule above. It does not contribute to the cursor. No game is dropped because of its headers.

The unlinked cursor is stored in the target database's `Info` table (row `AccountSyncCursor`,
value = cursor in milliseconds), written in the same transaction as the imported games, using
O2's shared cursor rule. "Games in the file" includes games skipped as duplicates.

The cursor is native authority: the account workflow reads it from the target database for an
unlinked target and uses it as the download's `since_ms`, instead of the renderer's value. A
database without the row (every database written by the old code, and every new one) has no
cursor, so the first sync is full history and the dedup recovers the lost games.
`get_latest_game_timestamp` and `convert_pgn`'s `timestamp` parameter lose their only callers and
are removed with the generated bindings and the renderer code that passed them (`AccountCard.tsx`,
`tauri.ts`, tests).

`adopt_account_download` keeps the holds instead of discarding them, and the account completion
snapshot retains them so a retried conversion (after a failed conversion, using the retained
publication) uses the same holds. Wherever a Lichess conversion
runs without them, O2's `None` rule applies.

## Decisions and trade-offs

Decided autonomously (full auto), to be recorded by the adopter:

* **D1 — Lichess cursor reach.** Chosen: after the export, a Mongo-served coverage stream for the same `since` yields holds for ongoing and just-finished games, and the cursor stops before the oldest hold the export did not cover (O1, O2). Rejected: a fixed lookback of the longest correspondence time control (incomplete: a correspondence game has no maximum duration); an ongoing-only query (`finished=false`, the r1 plan), which loses a game that finished seconds before the query while still missing from the export's search index; replacing the export with the Mongo stream (the PGN cannot tell rated from casual for arena games, so local filtering would change which games are imported); dropping `since` and re-exporting full history every sync (minutes per sync for large accounts); storing ongoing ids and fetching them by id next sync (`POST /api/games/export/_ids`), which needs a second download into the same staging artefact and still misses a just-finished new game. Trade-off: the coverage stream doubles the per-game transfer time of a sync (60 games/s for one's own games, without moves), and while a rated correspondence game is open every sync re-exports the games started since it began; dedup discards them. Reversal path: the ids approach plus a delay, if the cost is observed to matter.
* **D2 — Unlinked dedup key.** Chosen: the linked merge's identity rule — provider game id decides, fingerprint only reconciles stored rows without a recorded id — with ids recorded in a new account-database table (O3). Rejected: header identity without moves (r1; collapses two daily games with the same players and start second); fingerprint alone including moves (r2; still collapses distinct games with identical moves or absent UTCTime, which the linked path deliberately keeps apart); writing Chess.com's `Link` into `Site` (changes what the database shows for every Chess.com game); keeping the start-time filter with a lookback (incomplete, same reason as D1).
* **D6 — Holds for finished games.** Chosen: every eligible finished game absent from the export holds, with no time window. Rejected: a `lastMoveAt` recency window (r2), because `lastMoveAt` does not change when a game ends on time or by resignation and is measured after a possibly long export. Reversal path: if a stuck hold is observed, fetch the held finished games by id (`POST /api/games/export/_ids`) into the batch.
* **D3 — Legacy cursors.** Chosen: one full-history sync for Lichess linked records and for every unlinked account database, deduplicated. Rejected: trusting old cursors (keeps the lost games lost); a partial lookback (incomplete). Cost: one longer sync per affected account after the update.
* **D4 — Coverage-request failure.** Chosen: fail the download with the existing typed error. Rejected: proceeding without holds and freezing the cursor (silent, and every later sync would re-export the same window without telling the user why).
* **D5 — Unlinked games without a start time.** Chosen: import them and leave them out of the cursor, as the unlinked importer does today. Rejected: rejecting the whole import (the linked receipt's behaviour), which would block every later sync of that account on one malformed provider game.

## Risks / open questions

* A rated game that lila's search index never returns holds the cursor at its start indefinitely: every later sync re-exports from there. That costs transfer time, never a game. The hold bound turns a widespread index failure into a typed download error rather than unbounded growth.
* The one-time full-history sync after the update (D3) re-imports a legacy game the user deleted from an unlinked account database, because no recorded id or stored row remembers it.
* The coverage stream is one extra request per Lichess sync and counts against Lichess rate limits; its transfer time equals the export's game count at 60 games/s without moves.

any UI copy change.

# Plan: Account sync must import correspondence and daily games that finish after a newer game started

## Goal

Every rated standard-variant game an account finishes is imported by a later account sync, on the
linked path (Linux, macOS) and on the unlinked path (Windows), for Lichess and Chess.com. Games
already lost by the old cursor are recovered once.

## MANDATE

Finding f-20261101-23 (db-search, entry=build, impact data-loss), verbatim:

> * **Where:** Lichess linked path: `src-tauri/src/db/linked_collections.rs:865-877` (cursor = newest game start time), `db/linked_collections/batch.rs:521-531` (`coverage_cursor_ms`), `src/components/home/AccountCard.tsx:316-322` (`sinceMs`), `src-tauri/src/fs.rs:1398-1407` (Lichess `since=`). Unlinked path (Windows, both providers): `getLatestGameTimestamp` (`db/mod.rs:2109-2121`) and `end_headers` skipping start ≤ cursor (`db/mod.rs:571-573`).
> * **Defect:** the cursor is a game start time. Lichess `since` filters on creation time (lila master: `inCreatedAtRange`, `g.createdAt.isAfter`), and the unlinked importer drops games that started before the stored newest start. Chess.com on the linked path is not affected (archives by end month, dedup by provider id).
> * **Failure scenario:** a correspondence game starts 1 Oct, the user syncs after a 10 Oct blitz game, the correspondence game ends 20 Oct: every later sync sends `since=<10 Oct>` and the finished game is never imported. On Windows a Chess.com daily game started 5 Sep and ended 3 Oct is dropped because the newest stored game started 19 Sep.
> * **Open question:** how far back must the Lichess cursor reach (longest correspondence time control, or a separate query for games ongoing at the last sync), and should the unlinked path dedup by provider game id (Site/Link) instead of filtering by start time?

## Threat model and non-goals

Inputs: provider HTTP responses (Lichess export stream, Lichess ongoing-games stream, Chess.com
archives), the user's existing account database or linked collection, and the persisted
linked-collection registry. The adversary is an ordinary malformed or surprising provider
response (missing header, unparseable timestamp, truncated stream) and an existing install whose
cursor was written by the old code. No hostile provider is assumed. Clock skew on the user's

Non-goals: which games are imported (rated, standard perf types) does not change; Chess.com

## Approach

### O1 — Lichess coverage holds from a consistent second stream

Answers the open question with "a separate query for games ongoing at the last sync" (MANDATE),
widened so it also covers a game that finished but is not yet in the export's search index.
A fixed correspondence lookback is rejected: a Lichess correspondence game has no maximum
duration, so no window is complete.

After the export request completes, `download_lichess_games_runtime` makes one authenticated
**coverage request** for the same account and the same `since`:
`/api/games/user/<player>?since=<since>&ongoing=true&moves=false&tags=false&clocks=false&evals=false&opening=false`
with `Accept: application/x-ndjson` and no `perfType`/`rated`, so lila serves it from Mongo
(`exportByUser` Mongo branch, `Query.createdBetween`, no `Query.finished` filter): every game
created after `since`, ongoing or finished. The request goes through `state.http_transport` like
the export, so tests observe it. Each line carries `id`, `rated`, `perf`, `status` and
`createdAt` (lila `GameApiV2.toJson`, probed 2026-11-03); those five are required. Order matters: the
coverage request runs after the export, so a game created during or after the export appears here.

A line is **eligible** when it is a game the export is meant to return: `rated` and `perf` in the
perf set `lichess_games_url` sends (one shared constant, rule 11), and `status` not `aborted` or
`noStart`. Every eligible line becomes a **coverage hold** `(id, createdAt, ongoing)`, where
`ongoing` means `status` is `created` or `started`. No time window decides whether a finished
game is covered: `lastMoveAt` is `g.movedAt`, which lila leaves unchanged when a game ends on
time or by resignation, so it says nothing about when the game finished or entered the search
index. Whether a finished hold is covered is decided only by its presence in the downloaded file
(O2). Holds are bounded by a named maximum count; exceeding it fails the download.

Failure semantics: a failed or rejected coverage request, an unparseable NDJSON line, a line
missing one of the fields above, or more holds than the bound fails the download with the same typed error mapping the export uses (no bearer token or
raw body in the error). A download never proceeds without its holds. The request runs only in the
Lichess runtime path, so the account workflow and the plain `download_lichess_games` command both
get it.

`RuntimeDownload` (`src-tauri/src/infra/operations.rs`) carries `coverage_holds:
Option<Vec<CoverageHold>>`: `Some` for Lichess, `None` for Chess.com (archives are keyed by end
month, MANDATE).

### O2 — One cursor rule, applied on both receipt paths

One shared function computes the next cursor from `since`, the games actually present in the
downloaded file, and the holds (rule 11: O2 and O3 call it):

* `newest = max(since, newest UTCDate/UTCTime start among games in the file)`;
* for Lichess, `floor = min(createdAt − 1 ms)` over holds that are ongoing **or** whose id is not among the file's provider game ids (`provider_game_id`); a finished hold that is in the file is covered and does not hold. A finished eligible game the export omitted therefore holds the cursor until an export contains it, however long ago its last move was;
* `cursor = min(newest, floor)` for Lichess, `newest` for Chess.com. Holds are created after `since` (the coverage request uses the same `since`), so the cursor never falls below `since`.
* A Lichess download without holds (`None`) never advances the cursor past `since`.

Linked path: `record_download` takes the holds and stores the result as the receipt's
`through_ms`. Receipt application in `batch.rs` replaces the cursor with `through_ms` instead of
taking `max(cursor, through)`. The existing contiguity guard (`receipt.since` none or `<= cursor`)
stays; a stale receipt can only lower the cursor, which only re-fetches more and is harmless
because the merge dedups by provider id. If holds must be persisted with a pending receipt, the
receipt keeps its computed `through_ms` instead of the hold list.

Legacy recovery (linked): a Lichess record whose cursor was written by the old semantics is
reported with `fetch_since_ms = None` once, so the next sync re-exports full history and the
dedup merge adds exactly the games the old cursor lost. A new persisted marker distinguishes
new-semantics cursors (`#[serde(default)]`, so old registries load); Chess.com records keep their
cursor (not affected, MANDATE). The executor checks `deny_unknown_fields` and the registry's
existing version handling and follows whichever compatibility rule that schema already uses.

### O3 — Unlinked import dedups by game identity, with a stored cursor

The account import's start-time skip (`Importer` `timestamp`) is removed. An unlinked account
import decides whether a game is already present by the same identity rule the linked merge uses
(`batch.rs`): the **provider game id** (`provider_game_id`: Lichess `Site`, Chess.com `Link`)
decides when the game has one; the **semantic fingerprint** (`semantic_fingerprint`: players,
Date, UTCTime, starting FEN, mainline moves) is used only to reconcile a stored row that has no
recorded provider id. Both are shared with the linked path, not copied (rule 11). Today
`semantic_fingerprint` refuses a game whose White, Black, Date or UTCTime is absent (linked
validation). Phase 1 therefore splits it into a shared fingerprint over the same fields that
encodes an absent field as absent, and the linked-path check that keeps refusing incomplete
games before calling it; linked behaviour and fingerprint values for complete games do not change.
The unlinked path calls the shared fingerprint directly, so a game or stored row without UTCTime
can still be reconciled.

The account database records provider ids in a new table created on first account import
(`CREATE TABLE IF NOT EXISTS`, one row per imported game: provider, provider game id, `Games.ID`),
written in the import transaction. Older builds ignore the table. For each incoming game:

* id already recorded → skip;
* id not recorded, and an unclaimed stored row without a recorded id has the same fingerprint → skip and record the id for that row (each stored row is claimed by at most one id);
* otherwise → import and record the id;
* no provider id → skip only when a stored row or an earlier game in the same file has the same fingerprint.

Two distinct provider games are never merged because of equal fingerprints, including equal moves
and absent UTCTime. If one incoming id matches several unclaimed fingerprint-equal stored rows,
one of them is claimed and the rest stay unclaimed; no game is dropped by that choice.

A game with a missing or unparseable Date/UTCTime is imported as before (the unlinked importer
already accepts it). Its identity follows the rule above. It does not contribute to the cursor. No game is dropped because of its headers.

The unlinked cursor is stored in the target database's `Info` table (row `AccountSyncCursor`,
value = cursor in milliseconds), written in the same transaction as the imported games, using
O2's shared cursor rule. "Games in the file" includes games skipped as duplicates.

The cursor is native authority: the account workflow reads it from the target database for an
unlinked target and uses it as the download's `since_ms`, instead of the renderer's value. A
database without the row (every database written by the old code, and every new one) has no
cursor, so the first sync is full history and the dedup recovers the lost games.
`get_latest_game_timestamp` and `convert_pgn`'s `timestamp` parameter lose their only callers and
are removed with the generated bindings and the renderer code that passed them (`AccountCard.tsx`,
`tauri.ts`, tests).

`adopt_account_download` keeps the holds instead of discarding them, and the account completion
snapshot retains them so a retried conversion (after a failed conversion, using the retained
publication) uses the same holds. Wherever a Lichess conversion
runs without them, O2's `None` rule applies.

## Decisions and trade-offs

Decided autonomously (full auto), to be recorded by the adopter:

* **D1 — Lichess cursor reach.** Chosen: after the export, a Mongo-served coverage stream for the same `since` yields holds for ongoing and just-finished games, and the cursor stops before the oldest hold the export did not cover (O1, O2). Rejected: a fixed lookback of the longest correspondence time control (incomplete: a correspondence game has no maximum duration); an ongoing-only query (`finished=false`, the r1 plan), which loses a game that finished seconds before the query while still missing from the export's search index; replacing the export with the Mongo stream (the PGN cannot tell rated from casual for arena games, so local filtering would change which games are imported); dropping `since` and re-exporting full history every sync (minutes per sync for large accounts); storing ongoing ids and fetching them by id next sync (`POST /api/games/export/_ids`), which needs a second download into the same staging artefact and still misses a just-finished new game. Trade-off: the coverage stream doubles the per-game transfer time of a sync (60 games/s for one's own games, without moves), and while a rated correspondence game is open every sync re-exports the games started since it began; dedup discards them. Reversal path: the ids approach plus a delay, if the cost is observed to matter.
* **D2 — Unlinked dedup key.** Chosen: the linked merge's identity rule — provider game id decides, fingerprint only reconciles stored rows without a recorded id — with ids recorded in a new account-database table (O3). Rejected: header identity without moves (r1; collapses two daily games with the same players and start second); fingerprint alone including moves (r2; still collapses distinct games with identical moves or absent UTCTime, which the linked path deliberately keeps apart); writing Chess.com's `Link` into `Site` (changes what the database shows for every Chess.com game); keeping the start-time filter with a lookback (incomplete, same reason as D1).
* **D6 — Holds for finished games.** Chosen: every eligible finished game absent from the export holds, with no time window. Rejected: a `lastMoveAt` recency window (r2), because `lastMoveAt` does not change when a game ends on time or by resignation and is measured after a possibly long export. Reversal path: if a stuck hold is observed, fetch the held finished games by id (`POST /api/games/export/_ids`) into the batch.
* **D3 — Legacy cursors.** Chosen: one full-history sync for Lichess linked records and for every unlinked account database, deduplicated. Rejected: trusting old cursors (keeps the lost games lost); a partial lookback (incomplete). Cost: one longer sync per affected account after the update.
* **D4 — Coverage-request failure.** Chosen: fail the download with the existing typed error. Rejected: proceeding without holds and freezing the cursor (silent, and every later sync would re-export the same window without telling the user why).
* **D5 — Unlinked games without a start time.** Chosen: import them and leave them out of the cursor, as the unlinked importer does today. Rejected: rejecting the whole import (the linked receipt's behaviour), which would block every later sync of that account on one malformed provider game.

## Risks / open questions

* A rated game that lila's search index never returns holds the cursor at its start indefinitely: every later sync re-exports from there. That costs transfer time, never a game. The hold bound turns a widespread index failure into a typed download error rather than unbounded growth.
* The one-time full-history sync after the update (D3) re-imports a legacy game the user deleted from an unlinked account database, because no recorded id or stored row remembers it.
* The coverage stream is one extra request per Lichess sync and counts against Lichess rate limits; its transfer time equals the export's game count at 60 games/s without moves.
