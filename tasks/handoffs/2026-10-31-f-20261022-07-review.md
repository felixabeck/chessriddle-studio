## Approach

### O1 — One startup-reconciliation wait with the existing startup-chain bound

All four waits for "production startup removed the seeded probe from `path-authority.json`"
(first session `:3725`, and the three reopen calls through `reopenAssertionSession`) go through
one exported helper; none of them calls `waitFor` for this condition directly any more. The
first session's extra orphan-image conditions remain its own predicate; the helper owns the
deadline, polling, timing and failure evidence, not the predicate (MANDATE: "fixed startup-probe
deadline ... unreliable"). On success it resolves with the parsed registry exactly as today's
waits do, because callers read `.entries` on it (`verify-app.mjs:3737-3749`, `:4100-4104`).

The helper's production signature takes **no timeout**: it waits with `waitFor`'s existing default
(45 s, `app-driver.mjs:113`), the same bound the verifier already grants "the renderer to mount
its window controls" by omitting `timeoutMs`. No new constant is introduced. Justification is the
traced ordering, not a guess: reconciliation finishes before `root.render`, so a reconciliation
bound tighter than the mount bound measures the same chain more strictly than the existing mount
check, under load, with a constant designed for a single IPC round trip. `IPC_PROBE_TIMEOUT_MS`
stays 5 s for its single-round-trip users. Any test seam (injected waiter, clock or short
deadline) is reachable only from tests, never from the four production call sites.

A registry read or parse failure during polling is an observation, never success and never an
early abort: polling continues, and the last such error is carried into the timeout evidence
(O3). (Today a throwing probe escapes `waitFor` immediately, `app-driver.mjs:120-126`.)

The deadline is measured from `Session.open` returning. Ordering of the later renderer/practice
waits in `reopenAssertionSession` is otherwise unchanged.

### O2 — Measured startup latency on every run

On success the helper prints one `  ..` line with a fixed phrase, the label and the elapsed
milliseconds from `Session.open` to probe removal (MANDATE: "require an unmodified rerun before
treating a transient failure as established" — every future run records the actual latency, so a
slow-startup regression or the real distribution is observable without a failure).

### O3 — Failure evidence that survives profile cleanup

On timeout the helper throws one error whose message carries, each bounded:
* the label and elapsed milliseconds;
* the registry observation at the deadline: readable or the last read/parse error, and whether the
  probe id (and for the first session, the orphan image) was still present;
* application-log evidence written since this `Session.open` (bytes before the open offset never
  appear): every error- or warning-level line in that slice up to a fixed line cap, then the last
  4 KiB, so an early bootstrap rejection is not pushed out by later info lines;
* renderer state from one `session.execute` bounded by a short timeout: `document.readyState`,
  whether `window.__TAURI_INTERNALS__` exists, whether the window controls are mounted, and the
  first 500 characters of body text; `unavailable` when the renderer rejects or does not answer;
* `driverDiagnostics()` output.

Every diagnostic source (registry, log, renderer, driver) is collected independently; the failure
of any one is recorded in place of its value and never replaces or suppresses the timeout error.

A reopen whose `Session.open` itself fails reports the same evidence the first-session open
failure already prints (driver output and the application log since the open offset). Both open
paths go through one shared open routine (open plus failure evidence) rather than two copies
(rule 11); it prints one fixed `  ..` line with the label for every assertion-session open.

Together these distinguish the MANDATE's alternatives: a logged bootstrap/IPC failure
(reconciliation failed), a still-unmounted renderer with no error (startup slow), and a launch or
profile-handoff failure (open fails, or no renderer answers). (MANDATE: "preserve any next
failure's exact stage and cleanup evidence".) The profile itself is not retained.

### O4 — Verification

Verification must go red if any of O1–O3 is reverted:
* Helper unit tests in `scripts/app-driver-tests.mjs` (already inside `gates:contract:check`)
  cover: late removal resolves and emits the O2 line; the production wait uses the default
  startup bound, not a caller-supplied timeout; read/parse failures during polling neither abort
  nor succeed; the timeout error carries every O3 field including the driver output and the
  open-offset log boundary; each diagnostic source failing (log read, renderer reject/hang,
  registry unreadable) still yields the timeout error.
* The timeout-evidence tests include a log whose early error- or warning-level line is followed by
  more than 4 KiB of info lines; the error must still be present.
* The shared open routine is unit-tested with a failing open for driver output and since-open log.
* `pnpm build && pnpm verify:app` exits 0 and its output contains exactly four O2 latency lines,
  one per startup wait, and exactly four O3 open lines, one per assertion-session open (first
  session plus three reopens); the proof command counts both, so a call site that bypasses the
  helper or the open routine fails the proof.

## Decisions and trade-offs

Decided autonomously (full auto, technical):

* **Question:** Should the startup-reconciliation probe keep the 5 s IPC bound, take a new
  measured bound, or follow the existing startup-chain bound?
  **Chosen:** the existing 45 s `waitFor` default already used for the renderer-mount wait, by
  omission (no new constant), plus per-run latency output and timeout diagnostics.
  **Rejected:** (a) keep 5 s and add diagnostics only — keeps a bound designed for one IPC round
  trip on a chain that includes migration and a 12,000-position inventory, so the gate stays flaky
  by construction; (b) a product-side readiness signal for the verifier — changes the shipped
  renderer for a test; (c) a fresh bound derived from timing a handful of local runs — no
  distribution data exists today and a few samples on one machine do not justify a number better
  than the bound already granted to the same chain; (d) retaining the throwaway profile on
  failure — unbounded disk accumulation under repeated drain failures, and the log slice plus
  registry observation carry the distinguishing evidence.
  **Reason:** reconciliation completes strictly before the renderer mounts
  (`src/bootstrap.tsx`), and the verifier already allows 45 s for the mount.
  **Reversal path:** if the recorded latency lines show startup consistently far below the bound,
  give the helper a measured startup bound below the default; if a timeout with diagnostics shows a logged
  reconciliation failure, file a product finding.

deadline, polling, timing and failure evidence, not the predicate (MANDATE: "fixed startup-probe
deadline ... unreliable"). On success it resolves with the parsed registry exactly as today's
waits do, because callers read `.entries` on it (`verify-app.mjs:3737-3749`, `:4100-4104`).

The helper's production signature takes **no timeout**: it waits with `waitFor`'s existing default
(45 s, `app-driver.mjs:113`), the same bound the verifier already grants "the renderer to mount
its window controls" by omitting `timeoutMs`. No new constant is introduced. Justification is the
traced ordering, not a guess: reconciliation finishes before `root.render`, so a reconciliation
bound tighter than the mount bound measures the same chain more strictly than the existing mount
check, under load, with a constant designed for a single IPC round trip. `IPC_PROBE_TIMEOUT_MS`
stays 5 s for its single-round-trip users. Any test seam (injected waiter, clock or short
deadline) is reachable only from tests, never from the four production call sites.

A registry read or parse failure during polling is an observation, never success and never an
early abort: polling continues, and the last such error is carried into the timeout evidence
(O3). (Today a throwing probe escapes `waitFor` immediately, `app-driver.mjs:120-126`.)

The deadline is measured from `Session.open` returning. Ordering of the later renderer/practice
waits in `reopenAssertionSession` is otherwise unchanged.

### O2 — Measured startup latency on every run

On success the helper prints one `  ..` line with a fixed phrase, the label and the elapsed
milliseconds from `Session.open` to probe removal (MANDATE: "require an unmodified rerun before
treating a transient failure as established" — every future run records the actual latency, so a
slow-startup regression or the real distribution is observable without a failure).

### O3 — Failure evidence that survives profile cleanup

On timeout the helper throws one error whose message carries, each bounded:
* the label and elapsed milliseconds;
* the registry observation at the deadline: readable or the last read/parse error, and whether the
  probe id (and for the first session, the orphan image) was still present;
* application-log evidence written since this `Session.open` (bytes before the open offset never
  appear): every error- or warning-level line in that slice up to a fixed line cap, then the last
  4 KiB, so an early bootstrap rejection is not pushed out by later info lines;
* renderer state from one `session.execute` bounded by a short timeout: `document.readyState`,
  whether `window.__TAURI_INTERNALS__` exists, whether the window controls are mounted, and the
  first 500 characters of body text; `unavailable` when the renderer rejects or does not answer;
* `driverDiagnostics()` output.

Every diagnostic source (registry, log, renderer, driver) is collected independently; the failure
of any one is recorded in place of its value and never replaces or suppresses the timeout error.

A reopen whose `Session.open` itself fails reports the same evidence the first-session open
failure already prints (driver output and the application log since the open offset). Both open
paths go through one shared open routine (open plus failure evidence) rather than two copies
(rule 11); it prints one fixed `  ..` line with the label for every assertion-session open.

Together these distinguish the MANDATE's alternatives: a logged bootstrap/IPC failure
(reconciliation failed), a still-unmounted renderer with no error (startup slow), and a launch or
profile-handoff failure (open fails, or no renderer answers). (MANDATE: "preserve any next
failure's exact stage and cleanup evidence".) The profile itself is not retained.

### O4 — Verification

Verification must go red if any of O1–O3 is reverted:
* Helper unit tests in `scripts/app-driver-tests.mjs` (already inside `gates:contract:check`)
  cover: late removal resolves and emits the O2 line; the production wait uses the default
  startup bound, not a caller-supplied timeout; read/parse failures during polling neither abort
  nor succeed; the timeout error carries every O3 field including the driver output and the
  open-offset log boundary; each diagnostic source failing (log read, renderer reject/hang,
  registry unreadable) still yields the timeout error.
* The timeout-evidence tests include a log whose early error- or warning-level line is followed by
  more than 4 KiB of info lines; the error must still be present.
* The shared open routine is unit-tested with a failing open for driver output and since-open log.
* `pnpm build && pnpm verify:app` exits 0 and its output contains exactly four O2 latency lines,
  one per startup wait, and exactly four O3 open lines, one per assertion-session open (first
  session plus three reopens); the proof command counts both, so a call site that bypasses the
  helper or the open routine fails the proof.

## Decisions and trade-offs

Decided autonomously (full auto, technical):

* **Question:** Should the startup-reconciliation probe keep the 5 s IPC bound, take a new
  measured bound, or follow the existing startup-chain bound?
  **Chosen:** the existing 45 s `waitFor` default already used for the renderer-mount wait, by
  omission (no new constant), plus per-run latency output and timeout diagnostics.
  **Rejected:** (a) keep 5 s and add diagnostics only — keeps a bound designed for one IPC round
  trip on a chain that includes migration and a 12,000-position inventory, so the gate stays flaky
  by construction; (b) a product-side readiness signal for the verifier — changes the shipped
  renderer for a test; (c) a fresh bound derived from timing a handful of local runs — no
  distribution data exists today and a few samples on one machine do not justify a number better
  than the bound already granted to the same chain; (d) retaining the throwaway profile on
  failure — unbounded disk accumulation under repeated drain failures, and the log slice plus
  registry observation carry the distinguishing evidence.
  **Reason:** reconciliation completes strictly before the renderer mounts
  (`src/bootstrap.tsx`), and the verifier already allows 45 s for the mount.
  **Reversal path:** if the recorded latency lines show startup consistently far below the bound,
  give the helper a measured startup bound below the default; if a timeout with diagnostics shows a logged
  reconciliation failure, file a product finding.

## Risks / open questions

* A genuinely slow product startup (e.g. 30 s) would now pass. It is visible in the latency line;
  setting a startup budget is out of scope (Threat model).
* If the original failure was a reconciliation rejection rather than slowness, this change does
  not fix it; the next occurrence will carry the log evidence that routes it to a product finding.
