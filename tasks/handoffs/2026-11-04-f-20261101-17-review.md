## Approach

### O1 — Per-file deck map: the ordinal is resolved to a stable deck number natively

Answers the MANDATE's open question with "stable per-game identity independent of the ordinal",
held natively, rather than physically shifting decks: a shift would rewrite every leaf of every
later game (premise: identity is baked into leaf names and envelopes) and could not be one atomic
step. A deck's storage key becomes `hash_deck(file_id, deck_number)`; the existing envelope `game`
field holds that deck number.

* A per-file map leaf in the practice directory, keyed by a hash of `file_id` with its own owned
  leaf suffix, records: storage version, `file_id`, an `epoch` counter, the ordinal → deck-number
  list, the next unused deck number, and an optional pending remap (O3). Written only through the
  existing atomic `write_json` route, size-bounded and validated like the other envelopes; a
  malformed or identity-mismatched map is an inventory anomaly and refuses commands for that
  file with a typed error, never a silent identity fallback.
* **No map = identity mapping** (deck number = ordinal, epoch 0). Every existing deck stays
  reachable without migration and every file that never had a game deleted is unchanged on disk.
* An ordinal beyond the map's list has no deck yet; creating its first deck (sync of an absent
  deck) allocates the next unused deck number and appends it to the map in the same critical
  section. Deck numbers are never reused, so no new game can inherit a retired or stranded deck.
* A per-file lock (in-process mutex + advisory lock, same shape as `with_deck_lock`) serializes
  every map read-modify-write. Lock order: PGN edit lock → file map lock → deck lock, everywhere.
  Every practice command that resolves an ordinal holds the file map lock from resolution to the
  end of its deck operation, so a remap cannot interleave between them.
* Inventory (`list_practice_decks`) reports each deck under its **current ordinal** through the
  map, so `pathOwners`, anomaly/repairability matching and legacy-migration comparisons keep
  their `(file, ordinal)` semantics unchanged. A deck whose number no current ordinal maps to
  (retired, O3) is not reported as a deck of any game.

### O2 — Epoch discriminator on every deck-addressed command after load

* `load_practice_deck` returns the file map's epoch together with the deck snapshot, including
  when no deck exists yet.
* Every later command for that deck — sync, record review, reset, load reviews, acknowledge
  orphans, repair, migrate — carries the epoch the renderer loaded under. Native refuses with
  `Error::Conflict` when the file's current epoch differs, before touching any deck leaf.
* The renderer treats that refusal as "this deck identity is stale": it discards the queued or
  in-flight write's payload and rehydrates the atom from native; it never retries the same
  positions or rating against the new resolution. The rating-dropped / queued-write-not-saved
  notices that already exist report a dropped rating; no new user-facing copy.
* Generated bindings are regenerated (`pnpm bindings:generate`), never hand-edited.

### O3 — Delete remaps decks crash-consistently with the PGN mutation

Inside `delete_game_core`, under the PGN edit lock, around `commit_pgn_mutation`:

1. If neither a map nor any deck exists for the file, nothing is written (identity mapping stays
   correct for a file with no decks).
2. Otherwise, under the file map lock, persist the map (creating it from identity on first use,
   with next deck number = max(current game count, 1 + highest deck number with any leaf for this
   file)) with a pending remap `{ordinal n, base revision}` before the PGN commit.
3. Commit the PGN mutation.
4. If the replacement was installed (`Ok` or `CommittedDurabilityUncertain`): apply the remap —
   remove ordinal n from the list, bump the epoch, clear the pending record — in one map write;
   then retire the deleted game's deck by removing its leaves under its deck lock. A removal
   failure leaves an inert deck no ordinal maps to; it is logged and does not fail the delete.
   If the replacement was not installed (any error before installation): clear the pending
   record without changing list or epoch.
5. A failure to write the map after an installed replacement leaves the pending record; the
   delete reports `CommittedDurabilityUncertain` (the PGN change happened) rather than success.

**Pending recovery:** before any practice command or delete uses a map with a pending record, it
is resolved by comparing the file's current PGN revision with the recorded base revision: equal →
the delete did not land, clear it; different → apply it as in step 4. The revision is read outside
any `BLOCKING_GATEWAY` closure (no nested gateway use). Residual: an external edit of the same file
plus a crash between steps 2 and 3 resolves as "applied"; stated, not defended.

The `delete_game` command supplies the practice directory and lock context to the core; the
core's existing tests keep a way to run without practice state.

### O4 — Renderer delete barrier and cache invalidation

* For the span from just before `tauri.deleteGame` until the same-file tab update has been
  published (or refused), the file is in a "structure change" state. Practice native calls for that
  file — load, sync, record, reset, review page, acknowledge, repair, migrate — wait for it to end
  before issuing. This closes the window in which a PracticePanel mounted with a not-yet-renumbered
  ordinal would load the deck the new map assigns to that ordinal.
* When the barrier ends after a successful delete, every cached deck atom of that file is
  invalidated so its next subscriber rehydrates (new epoch, new resolution) instead of showing or
  syncing a cached snapshot of another game.
* The barrier is released on every exit path (success, refusal, error, renderer-side exception).

### O5 — The automatic sync backstop question: no confirmation prompt

The MANDATE's backstop question is answered "no" (Decided autonomously, below). O1–O4 remove
the mechanism that fed a wrong tree to `syncDeck`; the remaining large drops are real repertoire
edits, which the existing sync message already reports. Nothing in `opening.ts` `syncDeck` changes.

  games with decks and review shards, delete game 0, ordinal 0 now resolves to the former game 1's
  deck with its positions, revision, generation and review pages intact; the deleted deck's

* Renderer (Vitest): a practice call issued during an in-progress delete waits for the barrier; a

## Decisions and trade-offs

### Decided autonomously

* **Stable deck number via a native per-file map** — chosen over physically shifting later decks
  (rewrites every leaf of every later game, not atomic with the PGN replacement, cost grows with
  the number of later games and shards) and over an identity written into the PGN (a custom tag
  changes the user's file content and duplicates on copy/paste of a game; a content fingerprint
  changes on every edit). Reversal path: drop the map leaf; with no map every file falls back to
  identity mapping.
* **Backstop prompt: no.** Chosen over a confirmation when an automatic sync would drop most of a
  non-empty deck. The prompt would be a new user-visible interruption on legitimate large
  repertoire edits, and with O1–O4 the wrong-tree input it guarded against no longer reaches
  `syncDeck` from any in-app path; the external-edit case is a stated known limit. Reversal path:
  a ratio guard in `PracticePanel`'s sync effect before `setDeck`.
* **Deleted game's deck is removed**, not kept unreachable: the user deleted the game, the deck has
  no game to belong to, and keeping it would accumulate leaves and inventory entries nobody can
  open. Reversal path: skip the removal in O3 step 4; the deck stays inert.

## Approach

### O1 — Per-file deck map: the ordinal is resolved to a stable deck number natively

Answers the MANDATE's open question with "stable per-game identity independent of the ordinal",
held natively, rather than physically shifting decks: a shift would rewrite every leaf of every
later game (premise: identity is baked into leaf names and envelopes) and could not be one atomic
step. A deck's storage key becomes `hash_deck(file_id, deck_number)`; the existing envelope `game`
field holds that deck number.

* A per-file map leaf in the practice directory, keyed by a hash of `file_id` with its own owned
  leaf suffix, records: storage version, `file_id`, an `epoch` counter, a list indexed by ordinal
  whose entries are either a deck number or "no deck yet", the next unused deck number, and an
  optional pending remap (O3). Written only through the existing atomic `write_json` route,
  size-bounded and validated like the other envelopes. A malformed or identity-mismatched map is
  an inventory anomaly; practice commands for that file refuse with a typed error, never a silent
  identity fallback. Repairing a damaged map is not part of this task (see Not part of this task).
* **No map = identity mapping** (deck number = ordinal, epoch 0). Every existing deck stays
  reachable without migration.
* Resolution is per ordinal and never positional: when a map exists, an ordinal at or beyond the
  list's end, or an entry marked "no deck yet", has no deck. Creating the first deck at such an
  ordinal k (sync of an absent deck) extends the list with "no deck yet" entries up to k when
  needed, stores a freshly allocated deck number **at index k**, and writes the map in the same
  critical section as the deck creation. Deck numbers are never reused, so no game can inherit a
  retired or stranded deck, whatever order appended games are first trained in.
* A per-file lock (in-process mutex + advisory lock, same shape as `with_deck_lock`) serializes
  every map read-modify-write. Lock order everywhere: PGN edit lock → file map lock → deck lock.
  Every practice command that resolves an ordinal holds the file map lock from epoch check and
  resolution to the end of its deck operation, so a remap cannot interleave between them.
* Inventory (`list_practice_decks`) reports each deck under its **current ordinal** through the
  map, so `pathOwners`, anomaly/repairability matching keep their `(file, ordinal)` semantics. A
  deck whose number no current ordinal maps to (retired or stranded) is not reported as a deck of
  any game.

### O2 — Epoch discriminator, bound to the payload it authorizes

* A file's epoch changes on every in-app delete of a game of that file, whether or not any deck or
  map existed before (O3 step 1).
* The renderer obtains the epoch independently of deck validity: `load_practice_deck` returns it
  with the snapshot (also when no deck exists), and a Specta-registered read of the file's current
  epoch for an ordinal succeeds even when that deck is damaged, so repair, orphan acknowledgement
  and legacy migration have an epoch without a successful load.
* Every deck-addressed command — sync, record review, reset, load reviews, acknowledge orphans,
  repair, migrate — carries an expected epoch. Native refuses with `Error::Conflict` when the
  file's current epoch differs, before touching any deck leaf, under the map lock (O1).
* **The epoch travels with the payload.** A sync or rating payload is bound to the epoch under
  which its identity (the tab's ordinal) was last valid — the epoch of the hydration that the
  controller's committed deck came from, or of the "no deck" load for an empty deck. No renderer
  path substitutes an epoch obtained by a later load (including `persistSync`'s
  reload-before-first-write and the rating-conflict reload) for a payload computed earlier; if
  such a reload observes a different epoch, the payload is dropped.
* On an epoch conflict the renderer discards the payload and rehydrates the atom; it never retries
  the same positions or rating against the new resolution. The existing rating-dropped /
  queued-write-not-saved notices report a dropped rating; no new user-facing copy.
* **Legacy migration** imports a browser-era deck only into a file whose epoch is 0 (no in-app
  delete since the legacy era, so the legacy key's ordinal is still the deck's identity). For a
  file whose epoch is non-zero, native refuses the import; the renderer treats that outcome as
  superseded: the legacy value is neither imported nor removed, and it is not reported as a
  migration failure that blocks practice or saved-data clearing.
* Generated bindings are regenerated (`pnpm bindings:generate`), never hand-edited.

### O3 — Delete remaps decks crash-consistently with the PGN mutation

The off-unix refusal in `delete_game` stays the first thing the command does, before any practice
write. Inside `delete_game_core`, under the PGN edit lock, around `commit_pgn_mutation`:

1. Resolve any existing pending remap for the file (below). Then, under the file map lock, persist
   the map — creating it from identity on first use, with next deck number = max(current game
   count, 1 + highest deck number with any leaf for this file) — with a pending remap
   `{ordinal n, base revision}`, before the PGN commit. If this write fails the delete is refused
   with nothing changed.
2. Commit the PGN mutation.
3. **Finalize only after the PGN replacement is installed and durably published** (its PGN-edit
   durability stage clean): remove ordinal n from the list (when present), bump the epoch and clear
   the pending record in one map write; then retire the deleted game's deck by removing its leaves
   under its deck lock. A removal failure leaves an inert deck no ordinal maps to; it is logged and
   does not fail the delete. Post-install uncertainty that does not concern the PGN file's own
   durability (capability rebind, cache invalidation, collection refresh) does not block
   finalization.
4. If the replacement was not installed (any error before installation): clear the pending record
   without changing the list or epoch. If it was installed but its PGN durability is uncertain:
   leave the pending record for resolution; the delete reports the existing
   `CommittedDurabilityUncertain`.
5. A failure to write the map after an installed replacement leaves the pending record; the
   delete reports `CommittedDurabilityUncertain` rather than success.

**Pending resolution** runs under the file's PGN edit lock, then the map lock, so it serializes
with any in-flight delete and with every other in-app PGN mutation. It runs:

* before every in-app PGN mutation of the file (`write_game_core`, `delete_game_core`,
  `transform_file_core`), so no in-app write can change the revision while a pending record is
  unresolved; and
* before any practice command for the file uses its map.

It compares the file's current PGN revision with the base revision: equal → the delete did not
land; clear the record. Different → the replacement landed (no in-app writer can have changed the
revision first); apply step 3 only after re-establishing the PGN file's durability (parent sync of
the current file); if durability still cannot be established, the record stays and the command
fails typed. An unreadable map does not block PGN mutations (it is a practice anomaly; practice
commands for that file refuse). The revision read and durability sync run outside any
`BLOCKING_GATEWAY` closure (no nested gateway use). Residual: an external edit of the same file
while a pending record exists resolves as "applied"; stated, not defended.

The `delete_game` command supplies the practice directory to the core; the PGN core paths keep a
way to run without practice state for tests that do not concern it.

### O4 — Renderer delete barrier and cache invalidation

* For the span from just before `tauri.deleteGame` until the same-file tab update (renumbering on
  success; the conflict/unverified freshness marking on every committed-error branch, including
  `applied-despite-error`) has been published or refused, the file is in a "structure change"
  state. Practice native calls for that file wait for it to end before issuing. This closes the
  window in which a PracticePanel mounted with a not-yet-renumbered ordinal would load the deck the
  new map assigns to that ordinal.
* On every outcome where the replacement may have been installed (success, committed-but-uncertain,
  `applied-despite-error`), every cached deck atom of that file is invalidated before the barrier
  ends, so its next subscriber rehydrates (new epoch, new resolution).
* The barrier is released on every exit path (success, refusal, error, renderer-side exception).

## Decisions and trade-offs

### Decided autonomously

* **Stable deck number via a native per-file map** — chosen over physically shifting later decks
  (rewrites every leaf of every later game, not atomic with the PGN replacement, cost grows with
  the number of later games and shards) and over an identity written into the PGN (a custom tag
  changes the user's file content and duplicates on copy/paste of a game; a content fingerprint
  changes on every edit). Reversal path: drop the map leaf; with no map every file falls back to
  identity mapping.
* **Backstop prompt: no.** Chosen over a confirmation when an automatic sync would drop most of a
  non-empty deck. The prompt would be a new user-visible interruption on legitimate large
  repertoire edits, and with O1–O4 the wrong-tree input it guarded against no longer reaches
  `syncDeck` from any in-app path; the external-edit case is a stated known limit. Reversal path:
  a ratio guard in `PracticePanel`'s sync effect before `setDeck`.
* **Deleted game's deck is removed**, not kept unreachable: the user deleted the game, the deck has
  no game to belong to, and keeping it would accumulate leaves and inventory entries nobody can
  open. Reversal path: skip the removal in O3 step 4; the deck stays inert.

  which its identity (the tab's ordinal) was last valid — the epoch of the hydration that the
  controller's committed deck came from, or of the "no deck" load for an empty deck. No renderer
  path substitutes an epoch obtained by a later load (including `persistSync`'s
  reload-before-first-write and the rating-conflict reload) for a payload computed earlier; if
  such a reload observes a different epoch, the payload is dropped.
* On an epoch conflict the renderer discards the payload and rehydrates the atom; it never retries
  the same positions or rating against the new resolution. The existing rating-dropped /
  queued-write-not-saved notices report a dropped rating; no new user-facing copy.
* **Legacy migration** imports a browser-era deck only into a file whose epoch is 0 (no in-app
  delete since the legacy era, so the legacy key's ordinal is still the deck's identity). For a
  file whose epoch is non-zero, native refuses the import; the renderer treats that outcome as
  superseded: the legacy value is neither imported nor removed, and it is not reported as a
  migration failure that blocks practice or saved-data clearing.
* Generated bindings are regenerated (`pnpm bindings:generate`), never hand-edited.

### O3 — Delete remaps decks crash-consistently with the PGN mutation

The off-unix refusal in `delete_game` stays the first thing the command does, before any practice
write. Inside `delete_game_core`, under the PGN edit lock, around `commit_pgn_mutation`:

1. Resolve any existing pending remap for the file (below). Then, under the file map lock, persist
   the map — creating it from identity on first use, with next deck number = max(current game
   count, 1 + highest deck number with any leaf for this file) — with a pending remap
   `{ordinal n, game count N before the delete}`, before the PGN commit. If this write fails the
   delete is refused with nothing changed.
2. Commit the PGN mutation.
3. **Finalize only after the PGN replacement is installed and durably published** (its PGN-edit
   durability stage clean): remove ordinal n from the list (when present), bump the epoch and clear
   the pending record in one map write; then retire the deleted game's deck by removing its leaves
   under its deck lock. A removal failure leaves an inert deck no ordinal maps to; it is logged and
   does not fail the delete. Post-install uncertainty that does not concern the PGN file's own
   durability (capability rebind, cache invalidation, collection refresh) does not block
   finalization.
4. If the replacement was not installed (any error before installation): clear the pending record
   without changing the list or epoch. If it was installed but its PGN durability is uncertain:
   leave the pending record for resolution; the delete reports the existing
   `CommittedDurabilityUncertain`.
5. A failure to write the map after an installed replacement leaves the pending record; the
   delete reports `CommittedDurabilityUncertain` rather than success.

**Pending resolution** runs under the file's PGN edit lock, then the map lock, so it serializes
with any in-flight delete and with every other in-app PGN mutation. Its evidence is the file's
**game count**, not its revision (a revision also changes on a save in place or a rename, which
delete nothing):

* It runs before every in-app PGN mutation that can change the game count — delete, append
  (`write_game` with the append expectation) and `transform_file_core` — and before any practice
  command for the file uses its map. Such a mutation is refused, typed, while the file's map
  exists but cannot be read, because the pending status cannot be established. A save that
  replaces one game in place neither changes the count nor consults the map, so saving is never
  blocked by practice storage.
* Under that rule no in-app writer can change the count while a record is pending, so: current
  count = N − 1 → the delete landed; apply step 3, after re-establishing the PGN file's durability
  (parent sync of the current file); if durability still cannot be established, the record stays
  and the command fails typed. Any other count → the delete did not land; clear the record without
  changing list or epoch.
* The count is read from the scan cache / a scan outside any `BLOCKING_GATEWAY` closure (no nested
  gateway use). Residual: an external program changing the game count while a record is pending
  can be misread; stated, not defended.

The `delete_game` command supplies the practice directory to the core; the PGN core paths keep a
way to run without practice state for tests that do not concern it.

### O4 — Renderer delete barrier and cache invalidation

* For the span from just before `tauri.deleteGame` until the same-file tab update (renumbering on
  success; the conflict/unverified freshness marking on every committed-error branch, including
  `applied-despite-error`) has been published or refused, the file is in a "structure change"
  state. Practice native calls for that file wait for it to end before issuing. This closes the
  window in which a PracticePanel mounted with a not-yet-renumbered ordinal would load the deck the
  new map assigns to that ordinal.
* On every outcome where the replacement may have been installed (success, committed-but-uncertain,
  `applied-despite-error`), every cached deck atom of that file is invalidated before the barrier
  ends, so its next subscriber rehydrates (new epoch, new resolution).
* The barrier is released on every exit path (success, refusal, error, renderer-side exception).

## Decisions and trade-offs

### Decided autonomously

* **Stable deck number via a native per-file map** — chosen over physically shifting later decks
  (rewrites every leaf of every later game, not atomic with the PGN replacement, cost grows with
  the number of later games and shards) and over an identity written into the PGN (a custom tag
  changes the user's file content and duplicates on copy/paste of a game; a content fingerprint
  changes on every edit). Reversal path: drop the map leaf; with no map every file falls back to
  identity mapping.
* **Backstop prompt: no.** Chosen over a confirmation when an automatic sync would drop most of a
  non-empty deck. The prompt would be a new user-visible interruption on legitimate large
  repertoire edits, and with O1–O4 the wrong-tree input it guarded against no longer reaches
  `syncDeck` from any in-app path; the external-edit case is a stated known limit. Reversal path:
  a ratio guard in `PracticePanel`'s sync effect before `setDeck`.
* **Deleted game's deck is removed**, not kept unreachable: the user deleted the game, the deck has
  no game to belong to, and keeping it would accumulate leaves and inventory entries nobody can
  open. Reversal path: skip the removal in O3 step 4; the deck stays inert.

## Approach

### O1 — Per-file deck map: the ordinal is resolved to a stable deck number natively

Answers the MANDATE's open question with "stable per-game identity independent of the ordinal",
held natively, rather than physically shifting decks: a shift would rewrite every leaf of every
later game (premise: identity is baked into leaf names and envelopes) and could not be one atomic
step. A deck's storage key becomes `hash_deck(file_id, deck_number)`; the existing envelope `game`
field holds that deck number.

* A per-file map leaf in the practice directory, keyed by a hash of `file_id` with its own owned
  leaf suffix, records: storage version, `file_id`, an `epoch` token, a list indexed by ordinal
  whose entries are either a deck number or "no deck yet", the next unused deck number, and an
  optional pending remap (O3). Written only through the existing atomic `write_json` route,
  size-bounded and validated like the other envelopes. A malformed or identity-mismatched map is
  an inventory anomaly and is never replaced by a silent identity fallback: deck loads for every
  ordinal of that file fail with the existing damaged-deck category, so the panel offers its
  existing Repair action. **Repair with a damaged map** is admitted without an epoch (there is no
  trustworthy one, and nothing it protects survives the repair): under the map lock it removes
  every deck leaf of that file (deck numbers found by the envelopes' `file_id`), because no deck
  can be attributed to a game any more, and **replaces** the damaged map with a fresh valid map —
  every ordinal "no deck yet", next deck number above every deck number that had a leaf, a fresh
  epoch, no pending record. The map is never simply removed, because "no map" would re-admit
  browser-era legacy imports (O2). This follows d-20260923-02 (repair removes untrusted native data
  rather than guessing) and matches the existing confirmation copy, which already says Repair
  "deletes native practice history for {{name}}" with the file's name. Repair with a readable map
  keeps today's single-deck behaviour under the normal epoch check.
* **No map = identity mapping** (deck number = ordinal, a fixed "no map" epoch). Every existing
  deck stays reachable without migration.
* Resolution is per ordinal and never positional: when a map exists, an ordinal at or beyond the
  list's end, or an entry marked "no deck yet", has no deck. Creating the first deck at such an
  ordinal k (sync of an absent deck) extends the list with "no deck yet" entries up to k when
  needed, stores a freshly allocated deck number **at index k**, and writes the map in the same
  critical section as the deck creation. Deck numbers are never reused, so no game can inherit a
  retired or stranded deck, whatever order appended games are first trained in.
* A per-file lock (in-process mutex + advisory lock, same shape as `with_deck_lock`) serializes
  every map read-modify-write. Lock order everywhere: PGN edit lock → file map lock → deck lock.
  Every practice command that resolves an ordinal holds the file map lock from epoch check and
  resolution to the end of its deck operation, so a remap cannot interleave between them.
* Inventory (`list_practice_decks`) reports each deck under its **current ordinal** through the
  map, so `pathOwners`, anomaly/repairability matching keep their `(file, ordinal)` semantics. A
  deck whose number no current ordinal maps to (retired or stranded) is not reported as a deck of
  any game.

### O2 — Epoch discriminator, bound to the payload it authorizes

* The epoch is an opaque token. A file's epoch changes on every in-app delete of a game of that
  file, whether or not any deck or map existed before (O3 step 1), and on damaged-map Repair. A new
  epoch never equals an epoch the file had before, including one lost with a damaged map (for
  example a fresh random token rather than a counter); the executor chooses the representation,
  carried over IPC without precision loss.
* The renderer obtains the epoch independently of deck validity: `load_practice_deck` returns it
  with the snapshot (also when no deck exists), and a Specta-registered read of the file's current
  epoch for an ordinal succeeds even when that deck is damaged, so repair, orphan acknowledgement
  and legacy migration have an epoch without a successful load.
* Every deck-addressed command — sync, record review, reset, load reviews, acknowledge orphans,
  repair, migrate — carries an expected epoch; the only exception is Repair while the file's map
  is damaged (O1). Native refuses with `Error::Conflict` when the
  file's current epoch differs, before touching any deck leaf, under the map lock (O1).
* **The epoch travels with the payload.** A sync or rating payload is bound to the epoch under
  which its identity (the tab's ordinal) was last valid — the epoch of the hydration that the
  controller's committed deck came from, or of the "no deck" load for an empty deck. No renderer
  path substitutes an epoch obtained by a later load (including `persistSync`'s
  reload-before-first-write and the rating-conflict reload) for a payload computed earlier; if
  such a reload observes a different epoch, the payload is dropped.
* On an epoch conflict the renderer discards the payload and rehydrates the atom; it never retries
  the same positions or rating against the new resolution. The existing rating-dropped /
  queued-write-not-saved notices report a dropped rating; no new user-facing copy.
* **Legacy migration** imports a browser-era deck only into a file that has no map (no in-app
  delete since the legacy era, so the legacy key's ordinal is still the deck's identity). For a
  file that has a map — including one written by damaged-map Repair — native refuses the import; the renderer treats that outcome as
  superseded: the legacy value is neither imported nor removed, and it is not reported as a
  migration failure that blocks practice or saved-data clearing.
* Generated bindings are regenerated (`pnpm bindings:generate`), never hand-edited.

### O3 — Delete remaps decks crash-consistently with the PGN mutation

The off-unix refusal in `delete_game` stays the first thing the command does, before any practice
write. Inside `delete_game_core`, under the PGN edit lock, around `commit_pgn_mutation`:

1. Resolve any existing pending remap for the file (below). Then, under the file map lock, persist
   the map — creating it from identity on first use, with next deck number = max(current game
   count, 1 + highest deck number with any leaf for this file) — with a pending remap
   `{ordinal n, game count N before the delete}`, before the PGN commit. If this write fails the
   delete is refused with nothing changed.
2. Commit the PGN mutation.
3. **Finalize only after the PGN replacement is installed and durably published** (its PGN-edit
   durability stage clean): remove ordinal n from the list (when present), set a new epoch and clear
   the pending record in one map write; then retire the deleted game's deck by removing its leaves
   under its deck lock. A removal failure leaves an inert deck no ordinal maps to; it is logged and
   does not fail the delete. Post-install uncertainty that does not concern the PGN file's own
   durability (capability rebind, cache invalidation, collection refresh) does not block
   finalization.
4. If the replacement was not installed (any error before installation): clear the pending record
   without changing the list or epoch. If it was installed but its PGN durability is uncertain:
   leave the pending record for resolution; the delete reports the existing
   `CommittedDurabilityUncertain`.
5. A failure to write the map after an installed replacement leaves the pending record; the
   delete reports `CommittedDurabilityUncertain` rather than success.

**Pending resolution** runs under the file's PGN edit lock, then the map lock, so it serializes
with any in-flight delete and with every other in-app PGN mutation. Its evidence is the file's
**game count**, not its revision (a revision also changes on a save in place or a rename, which
delete nothing):

* It runs before **every** in-app PGN content mutation of the file — every `commit_pgn_mutation`
  caller (save, append, delete) and `transform_file_core` — and before any practice command for the
  file uses its map. A save can itself append (`write_game_core` appends whenever the index equals
  the game count, whatever the expectation, `pgn.rs:2084-2090`), so no mutation is exempted by its
  API. Any such mutation is refused, typed, while the file's map exists but cannot be read, because
  the pending status cannot be established; the damaged-map Repair (O1) is the recovery. A file with
  no map pays one absent-leaf check.
* Under that rule no in-app writer can change the count while a record is pending, so: current
  count = N − 1 → the delete landed; apply step 3, after re-establishing the PGN file's durability
  (parent sync of the current file); if durability still cannot be established, the record stays
  and the command fails typed. Any other count → the delete did not land; clear the record without
  changing list or epoch.
* The count is read from the scan cache / a scan outside any `BLOCKING_GATEWAY` closure (no nested
  gateway use). Residual: an external program changing the game count while a record is pending
  can be misread; stated, not defended.

The `delete_game` command supplies the practice directory to the core; the PGN core paths keep a
way to run without practice state for tests that do not concern it.

### O4 — Renderer delete barrier and cache invalidation

* For the span from just before `tauri.deleteGame` until the same-file tab update (renumbering on
  success; the conflict/unverified freshness marking on every committed-error branch, including
  `applied-despite-error`) has been published or refused, the file is in a "structure change"
  state. Practice native calls for that file wait for it to end before issuing. This closes the
  window in which a PracticePanel mounted with a not-yet-renumbered ordinal would load the deck the
  new map assigns to that ordinal.
* On every outcome where the replacement may have been installed (success, committed-but-uncertain,
  `applied-despite-error`), every cached deck atom of that file is invalidated before the barrier
  ends, so its next subscriber rehydrates (new epoch, new resolution).
* The barrier is released on every exit path (success, refusal, error, renderer-side exception).

## Decisions and trade-offs

### Decided autonomously

* **Stable deck number via a native per-file map** — chosen over physically shifting later decks
  (rewrites every leaf of every later game, not atomic with the PGN replacement, cost grows with
  the number of later games and shards) and over an identity written into the PGN (a custom tag
  changes the user's file content and duplicates on copy/paste of a game; a content fingerprint
  changes on every edit). Reversal path: drop the map leaf; with no map every file falls back to
  identity mapping.
* **Backstop prompt: no.** Chosen over a confirmation when an automatic sync would drop most of a
  non-empty deck. The prompt would be a new user-visible interruption on legitimate large
  repertoire edits, and with O1–O4 the wrong-tree input it guarded against no longer reaches
  `syncDeck` from any in-app path; the external-edit case is a stated known limit. Reversal path:
  a ratio guard in `PracticePanel`'s sync effect before `setDeck`.
* **Damaged-map Repair is file-wide.** The per-file map is new machinery this plan introduces to
  satisfy the MANDATE's stable identity; its damage must not be a dead end
  (async-resource-invariants: every operation has an error path), and without a trustworthy map
  no deck of the file can be attributed to a game. Chosen: remove the file's decks and write a
  fresh map, as d-20260923-02 removes untrusted native data instead of guessing; the existing
  Repair copy already names the file. Rejected: rebuilding an identity map (re-creates the
  MANDATE's misattribution whenever a delete happened); refusing practice for the file forever
  (no recovery: Clear saved data is blocked by anomalies and clears browser storage only).
  Reversal path: the damaged-map branch of repair in `practice.rs`.
* **Deleted game's deck is removed**, not kept unreachable: the user deleted the game, the deck has
  no game to belong to, and keeping it would accumulate leaves and inventory entries nobody can
  open. Reversal path: skip the removal in O3 step 4; the deck stays inert.

# Plan: deleting a game no longer hands its practice deck to the next game (f-20261101-17)

## Goal

After a game is deleted from a repertoire file inside ChessFable, every remaining game keeps its
own practice deck and review history, the deleted game's deck is retired, and no automatic sync,
review or reset can write one game's tree or rating into another game's deck — including
operations that were in flight or queued when the delete happened, and including a crash between
the PGN replacement and the practice bookkeeping.

## MANDATE

Verbatim from `tasks/findings.md`, f-20261101-17:

* **Where:** `src-tauri/src/practice.rs:308-314` (`hash_deck(file_id, game)` keys a deck by the game's ordinal), `practice.rs` `sync_practice_positions_in` (replaces the positions document), `src-tauri/src/pgn.rs` `delete_game_core` (no practice-store change), `src/components/panels/info/InfoPanel.tsx:518-545` (after delete, open tabs are renumbered `gameNumber > index → gameNumber - 1`, no practice call), `src/components/panels/practice/PracticePanel.tsx` (`deckIdentity = { file, game: getTabGameNumber(currentTab) }`, automatic `syncDeck`), `src/components/files/opening.ts` `syncDeck` (drops cards absent from the tree).

* **Failure scenario:** a repertoire file with game 0 "White" and game 1 "Black", both trained for weeks. Delete game 0: the Black tab becomes game 0, loads White's deck, the sync drops White's cards, keeps schedules only where board states coincide and adds the rest as unseen, and persists that under (file, 0). Black's real schedule and review log stay unreachable under (file, 1) until a newly appended game inherits and prunes them.
* **Open question:** stable per-game identity independent of the ordinal (and how it survives external edits of the PGN), or a native delete that shifts later decks and retires the deleted one atomically with the PGN mutation? Plus a backstop: should an automatic sync that would drop most of a non-empty deck ask first?

## Approach

### O1 — Per-file deck map: the ordinal is resolved to a stable deck number natively

Answers the MANDATE's open question with "stable per-game identity independent of the ordinal",
held natively, rather than physically shifting decks: a shift would rewrite every leaf of every
later game (premise: identity is baked into leaf names and envelopes) and could not be one atomic
step. A deck's storage key becomes `hash_deck(file_id, deck_number)`; the existing envelope `game`
field holds that deck number.

* A per-file map leaf in the practice directory, keyed by a hash of `file_id` with its own owned
  leaf suffix, records: storage version, `file_id`, an `epoch` token, a list indexed by ordinal
  whose entries are either a deck number or "no deck yet", the next unused deck number, a
  "legacy superseded" marker (O2), and an optional pending remap (O3). Written only through the existing atomic `write_json` route,
  size-bounded and validated like the other envelopes. A malformed or identity-mismatched map is
  an inventory anomaly and is never replaced by a silent identity fallback: deck loads for every
  ordinal of that file fail with the existing damaged-deck category, so the panel offers its
  existing Repair action. **Repair with a damaged map** is admitted without an epoch (there is no
  trustworthy one, and nothing it protects survives the repair): under the map lock it removes
  every deck leaf of that file (deck numbers found by the envelopes' `file_id`), because no deck
  can be attributed to a game any more, and **replaces** the damaged map with a fresh valid map —
  every ordinal "no deck yet", next deck number above every deck number that had a leaf, a fresh
  epoch, the legacy-superseded marker set, no pending record. The map is never simply removed,
  because "no map" would re-admit browser-era legacy imports (O2). This follows d-20260923-02 (repair removes untrusted native data
  rather than guessing) and matches the existing confirmation copy, which already says Repair
  "deletes native practice history for {{name}}" with the file's name. Repair with a readable map
  keeps today's single-deck behaviour under the normal epoch check.
* **No map = identity mapping** (deck number = ordinal, a fixed "no map" epoch). Every existing
  deck stays reachable without migration.
* Resolution is per ordinal and never positional: when a map exists, an ordinal at or beyond the
  list's end, or an entry marked "no deck yet", has no deck. Creating the first deck at such an
  ordinal k (sync of an absent deck) extends the list with "no deck yet" entries up to k when
  needed, stores a freshly allocated deck number **at index k**, and writes the map in the same
  critical section as the deck creation. Deck numbers are never reused, so no game can inherit a
  retired or stranded deck, whatever order appended games are first trained in.
* A per-file lock (in-process mutex + advisory lock, same shape as `with_deck_lock`) serializes
  every map read-modify-write. Lock order everywhere: PGN edit lock → file map lock → deck lock.
  Every practice command that resolves an ordinal holds the file map lock from epoch check and
  resolution to the end of its deck operation, so a remap cannot interleave between them.
* Inventory (`list_practice_decks`) reports each deck under its **current ordinal** through the
  map, so `pathOwners`, anomaly/repairability matching keep their `(file, ordinal)` semantics. A
  deck whose number no current ordinal maps to (retired or stranded) is not reported as a deck of
  any game.

### O2 — Epoch discriminator, bound to the payload it authorizes

* The epoch is an opaque token. A file's epoch changes on every in-app delete of a game of that
  file, whether or not any deck or map existed before (O3 step 1), and on damaged-map Repair. A new
  epoch never equals an epoch the file had before, including one lost with a damaged map (for
  example a fresh random token rather than a counter); the executor chooses the representation,
  carried over IPC without precision loss.
* The renderer obtains the epoch independently of deck validity: `load_practice_deck` returns it
  with the snapshot (also when no deck exists), and a Specta-registered read of the file's current
  epoch for an ordinal succeeds even when that deck is damaged, so repair, orphan acknowledgement
  and legacy migration have an epoch without a successful load.
* Every deck-addressed command — sync, record review, reset, load reviews, acknowledge orphans,
  repair, migrate — carries an expected epoch; the only exception is Repair while the file's map
  is damaged (O1). Native refuses with `Error::Conflict` when the
  file's current epoch differs, before touching any deck leaf, under the map lock (O1).
* **The epoch travels with the payload.** A sync or rating payload is bound to the epoch under
  which its identity (the tab's ordinal) was last valid — the epoch of the hydration that the
  controller's committed deck came from, or of the "no deck" load for an empty deck. No renderer
  path substitutes an epoch obtained by a later load (including `persistSync`'s
  reload-before-first-write and the rating-conflict reload) for a payload computed earlier; if
  such a reload observes a different epoch, the payload is dropped.
* On an epoch conflict the renderer discards the payload and rehydrates the atom; it never retries
  the same positions or rating against the new resolution. The existing rating-dropped /
  queued-write-not-saved notices report a dropped rating; no new user-facing copy.
* **Legacy migration** imports a browser-era deck only into a file whose legacy ordinals are still
  identities: a file with no map, or with a map whose legacy-superseded marker is unset. The marker
  is set exactly when a remap is applied (O3 step 3, including by pending resolution) and by
  damaged-map Repair; a map created for a delete that then did not land (refused, cancelled,
  crashed before installation) leaves it unset, because no ordinal moved. For a file whose marker
  is set, native refuses the import; the renderer treats that outcome as
  superseded: the legacy value is neither imported nor removed, and it is not reported as a
  migration failure that blocks practice or saved-data clearing.
* Generated bindings are regenerated (`pnpm bindings:generate`), never hand-edited.

### O3 — Delete remaps decks crash-consistently with the PGN mutation

The off-unix refusal in `delete_game` stays the first thing the command does, before any practice
write. Inside `delete_game_core`, under the PGN edit lock, around `commit_pgn_mutation`:

1. Resolve any existing pending remap for the file (below). Then, under the file map lock, persist
   the map — creating it from identity on first use, with next deck number = max(current game
   count, 1 + highest deck number with any leaf for this file) — with a pending remap
   `{ordinal n, game count N before the delete}`, before the PGN commit. If this write fails the
   delete is refused with nothing changed.
2. Commit the PGN mutation.
3. **Finalize only after the PGN replacement is installed and durably published** (its PGN-edit
   durability stage clean): remove ordinal n from the list (when present), set a new epoch and clear
   the pending record in one map write; then retire the deleted game's deck by removing its leaves
   under its deck lock. A removal failure leaves an inert deck no ordinal maps to; it is logged and
   does not fail the delete. Post-install uncertainty that does not concern the PGN file's own
   durability (capability rebind, cache invalidation, collection refresh) does not block
   finalization.
4. If the replacement was not installed (any error before installation): clear the pending record
   without changing the list or epoch. If it was installed but its PGN durability is uncertain:
   leave the pending record for resolution; the delete reports the existing
   `CommittedDurabilityUncertain`.
5. A failure to write the map after an installed replacement leaves the pending record; the
   delete reports `CommittedDurabilityUncertain` rather than success.

**Pending resolution** runs under the file's PGN edit lock, then the map lock, so it serializes
with any in-flight delete and with every other in-app PGN mutation. Its evidence is the file's
**game count**, not its revision (a revision also changes on a save in place or a rename, which
delete nothing):

* It runs before **every** in-app PGN content mutation of the file — every `commit_pgn_mutation`
  caller (save, append, delete) and `transform_file_core` — and before any practice command for the
  file uses its map. A save can itself append (`write_game_core` appends whenever the index equals
  the game count, whatever the expectation, `pgn.rs:2084-2090`), so no mutation is exempted by its
  API. Any such mutation is refused, typed, while the file's map exists but cannot be read, because
  the pending status cannot be established; the damaged-map Repair (O1) is the recovery. A file with
  no map pays one absent-leaf check.
* Under that rule no in-app writer can change the count while a record is pending, so: current
  count = N − 1 → the delete landed; apply step 3, after re-establishing the PGN file's durability
  (parent sync of the current file); if durability still cannot be established, the record stays
  and the command fails typed. Any other count → the delete did not land; clear the record without
  changing list or epoch.
* The count is read from the scan cache / a scan outside any `BLOCKING_GATEWAY` closure (no nested
  gateway use). Residual: an external program changing the game count while a record is pending
  can be misread; stated, not defended.

The `delete_game` command supplies the practice directory to the core; the PGN core paths keep a
way to run without practice state for tests that do not concern it.

### O4 — Renderer delete barrier and cache invalidation

* For the span from just before `tauri.deleteGame` until the same-file tab update (renumbering on
  success; the conflict/unverified freshness marking on every committed-error branch, including
  `applied-despite-error`) has been published or refused, the file is in a "structure change"
  state. Practice native calls for that file wait for it to end before issuing. This closes the
  window in which a PracticePanel mounted with a not-yet-renumbered ordinal would load the deck the
  new map assigns to that ordinal.
* On every outcome where the replacement may have been installed (success, committed-but-uncertain,
  `applied-despite-error`), every cached deck atom of that file is invalidated before the barrier
  ends, so its next subscriber rehydrates (new epoch, new resolution).
* The barrier is released on every exit path (success, refusal, error, renderer-side exception).

### O5 — The automatic sync backstop question: no confirmation prompt

The MANDATE's backstop question is answered "no" (Decided autonomously, below). O1–O4 remove
the mechanism that fed a wrong tree to `syncDeck`; the remaining large drops are real repertoire
edits, which the existing sync message already reports. Nothing in `opening.ts` `syncDeck` changes.

## Decisions and trade-offs

### Decided autonomously

* **Stable deck number via a native per-file map** — chosen over physically shifting later decks
  (rewrites every leaf of every later game, not atomic with the PGN replacement, cost grows with
  the number of later games and shards) and over an identity written into the PGN (a custom tag
  changes the user's file content and duplicates on copy/paste of a game; a content fingerprint
  changes on every edit). Reversal path: drop the map leaf; with no map every file falls back to
  identity mapping.
* **Backstop prompt: no.** Chosen over a confirmation when an automatic sync would drop most of a
  non-empty deck. The prompt would be a new user-visible interruption on legitimate large
  repertoire edits, and with O1–O4 the wrong-tree input it guarded against no longer reaches
  `syncDeck` from any in-app path; the external-edit case is a stated known limit. Reversal path:
  a ratio guard in `PracticePanel`'s sync effect before `setDeck`.
* **Damaged-map Repair is file-wide.** The per-file map is new machinery this plan introduces to
  satisfy the MANDATE's stable identity; its damage must not be a dead end
  (async-resource-invariants: every operation has an error path), and without a trustworthy map
  no deck of the file can be attributed to a game. Chosen: remove the file's decks and write a
  fresh map, as d-20260923-02 removes untrusted native data instead of guessing; the existing
  Repair copy already names the file. Rejected: rebuilding an identity map (re-creates the
  MANDATE's misattribution whenever a delete happened); refusing practice for the file forever
  (no recovery: Clear saved data is blocked by anomalies and clears browser storage only).
  Reversal path: the damaged-map branch of repair in `practice.rs`.
* **Deleted game's deck is removed**, not kept unreachable: the user deleted the game, the deck has
  no game to belong to, and keeping it would accumulate leaves and inventory entries nobody can
  open. Reversal path: skip the removal in O3 step 4; the deck stays inert.

## Risks / open questions

* Per-file serialization of practice commands across games of one file; operations are short
  local file writes, so contention is not expected to be visible.
* Pending recovery needs the file's game count inside practice commands, but only while a record
  is pending; the PGN may then be unavailable (moved/deleted) — the command fails typed for that
  file, as other PGN-reading practice authorizations already do.

## Not part of this task

* External-program reorders/inserts/deletes; linked-collection delete/cleanup (no practice);
  repairing decks misattributed before this change; a deck manager UI; any change to `syncDeck`;
  any change to Clear saved data (it clears browser storage only, `__root.tsx:274`).
