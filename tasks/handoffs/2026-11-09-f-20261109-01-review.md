## Approach

### O1 — Decision: support one-sided clocks (answers the MANDATE's open question)

"Decide whether asymmetric timed/unlimited games are supported … or blocked in the form". Chosen:
support. The form already ships the choice, upstream supported it, and every native clock path
except two refusals is already per-side. Blocking would remove a shipped capability (a product
reduction), while supporting it only repairs a broken path. Recorded under Decided autonomously.

### O2 — Native validation accepts any combination of present sides

`validate_time_controls` accepts none, one or both sides with a control. Every **present** side is
checked against the existing `MAX_ENGINE_LIMIT` range (initial time and increment) and the
`MIN_INITIAL_TIME_MS` floor, with the same error strings as today. The "both players must provide
a time control" error disappears. The comment above `MIN_INITIAL_TIME_MS` stays accurate.

### O3 — Engine `go` mode is chosen from the mover's own side

The engine `go` selection becomes a pure function of the mover's colour, the player's `go`, the
current per-side times and the clock increments, so it is unit-testable without spawning an
engine:

* Mover's side has a clock with sampled remaining time above zero → `GoMode::PlayersTime`. A
  timed opponent contributes its real remaining time and increment. An unlimited opponent is
  reported with the **mover's own** remaining time and increment (a neutral mirror: no
  fabricated time advantage either way). The player's `go` is ignored, matching the renderer
  sending `go: null` for a timed side.
* **Expired mover (closes PR-1).** Mover's side has a clock and its sampled remaining time is `0`
  → no search is started and no `go` is written. The request returns `Ok(())` without a move, so
  the game loop does not treat it as an engine failure, and the clock loop's next tick
  (`settle_active_clock`, which flags whenever `elapsed >= remaining`) records the timeout with
  its normal result (opponent wins, or draw on insufficient material). This applies to every timed
  mover, one-sided or not. For two timed sides the outcome is unchanged (today the engine gets
  `go wtime 0 …` and its move is refused by the settle in `apply_move`); for a one-sided game it
  prevents the both-zero `PlayersTime` that `PlayersTime::validate` rejects and that would
  otherwise end the game as `Interrupted(EngineFailure)`.
* **Outgoing bound (closes PR-2).** Each clock and increment written into `PlayersTime` is the
  game value clamped to `MAX_ENGINE_LIMIT`. The game clock itself is never changed. A clock that
  grew past the UCI limit through increments therefore still produces a valid `go` and the game
  continues. This also repairs the same failure for two timed sides (threat model: an engine must
  never receive a value outside `MAX_ENGINE_LIMIT`). The `u32::try_from` errors become
  unreachable and are replaced by the clamp.
* Mover's side has no clock → the player's `go`, or `GoMode::Depth(20)` when absent, regardless of
  whether the opponent is timed. This is the existing no-clock behaviour applied per side.
* A state where `clock` is `None` while a time is `Some` remains `Error::Conflict` (an internal
  inconsistency, not a user configuration).

### O4 — Renderer stays aligned

`hasStartableTimeControl` already accepts an Unlimited side, and `startGame` already sends each
side independently, so no renderer logic changes. Only its doc comment is updated so it names the
per-side native rule it mirrors. A rendered `BoardGame` test proves the MANDATE scenario: with one

`Board.Opponent.TimeTooShort` text appears, clicking Start calls `startGame` with exactly one

  floor-checked when the other side is Unlimited, and that a one-sided game debits and flags only

## Approach

### O1 — Decision: support one-sided clocks (answers the MANDATE's open question)

"Decide whether asymmetric timed/unlimited games are supported … or blocked in the form". Chosen:
support. The form already ships the choice, upstream supported it, and every native clock path
except two refusals is already per-side. Blocking would remove a shipped capability (a product
reduction), while supporting it only repairs a broken path. Recorded under Decided autonomously.

### O2 — Native validation accepts any combination of present sides

`validate_time_controls` accepts none, one or both sides with a control. Every **present** side is
checked against the existing `MAX_ENGINE_LIMIT` range (initial time and increment) and the
`MIN_INITIAL_TIME_MS` floor, with the same error strings as today. The "both players must provide
a time control" error disappears. The comment above `MIN_INITIAL_TIME_MS` stays accurate.

### O3 — Engine `go` mode is chosen from the mover's own side

The engine `go` selection becomes a pure function of the mover's colour, the player's `go`, the
current per-side times and the clock increments, so it is unit-testable without spawning an
engine:

* Mover's side has a clock with sampled remaining time above zero → `GoMode::PlayersTime`. A
  timed opponent contributes its real remaining time and increment. An unlimited opponent is
  reported with the **mover's own** remaining time and increment (a neutral mirror: no
  fabricated time advantage either way). The player's `go` is ignored, matching the renderer
  sending `go: null` for a timed side.
* **Expired mover (closes PR-1).** Mover's side has a clock and its sampled remaining time is `0`
  → no search is started and no `go` is written. The request returns `Ok(())` without a move, so
  the game loop does not treat it as an engine failure, and the clock loop's next tick
  (`settle_active_clock`, which flags whenever `elapsed >= remaining`) records the timeout with
  its normal result (opponent wins, or draw on insufficient material). This applies to every timed
  mover, one-sided or not. For two timed sides the outcome is unchanged (today the engine gets
  `go wtime 0 …` and its move is refused by the settle in `apply_move`); for a one-sided game it
  prevents the both-zero `PlayersTime` that `PlayersTime::validate` rejects and that would
  otherwise end the game as `Interrupted(EngineFailure)`.
* **Outgoing bound (closes PR-2).** Each clock and increment written into `PlayersTime` is the
  game value clamped to `MAX_ENGINE_LIMIT`. The game clock itself is never changed. A clock that
  grew past the UCI limit through increments therefore still produces a valid `go` and the game
  continues. This also repairs the same failure for two timed sides (threat model: an engine must
  never receive a value outside `MAX_ENGINE_LIMIT`). The `u32::try_from` errors become
  unreachable and are replaced by the clamp.
* Mover's side has no clock → the player's `go`, or `GoMode::Depth(20)` when absent, regardless of
  whether the opponent is timed. This is the existing no-clock behaviour applied per side.
* A state where `clock` is `None` while a time is `Some` remains `Error::Conflict` (an internal
  inconsistency, not a user configuration).

### O4 — Renderer stays aligned

`hasStartableTimeControl` already accepts an Unlimited side, and `startGame` already sends each
side independently, so no renderer logic changes. Only its doc comment is updated so it names the
per-side native rule it mirrors. A rendered `BoardGame` test proves the MANDATE scenario: with one
side Unlimited and the other on a startable Time control, Start is enabled, no
`Board.Opponent.TimeTooShort` text appears, clicking Start calls `startGame` with exactly one
`null` time control, and a short timed side alongside an Unlimited side still disables Start.

### O5 — Verification

* Native: the old asymmetry-rejection test is replaced by tests proving that each one-sided
  configuration is accepted by `GameController::new`, that a present side is still range- and
  floor-checked when the other side is Unlimited, and that a one-sided game debits and flags only
  the timed side while the unlimited side's time stays `None` across a move and a takeback.
* Native `go` selection: table tests of the O3 function for every combination (both timed, white
  only, black only, neither, with and without player `go`), including the mirrored values, the
  expired-mover "no search" outcome, clamping of a clock above `MAX_ENGINE_LIMIT`, and the
  `Conflict` case.
* **Production request path (closes PR-3).** Tests drive the real `request_engine_move` with a
  registered `EngineActor::recording_test_actor` and `tauri::test::mock_app()`, following the
  harness at `game.rs:3607-3680`: (a) a one-sided game (engine side timed, human side Unlimited)
  writes `go wtime … btime … winc … binc …` with the mirrored values, applies the scripted
  `bestmove`, and the game keeps playing with the unlimited side's time still `None`; (b) a
  one-sided game where the engine side is Unlimited writes the player's configured `go` (or
  `go depth 20`); (c) an expired timed engine writes no `go`, the request returns `Ok`, the game
  is still `Playing`, and the next `settle_active_clock` yields the timeout result, not
  `Interrupted(EngineFailure)`. Each would go red if the asymmetric `Conflict` refusal or the
  both-zero mirror returned.
* Renderer: the O4 rendered test, plus the existing floor tests unchanged.

## Decisions and trade-offs

### Decided autonomously

* **Question:** Support one-sided (timed vs Unlimited) games natively, or block them in the form?
  **Chosen:** support natively. **Rejected:** block in the form with a visible reason. It removes a
  choice the form and upstream already offered, and nothing recorded asks for that removal.
  **Reason:** `ClockState`, the tick loop, the increment, takeback and the renderer are already
  per-side. Only `validate_time_controls` and the engine `go` match refuse, both introduced by the
  audit commit `97c29add` without a product decision. **Reversal path:** restore the
  both-or-neither check in `validate_time_controls`, mirror it in `hasStartableTimeControl` with a
  form error, and drop the one-sided `go` branches.
* **Question:** Which opponent clock does a timed engine see when its opponent is Unlimited?
  **Chosen:** the mover's own remaining time and increment. **Rejected:** `MAX_ENGINE_LIMIT` (tells
  the engine that the opponent has a day left, which some engines read as time pressure on
  themselves), and making `PlayersTime` fields optional (changes the shared `GoMode` binding used
  by analysis for no gain). **Reason:** neutral, and confined to `game.rs`. Like every outgoing value it is clamped to
  `MAX_ENGINE_LIMIT`.
  **Reversal path:** change the mirror branch in the O3 function.

## Risks / open questions

* Some engines weigh opponent time in time management. The mirror keeps that neutral, and the
  exact choice only affects engine strength, not correctness.
* The clock display for the unlimited side shows no time (`getClockInfo` receives `undefined`).
  That matches an all-Unlimited game today and needs no change.
