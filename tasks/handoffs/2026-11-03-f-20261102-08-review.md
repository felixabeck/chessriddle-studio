## Decided autonomously (full auto)
Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open
  (a new persisted field with set and clear points on every origin change, and tabs restored from
  older sessions would have no flag). Cost: one range read and one lex per in-place save.
  Reversal path: replace the check with a flag only together with equivalent restore-path proof.
* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing
  the reader to fail the game (the importer would start rejecting games it imports today).

# Plan: an in-place save never deletes content the game tree could not hold (f-20261102-08)

## Goal

When a file game is opened, the PGN it was parsed from may contain content the in-memory tree
cannot hold. Saving the tree back over that range must never delete that content silently. A
comment after the result is content the tree can hold, so it must be kept. Content the tree
cannot hold must block an in-place overwrite of the range it came from. The user's edits stay
available to save as a new game.

## MANDATE

Verbatim from `tasks/findings.md`, f-20261102-08 (data-loss, area frontend-state, entry build):

* **Where:** `src/utils/chess.ts` `innerParsePGN` (the `token.type === "Outcome"` branch `break`s, and the `San` branch `continue`s silently when `parseSanOrUci` or `positionFromFen` fails); the save path `src/utils/tabs.ts` → `writeFileGame` replaces the whole game range with the serialised tree.
* **Defect:** the lexer returns every token of the game, but `innerParsePGN` keeps only what precedes the first `Outcome` token and silently skips a SAN it cannot play. The tree is the only source the save serialises, so whatever it skipped is removed from the user's file on the next save, with no error or warning.
* **Failure scenario:** a file game `[Event "A"]\n\n1. e4 e5 1-0 {White won on time}`, or `1. e4 * 1. d4 *` on one line, or a game with one mistyped move such as `1. e4 e5 2. Nf9 Nc6 3. Bb5`: the board shows the game without the trailing comment, without the moves after `*`, or without the mistyped move (and the moves after it that become illegal). Any edit followed by a save writes only the tree, so the comment, the later moves or the rest of the game disappear from the file.
* **Open question:** should the tree represent this content (for example a trailing game comment after the result, which changes where it is serialised), or should opening refuse or warn before a save can drop it, and is the answer different for an unplayable move than for a trailing comment?
* **Correction (2026-11-02):** moves are dropped in two places, not one. A token that is not well-formed move notation (the `2. Nf9` example: no rank 9) never reaches `innerParsePGN`: the vendored reader calls `visitor.san` only when `SanPlus::from_ascii` succeeds (`src-tauri/vendor/pgn-reader/src/reader.rs`, the default token arm of the movetext loop) and skips the token otherwise, so `lex_pgn_cancellable` does not return it. `innerParsePGN`'s `continue` drops well-formed but illegal moves (e.g. `2. Nd5`, or `Nc6` once a skipped move shifted the side to move). A fix must cover both the reader's silent skip and `innerParsePGN`; the trailing-comment and `1. e4 * 1. d4 *` examples stand as written.

## Threat model and non-goals

Input adversary: an ordinary user's PGN file written by another tool or by hand. It may contain
typos, illegal moves, results in the middle of movetext, results inside variations, comments
after the result, and out-of-range or malformed NAGs. Nobody constructs input to evade the
guard on purpose. The environments are the desktop app's file workspace: plain file games and
linked-collection games, both saved through `writeFileGame`.

Non-goals: making the tree represent illegal moves; changing how the database importer, the
linked-collection projection or provider export treat such games (they never overwrite the
user's file range with a renderer tree); changing ImportModal or PgnInput, which parse text the
user pasted and do not overwrite a file range.

## Approach

### O1 — The reader reports every content token it discards

MANDATE: "A fix must cover both the reader's silent skip and `innerParsePGN`."

In the vendored reader, a non-digit movetext token that fails `SanPlus::from_ascii` and a `$`
NAG that fails to parse are passed to a new `Visitor` callback. The callback defaults to a
no-op, so every other visitor (importer, scanners, `SkipRemainder`) is unchanged byte for byte.
The callback receives the raw token bytes, including inside variations. When a variation is
skipped (`Skip(true)`), it is not called. `CHESSFABLE.md` records the patch.

The lexer implements the callback and emits a new `Token` variant carrying the token text
(lossy UTF-8, as for comments). The variant is registered through Specta. Bindings are
regenerated with `pnpm bindings:generate`, never hand-edited. Cancellation follows the other
callbacks: a cancelled lexer pushes nothing.

### O2 — One parse yields the tree and a loss report

MANDATE: "silently skips a SAN it cannot play", "keeps only what precedes the first `Outcome`
token".

`innerParsePGN` never discards a token without recording it. The parse returns the tree plus a
loss report: either empty, or a non-empty list of what the tree does not hold. Only the shape
"empty vs non-empty" is contractual. A loss is recorded for:

1. a `San` token that cannot be played (`positionFromFen` error, `parseSanOrUci` returns
   nothing), including in variations;
2. the new unparsed token from O1;
3. a `Nag` token that is not a valid NAG code;
4. at top level, any token after the first `Outcome` other than a `Comment` (more moves, a
   variation, a NAG, a second outcome);
5. inside a variation, an `Outcome` token. The serializer never writes one there.

The tree is built exactly as today for every case except O3: moves after a top-level outcome
are still not added to the tree. The loss report is exposed to callers through one exported
parse function. `parsePGN`'s existing signature and behaviour stay unchanged for its current
callers. There is still one implementation of the tokens-to-tree walk.

### O3 — A comment after the result is kept in the tree

MANDATE: "should the tree represent this content (for example a trailing game comment after the
result, which changes where it is serialised)".

At top level, `Comment` tokens after the `Outcome` are processed by the existing comment branch.
They attach to the cursor (the last mainline node, or the root for a game without moves), merged
as two adjacent comments are today. The saved file then writes the comment before the result.
The text is kept, only its position relative to the result changes. Not a loss.

### O4 — An in-place save refuses to overwrite a range that held content the tree does not

MANDATE: "Any edit followed by a save writes only the tree, so the comment, the later moves or
the rest of the game disappear from the file."

Before the in-place branch writes over the tab's own range (both `game` and `linkedGame`
expectations, user save and autosave), it reads the current range, as `validateSource` does:

* stamp ≠ `sourceStamp` → the existing `sourceChanged` result;
* otherwise the range text is parsed with O2's function. A non-empty loss report → no write. The
  tab moves to `conflict` with a new `FileConflictReason`, and the result is `"conflict"`;
* otherwise the write proceeds with `sourceStamp`, exactly as today. The native stamp check
  binds the checked bytes to the overwritten bytes.

The check runs at write time, against the bytes about to be replaced. No per-tree flag is
persisted. So it also covers tabs restored from session storage that were opened before this
change, and a range the app itself last wrote (lossless by construction) passes. A read or
parse failure during this check follows the existing `validateSource` and catch-path mappings.
It never writes. The Save-As destination write and the append paths are unchanged.

### O5 — The refusal tells the user why and keeps their edits

The file conflict panel shows a reason-specific sentence for the new conflict reason, in place
of `FileFreshness.Changed`. It says that the game in the file contains moves or comments
ChessFable cannot keep, so saving over it would delete them, and that the user's version can be
saved as a new game. The panel keeps its existing actions: "Reload from disk" discards the edits
and re-opens the source, and "Save my version as a new game…" appends and leaves the original
range untouched. The new key goes into every shipped catalogue in that catalogue's language
(`docs/localization.md`), through `pnpm i18n:extract`. The quit gate continues to treat the
still-dirty tab as unsaved (d-20261102-08).

## Decisions and trade-offs

Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open

* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing

# Plan: an in-place save never deletes content the game tree could not hold (f-20261102-08)

## Goal

When a file game is opened, the PGN it was parsed from may contain content the in-memory tree
cannot hold. Saving the tree back over that range must never delete that content silently. A
comment after the result is content the tree can hold, so it must be kept. Content the tree
cannot hold must block an in-place overwrite of the range it came from. The user's edits stay
available to save as a new game.

## MANDATE

Verbatim from `tasks/findings.md`, f-20261102-08 (data-loss, area frontend-state, entry build):

* **Where:** `src/utils/chess.ts` `innerParsePGN` (the `token.type === "Outcome"` branch `break`s, and the `San` branch `continue`s silently when `parseSanOrUci` or `positionFromFen` fails); the save path `src/utils/tabs.ts` → `writeFileGame` replaces the whole game range with the serialised tree.
* **Defect:** the lexer returns every token of the game, but `innerParsePGN` keeps only what precedes the first `Outcome` token and silently skips a SAN it cannot play. The tree is the only source the save serialises, so whatever it skipped is removed from the user's file on the next save, with no error or warning.
* **Failure scenario:** a file game `[Event "A"]\n\n1. e4 e5 1-0 {White won on time}`, or `1. e4 * 1. d4 *` on one line, or a game with one mistyped move such as `1. e4 e5 2. Nf9 Nc6 3. Bb5`: the board shows the game without the trailing comment, without the moves after `*`, or without the mistyped move (and the moves after it that become illegal). Any edit followed by a save writes only the tree, so the comment, the later moves or the rest of the game disappear from the file.
* **Open question:** should the tree represent this content (for example a trailing game comment after the result, which changes where it is serialised), or should opening refuse or warn before a save can drop it, and is the answer different for an unplayable move than for a trailing comment?
* **Correction (2026-11-02):** moves are dropped in two places, not one. A token that is not well-formed move notation (the `2. Nf9` example: no rank 9) never reaches `innerParsePGN`: the vendored reader calls `visitor.san` only when `SanPlus::from_ascii` succeeds (`src-tauri/vendor/pgn-reader/src/reader.rs`, the default token arm of the movetext loop) and skips the token otherwise, so `lex_pgn_cancellable` does not return it. `innerParsePGN`'s `continue` drops well-formed but illegal moves (e.g. `2. Nd5`, or `Nc6` once a skipped move shifted the side to move). A fix must cover both the reader's silent skip and `innerParsePGN`; the trailing-comment and `1. e4 * 1. d4 *` examples stand as written.

## Threat model and non-goals

Input adversary: an ordinary user's PGN file written by another tool or by hand. It may contain
typos, illegal moves, results in the middle of movetext, results inside variations, comments
after the result, and out-of-range or malformed NAGs. Nobody constructs input to evade the
guard on purpose. The environments are the desktop app's file workspace: plain file games and
linked-collection games, both saved through `writeFileGame`.

Non-goals: making the tree represent illegal moves; changing how the database importer, the
linked-collection projection or provider export treat such games (they never overwrite the
user's file range with a renderer tree); changing ImportModal or PgnInput, which parse text the
user pasted and do not overwrite a file range.

## Approach

### O1 — The reader reports every content token it discards

MANDATE: "A fix must cover both the reader's silent skip and `innerParsePGN`."

In `read_movetext`, every arm that consumes bytes without a visitor call passes them to a new
`Visitor` callback with a kind, so the caller can tell a comment from discarded content. The
callback defaults to a no-op, so every other visitor (importer, scanners, `SkipRemainder`)
keeps its current results byte for byte. Reported kinds:

* **line comment:** the text of a `;` rest-of-line comment, without the `;` and the newline;
* **discarded:** everything else consumed silently that is not layout, i.e. a non-digit token that
  fails `SanPlus::from_ascii`, a `$` NAG whose digits do not parse, a token in the default arm that
  starts at or below `'9'` (other than `-`), a digit-led token that is neither an outcome nor a
  move number (digits optionally followed by dots), and a `%` escape line inside movetext.

Layout is not reported: whitespace, `.`, the `P` pawn prefix, move numbers, and the line-boundary
newline. Zero-based castling consumes its `+`/`#` suffix, so `0-0+` reports nothing. The skip
functions (`skip_movetext`, `skip_variation`) are unchanged: nothing is reported for a game or
variation a visitor chose to skip. `CHESSFABLE.md` records the patch.

The lexer implements the callback. A line comment becomes an ordinary `Token::Comment`, so the
tree keeps its text (it is saved in `{}` form). Discarded content becomes a new `Token` variant
carrying the text (lossy UTF-8, as for comments). The variant is registered through Specta.
Bindings are regenerated with `pnpm bindings:generate`, never hand-edited. Cancellation follows
the other callbacks: a cancelled lexer pushes nothing.

### O2 — One parse yields the tree and a loss report

MANDATE: "silently skips a SAN it cannot play", "keeps only what precedes the first `Outcome`
token".

`innerParsePGN` never discards a token without recording it. The parse returns the tree plus a
loss report: either empty, or a non-empty list of what the tree does not hold. Only the shape
"empty vs non-empty" is contractual. A loss is recorded for:

1. a `San` token that cannot be played (`positionFromFen` error, `parseSanOrUci` returns
   nothing), including in variations;
2. the new unparsed token from O1;
3. a `Nag` token that is not a valid NAG code;
4. at top level, any token after the first `Outcome` other than a `Comment` (more moves, a
   variation, a NAG, a second outcome);
5. inside a variation, an `Outcome` token. The serializer never writes one there;
6. a `Comment` whose `[%clk]` or `[%eval]` would replace a value the cursor node already holds
   from an earlier comment (the earlier value would not be saved). This applies to every comment,
   including the trailing comments of O3.

The tree is built exactly as today for every case except O3: moves after a top-level outcome
are still not added to the tree. The loss report is exposed to callers through one exported
parse function. `parsePGN`'s existing signature and behaviour stay unchanged for its current
callers. There is still one implementation of the tokens-to-tree walk.

### O3 — A comment after the result is kept in the tree

MANDATE: "should the tree represent this content (for example a trailing game comment after the
result, which changes where it is serialised)".

At top level, `Comment` tokens after the `Outcome` are processed by the existing comment branch.
They attach to the cursor (the last mainline node, or the root for a game without moves), merged
as two adjacent comments are today. The saved file then writes the comment before the result.
The text is kept, only its position relative to the result changes. Not a loss, unless O2 item 6
applies.

### O4 — An in-place save refuses to overwrite a range that held content the tree does not

MANDATE: "Any edit followed by a save writes only the tree, so the comment, the later moves or
the rest of the game disappear from the file."

Before the in-place branch writes over the tab's own range (both `game` and `linkedGame`
expectations, user save and autosave), it reads the current range, as `validateSource` does:

* stamp ≠ `sourceStamp` → the existing `sourceChanged` result;
* otherwise the range text is parsed with O2's function. A non-empty loss report → no write. The
  tab moves to `conflict` with a new `FileConflictReason`, and the result is `"conflict"`;
* otherwise the write proceeds with `sourceStamp`, exactly as today. The native stamp check
  binds the checked bytes to the overwritten bytes.

The check runs at write time, against the bytes about to be replaced. No per-tree flag is
persisted. A range the app itself last wrote is lossless by construction and passes. A tree
parsed by the pre-change parser cannot be restored into this code in the shipped app, because tab
storage does not survive a quit (Traced premises), so no migration of persisted trees is needed. A read or
parse failure during this check follows the existing `validateSource` and catch-path mappings.
It never writes. The Save-As destination write and the append paths are unchanged.

### O5 — The refusal tells the user why and keeps their edits

The file conflict panel shows a reason-specific sentence for the new conflict reason, in place
of `FileFreshness.Changed`. It says that the game in the file contains moves or comments
ChessFable cannot keep, so saving over it would delete them, and that the user's version can be
saved as a new game. The panel keeps its existing actions: "Reload from disk" discards the edits
and re-opens the source, and "Save my version as a new game…" appends and leaves the original
range untouched. The new key goes into every shipped catalogue in that catalogue's language
(`docs/localization.md`), through `pnpm i18n:extract`. The quit gate continues to treat the
still-dirty tab as unsaved (d-20261102-08).

## Decisions and trade-offs

Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open
  (a new persisted field with set and clear points on every origin change, and tabs restored from
  older sessions would have no flag). Cost: one range read and one lex per in-place save.
  Reversal path: replace the check with a flag only together with equivalent restore-path proof.
* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing
  the reader to fail the game (the importer would start rejecting games it imports today).

## Risks / open questions

* The new conflict panel replaces the board until the user chooses an action. This matches the
  existing `save-refused` behaviour.
* With autosave on, the first edit of a lossy game triggers the refusal at once. That is the
  earliest moment the user is at risk, and nothing is written.
* A game whose movetext has two clocks or evaluations on one node can no longer be saved in place,
  only as a new game. That is rare in exported files, and saving in place today deletes one of
  them.

# Plan: an in-place save never deletes content the game tree could not hold (f-20261102-08)

## Goal

When a file game is opened, the PGN it was parsed from may contain content the in-memory tree
cannot hold. Saving the tree back over that range must never delete that content silently. A
comment after the result is content the tree can hold, so it must be kept. Content the tree

## Approach

### O1 — The reader reports every content token it discards

MANDATE: "A fix must cover both the reader's silent skip and `innerParsePGN`."

In `read_movetext`, every arm that consumes bytes without a visitor call passes them to a new
`Visitor` callback with a kind, so the caller can tell a comment from discarded content. The
callback defaults to a no-op, so every other visitor (importer, scanners, `SkipRemainder`)
keeps its current results byte for byte. Reported kinds:

* **line comment:** the text of a `;` rest-of-line comment, without the `;` and the newline;
* **discarded:** everything else consumed silently that is not layout, i.e. a non-digit token that
  fails `SanPlus::from_ascii`, a `$` NAG whose digits do not parse, a token in the default arm that
  starts at or below `'9'` (other than `-`), a digit-led token that is neither an outcome nor a
  move number (digits optionally followed by dots), and a `%` escape line inside movetext.

Layout is not reported: whitespace, `.`, the `P` pawn prefix, move numbers, and the line-boundary
newline. Zero-based castling consumes its `+`/`#` suffix, so `0-0+` reports nothing. The skip
functions (`skip_movetext`, `skip_variation`) are unchanged: nothing is reported for a game or
variation a visitor chose to skip. `CHESSFABLE.md` records the patch.

The lexer implements the callback. A line comment whose text contains no `}` becomes an ordinary
`Token::Comment`, so the tree keeps its text (it is saved in `{}` form). A line comment containing
`}` cannot be written back in brace form (`chess.ts:116` writes comment text unescaped, and the
reader closes a brace comment at the first `}`), so the lexer emits it as discarded content. Discarded content becomes a new `Token` variant
carrying the text (lossy UTF-8, as for comments). The variant is registered through Specta.
Bindings are regenerated with `pnpm bindings:generate`, never hand-edited. Cancellation follows
the other callbacks: a cancelled lexer pushes nothing.

### O2 — One parse yields the tree and a loss report

MANDATE: "silently skips a SAN it cannot play", "keeps only what precedes the first `Outcome`
token".

`innerParsePGN` never discards a token without recording it. The parse returns the tree plus a
loss report: either empty, or a non-empty list of what the tree does not hold. Only the shape
"empty vs non-empty" is contractual. A loss is recorded for:

1. a `San` token that cannot be played (`positionFromFen` error, `parseSanOrUci` returns
   nothing), including in variations;
2. the new unparsed token from O1;
3. a `Nag` token that is not a valid NAG code;
4. at top level, any token after the first `Outcome` other than a `Comment` (more moves, a
   variation, a NAG, a second outcome);
5. inside a variation, an `Outcome` token. The serializer never writes one there;
6. a node whose comments carry more than one well-formed `[%clk]`, or more than one well-formed
   `[%eval]`, in total, whether within one comment or across several. The tree holds one clock
   and one evaluation per node: `chess.ts:405-411` replaces the node's value, and chessops
   `parseComment` keeps only the last match within one comment. Only one value would be saved.
   This applies to every comment, including the trailing comments of O3.

The tree is built exactly as today for every case except O3: moves after a top-level outcome
are still not added to the tree. The loss report is exposed to callers through one exported
parse function. `parsePGN`'s existing signature and behaviour stay unchanged for its current
callers. There is still one implementation of the tokens-to-tree walk.

### O3 — A comment after the result is kept in the tree

MANDATE: "should the tree represent this content (for example a trailing game comment after the
result, which changes where it is serialised)".

At top level, `Comment` tokens after the `Outcome` are processed by the existing comment branch.
They attach to the cursor (the last mainline node, or the root for a game without moves), merged
as two adjacent comments are today. The saved file then writes the comment before the result.
The text is kept, only its position relative to the result changes. Not a loss, unless O2 item 6
applies.

### O4 — An in-place save refuses to overwrite a range that held content the tree does not

MANDATE: "Any edit followed by a save writes only the tree, so the comment, the later moves or
the rest of the game disappear from the file."

Before the in-place branch writes over the tab's own range (both `game` and `linkedGame`
expectations, user save and autosave), it reads the current range, as `validateSource` does:

* stamp ≠ `sourceStamp` → the existing `sourceChanged` result;
* otherwise the range text is parsed with O2's function. A non-empty loss report → no write. The
  tab moves to `conflict` with a new `FileConflictReason`, and the result is `"conflict"`;
* otherwise the write proceeds with `sourceStamp`, exactly as today. The native stamp check
  binds the checked bytes to the overwritten bytes.

The check runs at write time, against the bytes about to be replaced. No per-tree flag is
persisted. A range the app itself last wrote is lossless by construction and passes. A tree
parsed by the pre-change parser cannot be restored into this code in the shipped app, because tab
storage does not survive a quit (Traced premises), so no migration of persisted trees is needed. A read or
parse failure during this check follows the existing `validateSource` and catch-path mappings.
It never writes. The Save-As destination write and the append paths are unchanged.

### O5 — The refusal tells the user why and keeps their edits

The file conflict panel shows a reason-specific sentence for the new conflict reason, in place
of `FileFreshness.Changed`. It says that the game in the file contains moves or comments
ChessFable cannot keep, so saving over it would delete them, and that the user's version can be
saved as a new game. The panel keeps its existing actions: "Reload from disk" discards the edits
and re-opens the source, and "Save my version as a new game…" appends and leaves the original

## Decisions and trade-offs

Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open
  (a new persisted field with set and clear points on every origin change, and tabs restored from
  older sessions would have no flag). Cost: one range read and one lex per in-place save.
  Reversal path: replace the check with a flag only together with equivalent restore-path proof.
* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing
  the reader to fail the game (the importer would start rejecting games it imports today).

## Risks / open questions

* The new conflict panel replaces the board until the user chooses an action. This matches the
  existing `save-refused` behaviour.
* With autosave on, the first edit of a lossy game triggers the refusal at once. That is the
  earliest moment the user is at risk, and nothing is written.
* A game whose movetext has two clocks or evaluations on one node can no longer be saved in place,
  only as a new game. That is rare in exported files, and saving in place today deletes one of
  them.

## Not part of this task

* Co-located joiners f-20261101-07 and f-20261101-19 (planner modes do not plan joiners).
* The database importer, linked projection and provider export treatment of unparsable tokens.
* ImportModal / PgnInput silently truncating pasted text (no file range is overwritten).
* The `[Result]` tag value versus a differing movetext result.
* Malformed header lines the reader skips in `read_headers` (for example an unquoted tag value).

### plan-r4.md

# Plan: an in-place save never deletes content the game tree could not hold (f-20261102-08)

## Goal

When a file game is opened, the PGN it was parsed from may contain content the in-memory tree

## Approach

### O1 — The reader reports every content token it discards

MANDATE: "A fix must cover both the reader's silent skip and `innerParsePGN`."

In `read_movetext`, every arm that consumes bytes without a visitor call passes them to a new
`Visitor` callback with a kind, so the caller can tell a comment from discarded content. The
callback defaults to a no-op, so every other visitor (importer, scanners, `SkipRemainder`)
keeps its current results byte for byte. Reported kinds:

* **line comment:** the text of a `;` rest-of-line comment, without the `;` and the newline;
* **discarded:** everything else consumed silently that is not layout, i.e. a non-digit token that
  fails `SanPlus::from_ascii`, a `$` NAG whose digits do not parse, a token in the default arm that
  starts at or below `'9'` (other than `-`), a digit-led token that is neither an outcome nor a
  move number (digits optionally followed by dots), and a `%` escape line inside movetext.

Layout is not reported: whitespace, `.`, the `P` pawn prefix, move numbers, and the line-boundary
newline. Zero-based castling consumes its `+`/`#` suffix, so `0-0+` reports nothing. The skip
functions (`skip_movetext`, `skip_variation`) are unchanged: nothing is reported for a game or
variation a visitor chose to skip. `CHESSFABLE.md` records the patch.

The lexer implements the callback. A line comment whose text contains no `}` becomes an ordinary
`Token::Comment`, so the tree keeps its text (it is saved in `{}` form). A line comment containing
`}` cannot be written back in brace form (`chess.ts:116` writes comment text unescaped, and the
reader closes a brace comment at the first `}`), so the lexer emits it as discarded content. Discarded content becomes a new `Token` variant
carrying the text (lossy UTF-8, as for comments). The variant is registered through Specta.
Bindings are regenerated with `pnpm bindings:generate`, never hand-edited. Cancellation follows
the other callbacks: a cancelled lexer pushes nothing.

### O2 — One parse yields the tree and a loss report

MANDATE: "silently skips a SAN it cannot play", "keeps only what precedes the first `Outcome`
token".

`innerParsePGN` never discards a token without recording it. The parse returns the tree plus a
loss report: either empty, or a non-empty list of what the tree does not hold. Only the shape
"empty vs non-empty" is contractual. A loss is recorded for:

1. a `San` token that cannot be played (`positionFromFen` error, `parseSanOrUci` returns
   nothing), including in variations;
2. the new unparsed token from O1;
3. a `Nag` token that is not a valid NAG code;
4. at top level, any token after the first `Outcome` other than a `Comment` (more moves, a
   variation, a NAG, a second outcome);
5. inside a variation, an `Outcome` token. The serializer never writes one there;
6. a node whose comments, as reduced by the `Comment` branch into the node's modelled fields,
   carry more than one well-formed `[%clk]`, or more than one well-formed `[%eval]`, in total,
   whether within one comment or across several. The tree holds one clock and one evaluation per
   node: `chess.ts:405-411` replaces the node's value, and chessops `parseComment` keeps only the
   last match within one comment. Only one value would be saved. This applies to every comment
   that branch handles, including the trailing comments of O3. A variation's starting comment is
   stored verbatim in `startingComment` (`chess.ts:439-452`) and is not counted.

The tree is built exactly as today for every case except O3: moves after a top-level outcome
are still not added to the tree. The loss report is exposed to callers through one exported
parse function. `parsePGN`'s existing signature and behaviour stay unchanged for its current
callers. There is still one implementation of the tokens-to-tree walk.

### O3 — A comment after the result is kept in the tree

MANDATE: "should the tree represent this content (for example a trailing game comment after the
result, which changes where it is serialised)".

At top level, `Comment` tokens after the `Outcome` are processed by the existing comment branch.
They attach to the cursor (the last mainline node, or the root for a game without moves), merged
as two adjacent comments are today. The saved file then writes the comment before the result.
The text is kept, only its position relative to the result changes. Not a loss, unless O2 item 6
applies.

### O4 — An in-place save refuses to overwrite a range that held content the tree does not

MANDATE: "Any edit followed by a save writes only the tree, so the comment, the later moves or
the rest of the game disappear from the file."

Before the in-place branch writes over the tab's own range (both `game` and `linkedGame`
expectations, user save and autosave), it reads the current range, as `validateSource` does:

* stamp ≠ `sourceStamp` → the existing `sourceChanged` result;
* otherwise the range text is parsed with O2's function. A non-empty loss report → no write. The
  tab moves to `conflict` with a new `FileConflictReason`, and the result is `"conflict"`;
* otherwise the write proceeds with `sourceStamp`, exactly as today. The native stamp check
  binds the checked bytes to the overwritten bytes.

The check runs at write time, against the bytes about to be replaced. No per-tree flag is
persisted. A range the app itself last wrote is lossless by construction and passes. A tree
parsed by the pre-change parser cannot be restored into this code in the shipped app, because tab
storage does not survive a quit (Traced premises), so no migration of persisted trees is needed. A read or
parse failure during this check follows the existing `validateSource` and catch-path mappings.
It never writes. The Save-As destination write and the append paths are unchanged.

### O5 — The refusal tells the user why and keeps their edits

The file conflict panel shows a reason-specific sentence for the new conflict reason, in place
of `FileFreshness.Changed`. It says that the game in the file contains moves or comments
ChessFable cannot keep, so saving over it would delete them, and that the user's version can be
saved as a new game. The panel keeps its existing actions: "Reload from disk" discards the edits
and re-opens the source, and "Save my version as a new game…" appends and leaves the original
range untouched. The new key goes into every shipped catalogue in that catalogue's language
(`docs/localization.md`), through `pnpm i18n:extract`. The quit gate continues to treat the
still-dirty tab as unsaved (d-20261102-08).

## Decisions and trade-offs

Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open
  (a new persisted field with set and clear points on every origin change, and tabs restored from
  older sessions would have no flag). Cost: one range read and one lex per in-place save.
  Reversal path: replace the check with a flag only together with equivalent restore-path proof.
* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing
  the reader to fail the game (the importer would start rejecting games it imports today).

## Risks / open questions

* The new conflict panel replaces the board until the user chooses an action. This matches the
  existing `save-refused` behaviour.
* With autosave on, the first edit of a lossy game triggers the refusal at once. That is the
  earliest moment the user is at risk, and nothing is written.
* A game whose movetext has two clocks or evaluations on one node can no longer be saved in place,
  only as a new game. That is rare in exported files, and saving in place today deletes one of
  them.

## Not part of this task

* Co-located joiners f-20261101-07 and f-20261101-19 (planner modes do not plan joiners).
* The database importer, linked projection and provider export treatment of unparsable tokens.
* ImportModal / PgnInput silently truncating pasted text (no file range is overwritten).
* The `[Result]` tag value versus a differing movetext result.
* Malformed header lines the reader skips in `read_headers` (for example an unquoted tag value).
  These are headers, not the comments and moves of the MANDATE.

# Plan: an in-place save never deletes content the game tree could not hold (f-20261102-08)

## Goal

When a file game is opened, the PGN it was parsed from may contain content the in-memory tree
cannot hold. Saving the tree back over that range must never delete that content silently. A
comment after the result is content the tree can hold, so it must be kept. Content the tree
cannot hold must block an in-place overwrite of the range it came from. The user's edits stay
available to save as a new game.

## MANDATE

Verbatim from `tasks/findings.md`, f-20261102-08 (data-loss, area frontend-state, entry build):

* **Where:** `src/utils/chess.ts` `innerParsePGN` (the `token.type === "Outcome"` branch `break`s, and the `San` branch `continue`s silently when `parseSanOrUci` or `positionFromFen` fails); the save path `src/utils/tabs.ts` → `writeFileGame` replaces the whole game range with the serialised tree.
* **Defect:** the lexer returns every token of the game, but `innerParsePGN` keeps only what precedes the first `Outcome` token and silently skips a SAN it cannot play. The tree is the only source the save serialises, so whatever it skipped is removed from the user's file on the next save, with no error or warning.
* **Failure scenario:** a file game `[Event "A"]\n\n1. e4 e5 1-0 {White won on time}`, or `1. e4 * 1. d4 *` on one line, or a game with one mistyped move such as `1. e4 e5 2. Nf9 Nc6 3. Bb5`: the board shows the game without the trailing comment, without the moves after `*`, or without the mistyped move (and the moves after it that become illegal). Any edit followed by a save writes only the tree, so the comment, the later moves or the rest of the game disappear from the file.
* **Open question:** should the tree represent this content (for example a trailing game comment after the result, which changes where it is serialised), or should opening refuse or warn before a save can drop it, and is the answer different for an unplayable move than for a trailing comment?
* **Correction (2026-11-02):** moves are dropped in two places, not one. A token that is not well-formed move notation (the `2. Nf9` example: no rank 9) never reaches `innerParsePGN`: the vendored reader calls `visitor.san` only when `SanPlus::from_ascii` succeeds (`src-tauri/vendor/pgn-reader/src/reader.rs`, the default token arm of the movetext loop) and skips the token otherwise, so `lex_pgn_cancellable` does not return it. `innerParsePGN`'s `continue` drops well-formed but illegal moves (e.g. `2. Nd5`, or `Nc6` once a skipped move shifted the side to move). A fix must cover both the reader's silent skip and `innerParsePGN`; the trailing-comment and `1. e4 * 1. d4 *` examples stand as written.

## Threat model and non-goals

Input adversary: an ordinary user's PGN file written by another tool or by hand. It may contain
typos, illegal moves, results in the middle of movetext, results inside variations, comments
after the result, and out-of-range or malformed NAGs. Nobody constructs input to evade the
guard on purpose. The environments are the desktop app's file workspace: plain file games and
linked-collection games, both saved through `writeFileGame`.

Non-goals: making the tree represent illegal moves; changing how the database importer, the
linked-collection projection or provider export treat such games (they never overwrite the
user's file range with a renderer tree); changing ImportModal or PgnInput, which parse text the
user pasted and do not overwrite a file range.

## Approach

### O1 — The reader reports every content token it discards

MANDATE: "A fix must cover both the reader's silent skip and `innerParsePGN`."

In `read_movetext`, every arm that consumes bytes without a visitor call passes them to a new
`Visitor` callback with a kind, so the caller can tell a comment from discarded content. The
callback defaults to a no-op, so every other visitor (importer, scanners, `SkipRemainder`)
keeps its current results byte for byte. Reported kinds:

* **line comment:** the text of a `;` rest-of-line comment, without the `;` and the newline;
* **discarded:** everything else consumed silently that is not layout, i.e. a non-digit token that
  fails `SanPlus::from_ascii`, a `$` NAG whose digits do not parse, a token in the default arm that
  starts at or below `'9'` (other than `-`), a digit-led token that is neither an outcome nor a
  move number (digits optionally followed by dots), and a `%` escape line inside movetext.

Layout is not reported: whitespace, `.`, the `P` pawn prefix, move numbers, and the line-boundary
newline. Zero-based castling consumes its `+`/`#` suffix, so `0-0+` reports nothing. The skip
functions (`skip_movetext`, `skip_variation`) are unchanged: nothing is reported for a game or
variation a visitor chose to skip. `CHESSFABLE.md` records the patch.

The lexer implements the callback. A line comment whose text contains no `}` becomes an ordinary
`Token::Comment`, so the tree keeps its text (it is saved in `{}` form). A line comment containing
`}` cannot be written back in brace form (`chess.ts:116` writes comment text unescaped, and the
reader closes a brace comment at the first `}`), so the lexer emits it as discarded content. Discarded content becomes a new `Token` variant
carrying the text (lossy UTF-8, as for comments). The variant is registered through Specta.
Bindings are regenerated with `pnpm bindings:generate`, never hand-edited. Cancellation follows
the other callbacks: a cancelled lexer pushes nothing.

### O2 — One parse yields the tree and a loss report

MANDATE: "silently skips a SAN it cannot play", "keeps only what precedes the first `Outcome`
token".

`innerParsePGN` never discards a token without recording it. The parse returns the tree plus a
loss report: either empty, or a non-empty list of what the tree does not hold. Only the shape
"empty vs non-empty" is contractual. A loss is recorded for:

1. a `San` token that cannot be played (`positionFromFen` error, `parseSanOrUci` returns
   nothing), including in variations;
2. the new unparsed token from O1;
3. a `Nag` token that is not a valid NAG code;
4. at top level, any token after the first `Outcome` other than a `Comment` (more moves, a
   variation, a NAG, a second outcome);
5. inside a variation, an `Outcome` token. The serializer never writes one there;
6. a node whose comments, as reduced by the `Comment` branch into the node's modelled fields,
   carry more than one well-formed `[%clk]`, or more than one well-formed `[%eval]`, in total,
   whether within one comment or across several. The tree holds one clock and one evaluation per
   node: `chess.ts:405-411` replaces the node's value, and chessops `parseComment` keeps only the
   last match within one comment. Only one value would be saved. This applies to every comment
   that branch handles, including the trailing comments of O3. A variation's starting comment is
   stored verbatim in `startingComment` (`chess.ts:439-452`) and is not counted.

The tree is built exactly as today for every case except O3: moves after a top-level outcome
are still not added to the tree. The loss report is exposed to callers through one exported
parse function. `parsePGN`'s existing signature and behaviour stay unchanged for its current
callers. There is still one implementation of the tokens-to-tree walk.

### O3 — A comment after the result is kept in the tree

MANDATE: "should the tree represent this content (for example a trailing game comment after the
result, which changes where it is serialised)".

At top level, `Comment` tokens after the `Outcome` are processed by the existing comment branch.
They attach to the cursor (the last mainline node, or the root for a game without moves), merged
as two adjacent comments are today. The saved file then writes the comment before the result.
The text is kept, only its position relative to the result changes. Not a loss, unless O2 item 6
applies.

### O4 — An in-place save refuses to overwrite a range that held content the tree does not

MANDATE: "Any edit followed by a save writes only the tree, so the comment, the later moves or
the rest of the game disappear from the file."

Before the in-place branch writes over the tab's own range (both `game` and `linkedGame`
expectations, user save and autosave), it reads the current range, as `validateSource` does:

* stamp ≠ `sourceStamp` → the existing `sourceChanged` result;
* otherwise the range text is parsed with O2's function. A non-empty loss report → no write. The
  tab moves to `conflict` with a new `FileConflictReason`, and the result is `"conflict"`;
* otherwise the write proceeds with `sourceStamp`, exactly as today. The native stamp check
  binds the checked bytes to the overwritten bytes.

The check runs at write time, against the bytes about to be replaced. No per-tree flag is
persisted. A range the app itself last wrote is lossless by construction and passes. A tree
parsed by the pre-change parser cannot be restored into this code in the shipped app, because tab
storage does not survive a quit (Traced premises), so no migration of persisted trees is needed. A read or
parse failure during this check follows the existing `validateSource` and catch-path mappings.
It never writes. The Save-As destination write and the append paths are unchanged.

### O5 — The refusal tells the user why and keeps their edits

The file conflict panel shows a reason-specific sentence for the new conflict reason, in place
of `FileFreshness.Changed`. It says that the game in the file contains moves or comments
ChessFable cannot keep, so saving over it would delete them, and that the user's version can be
saved as a new game. The panel keeps its existing actions: "Reload from disk" discards the edits
and re-opens the source, and "Save my version as a new game…" appends and leaves the original
range untouched. The new key goes into every shipped catalogue in that catalogue's language
(`docs/localization.md`), through `pnpm i18n:extract`. The quit gate continues to treat the
still-dirty tab as unsaved (d-20261102-08).

## Decisions and trade-offs

Decided autonomously (full auto). The precedents are d-20261101-07 and d-20261102-04 (a range
the tree cannot represent fails closed) and `Collections.RetiredTab` / `RetiredOriginRecovery`
(refuse the in-place write and keep the edits for a new game).

* **D1 — Trailing comment represented, other content guarded.** Question: represent, refuse at
  open, or guard the save? Chosen: represent what the tree can hold (a comment after the result),
  and guard the in-place save for what it cannot (unplayable or malformed moves, moves or other
  tokens after the result, bad NAGs, results inside variations). Rejected: refusing to open
  (a game with one typo could no longer even be viewed, although viewing loses nothing);
  representing illegal moves in the tree (a node must have a legal position); a warning that
  still allows the overwrite (the overwrite is the data loss). Reversal path: delete the O4
  guard and the new conflict reason. The parse remains a strict superset.
* **D2 — Guard at write time, no persisted flag.** Chosen: re-read and re-parse the range
  immediately before the in-place overwrite. Rejected: a loss flag persisted on the tree at open
  (a new persisted field with set and clear points on every origin change, and tabs restored from
  older sessions would have no flag). Cost: one range read and one lex per in-place save.
  Reversal path: replace the check with a flag only together with equivalent restore-path proof.
* **D3 — The surface is the existing file conflict panel, with a reason-specific sentence.**
  Rejected: a toast at open (another surface, and the user is not yet at risk); a new modal. The
  panel already offers both recovery actions.
* **D4 — Reader patch via a default-no-op visitor callback.** Rejected: having the lexer
  re-tokenise movetext itself (a second movetext tokenizer, rejected by d-20261023-09); changing
  the reader to fail the game (the importer would start rejecting games it imports today).

## Risks / open questions

* The new conflict panel replaces the board until the user chooses an action. This matches the
  existing `save-refused` behaviour.
* With autosave on, the first edit of a lossy game triggers the refusal at once. That is the
  earliest moment the user is at risk, and nothing is written.
* A game whose movetext has two clocks or evaluations on one node can no longer be saved in place,
  only as a new game. That is rare in exported files, and saving in place today deletes one of
  them.
