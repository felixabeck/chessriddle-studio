# Plan: f-20261011-03 — multi-predecessor deadline witness misses its drain boundary on slow hosts

## Goal

`db::repository::retirement_tests::multiple_predecessors_share_one_absolute_acquisition_deadline`
proves that one acquisition shares a single absolute retirement deadline across several
predecessors, without the proof depending on how fast the test thread wakes up after the
acquiring thread reaches its predecessor wait.

## MANDATE

From f-20261011-03, "Reopened (2026-11-02)":

> The `multiple_predecessors_share_one_absolute_acquisition_deadline` readiness miss (`reached`,
> `SIGNAL_TIMEOUT`, repository.rs:3196) has now failed hosted CI three times (runs 40923138518,
> 41493276529, 41541998483), each on a commit with no Rust or test input, while the handled note
> above left it unexplained. Remaining work: diagnose why the readiness boundary is not reached
> within `SIGNAL_TIMEOUT` under hosted llvm-cov, then fix the test's wait design or the code under
> test.

Original finding, "Why it matters": "drains and interactive pushes stall or are tempted to rerun
until green, which hides real regressions in the same tests."

## Threat model and non-goals

No adversary. The relevant environment is a slow or oversubscribed test host: hosted GitHub
runners under `llvm-cov`, running the full ~2878-test binary with libtest parallelism. Thread
wakeups and sleeps may finish hundreds of milliseconds late. The code under test is the
production predecessor-wait path in `src-tauri/src/db/repository.rs`. Only its test witness is
in scope, unless the diagnosis finds a production defect.

## Traced premises

Frozen at BASE `7fcedd82`.

* The test (`repository.rs:4544`) builds a repository with `with_retire_wait(MULTI_PREDECESSOR_BUDGET)`
  (700 ms). It holds one connection each on `first` and `second`, forces both into retirement
  through the real LRU, and installs two hooks scoped to `next`: `predecessor_wait` sends on

## Approach

### O1 — The first predecessor's release is ordered by the acquisition, not by test-thread wakeup

The `predecessor_wait` hook runs synchronously on the acquiring thread, before any predecessor
wait. It drops `first_held` there, once, after sleeping until `started +
FIRST_PREDECESSOR_RELEASE_DELAY`. Any later invocation is a no-op. The first predecessor
therefore drains before its wait begins, whatever the scheduling latency. The test thread no
longer releases `first`. The hook still signals `waiting`, so the test keeps observing that the
acquisition actually reached its predecessor wait.

The release instant is absolute, `started + FIRST_PREDECESSOR_RELEASE_DELAY`. `started` is
captured after `configure_test_hooks` returns (after the `TEST_HOOK_SERIAL` wait) and
immediately before the acquiring thread is spawned, as today. The hook sleeps until that instant,
or not at all if the instant has passed, so an acquiring-thread delay does not add to the
release time.

### O1b — Completion is timed where it happens

The acquiring thread records `started.elapsed()` when `initialization_connection` returns, and
sends it with the outcome. The shared-deadline assertion compares that value with
`MULTI_PREDECESSOR_COMPLETION_BOUND`. Test-thread wakeup latency after the outcome, which
reproduced a false "fresh retirement budget" failure at +1500 ms in the probe, therefore no
longer enters the measurement. The receive stays bounded by `COMPLETION_BOUND`.

This preserves:

* the real LRU retirement of both predecessors, and `assert_retained` for both before the call
  (the release happens after the predecessors are collected),
* `reached(&drain_signal)`: the first predecessor's wait must return `Ok` and fire the drain hook,
* the outcome assertion `Error::Conflict` from the still-held second predecessor, received within
  `COMPLETION_BOUND`,
* the shared-deadline assertion `started.elapsed() < MULTI_PREDECESSOR_COMPLETION_BOUND`,
* `assert_retained(second)` after the outcome, the final `drop(second_held)`, and the successful
  follow-up `initialization_connection`.

Why this still discriminates: if each predecessor got a fresh budget, the second wait would end
at about 500 ms + 700 ms ≈ 1200 ms, which exceeds 1050 ms. With one shared deadline, it ends at
about `start + 700 ms`. If the acquiring thread is delayed past the deadline before the hook, the
first wait still returns `Ok` (its gate is drained, premise 4). The second wait returns `Conflict`
immediately, so the outcome holds.

### O2 — Unchanged bounds and production code

# Plan: f-20261011-03 — multi-predecessor deadline witness misses its drain boundary on slow hosts

## Goal

`db::repository::retirement_tests::multiple_predecessors_share_one_absolute_acquisition_deadline`
proves that one acquisition shares a single absolute retirement deadline across several
predecessors, without the proof depending on how fast the test thread wakes up after the
acquiring thread reaches its predecessor wait.

## MANDATE

From f-20261011-03, "Reopened (2026-11-02)":

> The `multiple_predecessors_share_one_absolute_acquisition_deadline` readiness miss (`reached`,
> `SIGNAL_TIMEOUT`, repository.rs:3196) has now failed hosted CI three times (runs 40923138518,
> 41493276529, 41541998483), each on a commit with no Rust or test input, while the handled note
> above left it unexplained. Remaining work: diagnose why the readiness boundary is not reached
> within `SIGNAL_TIMEOUT` under hosted llvm-cov, then fix the test's wait design or the code under
> test.

Original finding, "Why it matters": "drains and interactive pushes stall or are tempted to rerun
until green, which hides real regressions in the same tests."

## Threat model and non-goals

No adversary. The relevant environment is a slow or oversubscribed test host: hosted GitHub
runners under `llvm-cov`, running the full ~2878-test binary with libtest parallelism. Thread
wakeups and sleeps may finish hundreds of milliseconds late. The code under test is the
production predecessor-wait path in `src-tauri/src/db/repository.rs`. Only its test witness is
in scope, unless the diagnosis finds a production defect.

## Traced premises

Frozen at BASE `7fcedd82`.

* The test (`repository.rs:4544`) builds a repository with `with_retire_wait(MULTI_PREDECESSOR_BUDGET)`
  (700 ms). It holds one connection each on `first` and `second`, forces both into retirement
  through the real LRU, and installs two hooks scoped to `next`: `predecessor_wait` sends on
  `waiting`, and `predecessor_drained` sends on `drained`. A scoped thread then calls
  `initialization_connection(next)`. The test thread waits `reached(&waited)`, sleeps until
  `started + FIRST_PREDECESSOR_RELEASE_DELAY` (500 ms), drops `first_held`, and waits
  `reached(&drain_signal)`. It then expects `Error::Conflict` within `COMPLETION_BOUND`, and
  `started.elapsed() < MULTI_PREDECESSOR_COMPLETION_BOUND` (1050 ms).
* The acquisition deadline is computed once at the start of the call:
  `acquire_probed_until(target, Instant::now() + self.retire_wait, …)` (`repository.rs:1990`).
  That moment is after `started`, on the spawned thread.
* `predecessor_admission_inner` (`repository.rs:730`) collects the matching retirements in
  `state.retired` order, releases the state lock, and fires `PredecessorWait` once. It then waits
  on each predecessor in order against the same `deadline`. It fires `PredecessorDrained`
  (`repository.rs:798`) only after that predecessor's wait returns `Ok`. A wait that returns
  `Err` propagates out of the call, so `PredecessorDrained` never fires.
* `DrainGate::wait_drained_until` (`repository.rs:216`) checks `outstanding != 0` before it
  checks the deadline. An already-drained gate returns `Ok` even after the deadline. An undrained
  gate returns `Conflict` once `now >= deadline`.
* The hooks run outside the hooks mutex (`run_noarg_test_hook` drops the guard before calling
  the callback). `PredecessorDrained` is one-shot, and `PredecessorWait` is restored after each
  call (`repository.rs:2529-2590`).
* **Reproduced mechanism, consistent with the hosted failure.** The test thread must drop `first_held` before the shared
  deadline, `started + ≥700 ms`, but it only gets to that point after it wakes from
  `reached(&waited)` and from its sleep to 500 ms. Its margin is therefore about 200 ms of
  test-thread scheduling latency. If the release lands after the deadline, the first
  predecessor's wait returns `Conflict` and `PredecessorDrained` never fires. `reached(&drain_signal)`
  then panics after `SIGNAL_TIMEOUT` with "lifecycle boundary was not reached: Timeout".
* Hosted evidence: in run 41541998483, job 125608220179 (Linux, `cargo test` under llvm-cov,
  183 s total), the test is reported FAILED 10.9 s after the preceding test result. That matches
  one 10 s `SIGNAL_TIMEOUT` expiry. The panic is at `repository.rs:3196:14`, inside `reached`,
  at `416f4e0a`. The log does not say which `reached` call failed. Retained log:
  `/tmp/drain-plan-drain-90a2aa88-slot0/build/ci/job-125608220179.log`.
* Disposable probe (below, under "Probe evidence") distinguishes the two `reached` calls.
* There is no production defect. Both the `Conflict` outcome and the missing drain hook are the
  correct production behaviour for a predecessor that is still held at the deadline.

Two design errors were caught during probing and are not in the plan:

* Measuring elapsed time on the test thread let +1500 ms of test-thread latency fail the elapsed
  bound with a misleading "fresh budget" message. Completion is therefore timed on the
  acquiring thread.
* Capturing `started` before `configure_test_hooks` counted the `TEST_HOOK_SERIAL` lock wait
  (4.48 s inside the suite). A release delay relative to hook entry stacked an acquiring-thread
  delay onto the release (1.30 s, false fail). `started` is therefore captured after the hooks
  are installed, and the release is anchored to an absolute instant.

## Approach

### O1 — The first predecessor's release is ordered by the acquisition, not by test-thread wakeup

The `predecessor_wait` hook runs synchronously on the acquiring thread, before any predecessor
wait. It drops `first_held` there, once, after sleeping until `started +
FIRST_PREDECESSOR_RELEASE_DELAY`. Any later invocation is a no-op. The first predecessor
therefore drains before its wait begins, whatever the scheduling latency. The test thread no
longer releases `first`. The hook still signals `waiting`, so the test keeps observing that the
acquisition actually reached its predecessor wait.

The release instant is absolute, `started + FIRST_PREDECESSOR_RELEASE_DELAY`. `started` is
captured after `configure_test_hooks` returns (after the `TEST_HOOK_SERIAL` wait) and
immediately before the acquiring thread is spawned, as today. The hook sleeps until that instant,
or not at all if the instant has passed, so an acquiring-thread delay does not add to the
release time.

### O1b — Completion is timed where it happens

The acquiring thread records `started.elapsed()` when `initialization_connection` returns, and
sends it with the outcome. The shared-deadline assertion compares that value with
`MULTI_PREDECESSOR_COMPLETION_BOUND`. Test-thread wakeup latency after the outcome, which
reproduced a false "fresh retirement budget" failure at +1500 ms in the probe, therefore no
longer enters the measurement. The receive stays bounded by `COMPLETION_BOUND`.

This preserves:

* the real LRU retirement of both predecessors, and `assert_retained` for both before the call
  (the release happens after the predecessors are collected),
* `reached(&drain_signal)`: the first predecessor's wait must return `Ok` and fire the drain hook,
* the outcome assertion `Error::Conflict` from the still-held second predecessor, received within
  `COMPLETION_BOUND`,
* the shared-deadline assertion `started.elapsed() < MULTI_PREDECESSOR_COMPLETION_BOUND`,
* `assert_retained(second)` after the outcome, the final `drop(second_held)`, and the successful
  follow-up `initialization_connection`.

Why this still discriminates: if each predecessor got a fresh budget, the second wait would end
at about 500 ms + 700 ms ≈ 1200 ms, which exceeds 1050 ms. With one shared deadline, it ends at
about `start + 700 ms`. If the acquiring thread is delayed past the deadline before the hook, the
first wait still returns `Ok` (its gate is drained, premise 4). The second wait returns `Conflict`
immediately, so the outcome holds.

### O1c — Each readiness wait names its boundary

This test's two readiness waits fail with distinct diagnostics: one for the predecessor-wait
boundary and one for the first-predecessor drain boundary. The waits keep their
`SIGNAL_TIMEOUT` safety bound. The shared `reached` helper and its other callers are unchanged.
Authority: the MANDATE's "diagnose why the readiness boundary is not reached". A recurrence
after this change must identify which boundary missed.

### O2 — Unchanged bounds and production code

No production code changes. These all stay as they are: `MULTI_PREDECESSOR_BUDGET`,
`FIRST_PREDECESSOR_RELEASE_DELAY`, `MULTI_PREDECESSOR_COMPLETION_BOUND`, `SIGNAL_TIMEOUT`,
`COMPLETION_BOUND`, the production `RETIRE_WAIT_TIMEOUT`, and the pool deadlines (d-20261031-02
keeps the first four and `SIGNAL_TIMEOUT` unchanged). The change is confined to this one test
body in `mod retirement_tests`.

### O3 — Discriminating proof

All disposable edits are restored byte-identically, and each one is reported with its exit code.
The planner's probe already measured the BASE side (Probe evidence). The phase repeats the
repaired side in the worktree:

1. **Test-thread latency.** With a disposable 300 ms and 1200 ms sleep on the test thread after
   `reached(&waited)`, the repaired test passes. The BASE failure under +300 ms is recorded
   evidence.
2. **Acquiring-thread delay.** With a disposable 800 ms sleep inside the hook before the release,
   so the release falls after the 700 ms deadline, the repaired test passes with `Conflict`.
3. **Fresh-budget fault.** A disposable production edit gives each predecessor wait in
   `predecessor_admission_inner` a fresh `Instant::now() + 700 ms` deadline. The repaired test
   must fail on the `MULTI_PREDECESSOR_COMPLETION_BOUND` assertion with exit 101, alone and
   combined with +1200 ms of test-thread latency.
4. **Diagnostics.** A disposable withheld signal for each boundary in turn (the
   `predecessor_wait` send, then the `predecessor_drained` send) fails with exit 101 and that
   boundary's own diagnostic. Each is then restored.
5. **Clean.** `db::repository::retirement_tests::` passes three consecutive times,
   `db::repository::` passes, and `cargo fmt --check` is clean.

## Decisions and trade-offs

* **Decided autonomously (full auto):**
  * **Question:** Does the fix for the multi-predecessor readiness miss belong in the test's wait
    design or in the repository code, and how is the first release ordered?
  * **Chosen:** Test-only. The first release moves into the acquiring thread's
    `predecessor_wait` hook.
  * **Rejected:** Widening `MULTI_PREDECESSOR_BUDGET` or the delays, which only enlarges a
    wall-clock margin, slows the test and touches bounds that d-20261031-02 keeps. Raising
    `SIGNAL_TIMEOUT`, which d-20261031-02 rejects and which cannot help because the drain never
    happens. Releasing from a helper thread, which reintroduces the scheduling race. Changing
    production deadline computation, which is correct (premises 2–4). Serializing tests or gates
    (d-20261023-12, d-20261031-02).
  * **Reason:** Probe evidence and source trace show the miss is a test-thread release landing
    after the shared deadline. The hook already runs on the acquiring thread, before the waits.
  * **Reversal path:** Restore the test-thread release only with a deterministic ordering
    primitive that keeps the first release before the deadline independently of scheduling, and
    keep O3's fresh-budget fault rejection.
  * The trade-off: the first predecessor's wait no longer blocks and then wakes on the drain. It
    observes an already-drained gate. Wake-on-drain is covered separately by
    `lru_retains_actual_handle_and_fences_same_key_reopen` and the other `retirement_tests`
    cases that release a held handle while a waiter blocks. This test's subject is the shared
    absolute deadline.
* Cites d-20261014-03 (observe actual boundaries, not end-to-end timing), d-20261022-27 (separate
  ordering from scheduling latency), d-20261031-02 (unchanged named bounds) and d-20261029-04
  (gate scheduling is not edited).

## Risks / open questions

* `MULTI_PREDECESSOR_COMPLETION_BOUND` (1050 ms) remains a wall-clock assertion. After O1b it
  depends only on the acquiring thread: either its own wakeup after the 700 ms deadline, or its
  late arrival at the hook, exceeding about 350 ms. That is the discriminating contract for the
  fresh-budget regression (about 1200 ms), it has not been observed failing, and d-20261031-02
  keeps it. This is a known limit, not part of this change.

* Which `reached` call failed in the three hosted runs is not proven (review-plan r1, PR1). The
  reproduced race explains the 10 s signature, and the repair removes it. If the
  predecessor-wait boundary misses after this change, O1c's diagnostic says so, and that would be
  a different cause to diagnose.
