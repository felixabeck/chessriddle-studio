## Approach

### O1 — In test builds each test thread gets its own production-sized `BLOCKING_GATEWAY`

In `cfg(test)` builds, the process-global `BLOCKING_GATEWAY` admits against a semaphore of
`BLOCKING_GATEWAY_PERMITS` (4) permits owned by the OS thread that awaits admission (lazily created
per thread), instead of one process-wide semaphore. A libtest test therefore sees exactly the
production capacity, saturating it from its own thread still blocks its own later admissions, and
no other test can consume it. Non-test builds keep exactly one process-wide semaphore of
`BLOCKING_GATEWAY_PERMITS`, unchanged. Isolated gateways built with `BlockingGateway::new(n)`
keep their single explicit semaphore in every build. Every read of the gateway's capacity
(admission in `spawn` / `spawn_cancellable`, and the test-only `available_permits` helper) goes
through the same selection, so no path observes a different semaphore than admission uses. The
permit, once acquired, is still moved into the blocking worker and released when the closure
exits (thread-of-acquisition only selects the semaphore; it does not bind the release thread).

This removes the mechanism the MANDATE's "independent of the tree" failure scenario rests on:
unrelated tests — including the deliberate four-holder saturations in `fs.rs` — no longer share
one queue. The `BlockingGateway` doc comment states both builds: shipped app = one process-wide
four-permit gateway (four nested acquisitions hang the process); test builds = four permits per
awaiting thread.

Known limits (pre-existing, not new mechanisms): production code that awaits gateway work on the
process-global `tauri::async_runtime` still shares those worker threads' semaphores across tests,
exactly as today's single global; a test that deliberately drives gateway contention from several
OS threads would see per-thread capacity (Locate found none).

### O1b — The fs.rs serialisation lock goes with the shared queue it existed for

`ARCHIVE_GATEWAY_TEST_LOCK` and its three acquisitions in `fs.rs` exist only "so separate test
runtimes cannot each retain half the gateway". With O1 that cannot happen, so the lock and its
comment are removed; the four archive tests keep every assertion and still saturate (their own)
four permits. If an archive test turns out to need serialisation for another reason, the lock
stays with a corrected comment instead (executor reports which).

### O2 — The fixture's 5 s ceiling stays an event ceiling

No change to `pgn.rs:2179-2182` or any other test bound (d-20261031-02 class: event-observation
ceilings stay 5 s; the open question required a trace before touching the bound, and the trace
shows the bound is not the cause).

### O3 — Verification

* **Revert detector (committed, `infra/blocking.rs` tests).** One test thread holds all four
  permits of `BLOCKING_GATEWAY` with parked workers; a second OS thread (with its own
  `current_thread` runtime) concurrently runs four admissions on `BLOCKING_GATEWAY` and they all
  complete within a generous event ceiling while the first thread's holders are still parked. On
  today's single process-wide semaphore the second thread cannot be admitted until release, so the
  test goes red if O1 is reverted. Holders are released on every exit path (guard), and the test

* **Capacity retained (committed, same module).** On one thread, with four holders parked, a

## Approach

### O1 — In test builds each test thread gets its own production-sized `BLOCKING_GATEWAY`

In `cfg(test)` builds, the process-global `BLOCKING_GATEWAY` admits against a semaphore of
`BLOCKING_GATEWAY_PERMITS` (4) permits owned by the OS thread that awaits admission (lazily created
per thread), instead of one process-wide semaphore. A libtest test on a `current_thread` runtime
(the default, and every gateway-saturating test Locate found) therefore sees exactly the
production capacity, saturating it from its own thread still blocks its own later admissions, and
no other test can consume it. A `multi_thread` test (e.g. `worker_threads = 4` in
`file_workspace.rs`) gets four permits per worker of its own runtime: more than production, still
isolated from other tests; none of those tests asserts the limit. Non-test builds keep exactly one process-wide semaphore of
`BLOCKING_GATEWAY_PERMITS`, unchanged. Isolated gateways built with `BlockingGateway::new(n)`
keep their single explicit semaphore in every build. Every read of the gateway's capacity
(admission in `spawn` / `spawn_cancellable`, and the test-only `available_permits` helper) goes
through the same selection, so no path observes a different semaphore than admission uses. The
permit, once acquired, is still moved into the blocking worker and released when the closure
exits (thread-of-acquisition only selects the semaphore; it does not bind the release thread).

This removes the mechanism the MANDATE's "independent of the tree" failure scenario rests on:
unrelated tests — including the deliberate four-holder saturations in `fs.rs` — no longer share
one queue. The `BlockingGateway` doc comment states both builds: shipped app = one process-wide
four-permit gateway (four nested acquisitions hang the process); test builds = four permits per
awaiting thread.

Known limits (pre-existing, not new mechanisms): production code that awaits gateway work on the
process-global `tauri::async_runtime` still shares those worker threads' semaphores across tests,
exactly as today's single global; a test that deliberately drives gateway contention from several
OS threads would see per-thread capacity (Locate found none).

### O1b — The fs.rs serialisation lock goes with the shared queue it existed for

`ARCHIVE_GATEWAY_TEST_LOCK` and its three acquisitions in `fs.rs` exist only "so separate test
runtimes cannot each retain half the gateway". With O1 that cannot happen, so the lock and its
comment are removed; the four archive tests keep every assertion and still saturate (their own)
four permits. If an archive test turns out to need serialisation for another reason, the lock
stays with a corrected comment instead (executor reports which).

### O2 — The fixture's 5 s ceiling stays an event ceiling

No change to `pgn.rs:2179-2182` or any other test bound (d-20261031-02 class: event-observation
ceilings stay 5 s; the open question required a trace before touching the bound, and the trace
shows the bound is not the cause).

### O3 — Verification

* **Revert detector (committed, `infra/blocking.rs` tests).** One test thread holds all four
  permits of `BLOCKING_GATEWAY` with parked workers; a second OS thread (with its own
  `current_thread` runtime) concurrently runs four admissions on `BLOCKING_GATEWAY` and they all
  complete within a generous event ceiling while the first thread's holders are still parked. On
  today's single process-wide semaphore the second thread cannot be admitted until release, so the
  test goes red if O1 is reverted. Holders are released on every exit path (guard), and the test
  bounds every wait.
* **Capacity retained (committed, same module).** On one thread, with four holders parked, a
  fifth `BLOCKING_GATEWAY` admission is not granted (bounded negative wait), then is granted
  after one release. It goes red if test builds lift the limit (the round-1 design) or change the
  per-thread capacity.

* **Question:** How is f-20261031-01's cross-test admission queueing on `BLOCKING_GATEWAY`
  removed? **Chosen:** in test builds, the global gateway's four permits are per awaiting OS
  thread (O1); production keeps one process-wide four-permit semaphore. **Rejected:** lifting the
  global limit in test builds (round-1 plan; breaks the `fs.rs` archive tests that prove cleanup
  waits for admission on the four-permit global, P1-01); raising the fixture's 5 s ceiling (masks
  the queue; d-20261031-02 keeps event ceilings at 5 s and the trace shows the bound is not the
  cause); injecting a gateway into `PgnRepository`/`AppState` (production API change for a
  test-isolation defect, and the archive tests drive production code that reads the global);
  serialising every gateway user with a test lock (any new test reintroduces it; d-20260914-04
  rejected `TEST_HOOK_SERIAL` for the same reason); trimming individual long holders (holds are
  legitimate and new ones keep appearing); a tokio runtime-id key (`Handle::id` needs
  `tokio_unstable`). **Reason:** the trace shows queueing on a production limiter shared by
  unrelated tests; per-thread capacity keeps every test's view of the production limit and removes
  the sharing. **Reversal:** a test that must observe gateway contention across OS threads of
  different tests, or a measured cost of per-thread semaphores; revert the O1 commit (and restore
  `ARCHIVE_GATEWAY_TEST_LOCK`).
