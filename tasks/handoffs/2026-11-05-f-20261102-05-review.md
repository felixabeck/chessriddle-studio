## Decided autonomously (to be recorded at adoption through `./scripts/findings.py record-decision`)

Decided autonomously (full auto; recorded at adoption):

* **D1 (order):** Question: How does policy §8's light-then-fastest-failing order map onto the push
  gate? Chosen: a light stage (contract, bundle, rust-lint) that must terminate before the heavy
  stage starts. The heavy stage keeps its declared order and admission, with mutation last.
  Rejected: the unchanged single P2 stage, because heavy lanes start before contract's lint and
  contract checks finish (measured gap about 88 s), which §8 forbids. Also rejected:
  frontend-coverage between rust-test and rust-coverage, because it saves about 15 s of measured
  time to red and reopens d-20261029-04's admission without new evidence. Reversal: measured lane
  durations that justify a new admission proof, or removing the light-stage barrier.
* **D2 (running work):** Question: Which lanes may finish once a sibling is red? Chosen: running
  commands finish under existing supervision, and a running multi-command lane stops at its next
  command boundary as `stopped`. Rejected: terminating running lanes, because it would lose receipts
  and cleanup guarantees, and policy §8 forbids only starts. Also rejected: letting multi-command
  lanes finish every command, because each further command is a gate start. Reversal: remove the
  boundary check for the latch.
* **D3 (scope):** Question: Does the latch apply to pre-review mode? Chosen: yes, because policy §8
  covers every batch runner and both modes share `runStep`/`runLane`. Rejected: a push-only latch,
  which would need a mode flag through shared helpers. Reversal: gate the latch on mode.

## Approach

### O1 Red latch

The first step or lane whose terminal status is `failed` latches the run. Advisory `warning`
results do not latch. Signals and cleanup errors keep their existing blocks. From that moment no
P0/P1 step, P2 lane or further lane command starts. The latch is recorded synchronously, as the
red task's terminal status is set and before that task's promise settles, so every `.then` chain
and every pre-start check observes it. Both modes get it because both use `runStep`/`runLane`.
This is the policy §8 sentence "After a red, start no further gate."

### O2 Not-started gates are reported as skipped

Every selected step or lane that does not start because of the latch records status `skipped`,
with a reason that names the first red task (for example `rust-lint failed, so no further gate
started`). Signal and cleanup reasons keep precedence over the latch reason. Each selected gate
appears exactly once in the summary. The existing dependency-specific skip reasons (guard,
setup-rust, frontend-build) may stay or be folded into the latch, provided this reporting
contract holds.

### O3 Already-running work

A gate that is already running when the latch is set is not terminated and keeps its existing
supervision and cleanup. That covers a concurrent sibling such as contract or bundle beside a
Rust lane, and mutation that started concurrently with frontend-coverage. Policy §8 permits
concurrency inside one stage and only forbids new starts. A running multi-command lane finishes its
current command and starts no further command. It records the new status `stopped`, with a reason
that names the red task and no exit code. `stopped` is not a failure: it does not set the exit code,
and the summary prints it like `skipped`. When the lane's own command failed, the lane is `failed`
as today. When signals or cleanup errors cut a lane between commands, the lane keeps today's
outcome.

### O4 Order and exit code

The declared order is kept: P0, P1, then contract and bundle beside the serial Rust lanes
(lint → test → coverage), then frontend-coverage, e2e, and mutation last unless the existing
concurrency thresholds apply. Rust coverage keeps running before frontend-coverage. Moving
frontend-coverage between Rust test and Rust coverage would save about 15 s of mean time to red
(115 s vs 130 s measured) at the cost of reopening d-20261029-04's compiler/memory admission, for
which there is no new evidence. Mutation (1703 s) stays last. Exit-code precedence is unchanged:
the first failed P0/P1 step, else the first failed or interrupted lane in table order.

### O6 Verification

discriminating cases:

   frontend-coverage, e2e and mutation never start (no spawn event). The summary lists each as
   `skipped` with the red-gate reason, and the exit code is the red lane's.
2. A P1 red (frontend-build) with all blocks: no lane starts, including contract. Every selected
   lane is `skipped`.
3. A running concurrent sibling (contract held while rust-lint fails) runs to completion, and its

4. A multi-command lane cut at a command boundary records `stopped`, the remaining commands never

5. An advisory `rust-target-eviction` warning does not latch, and every later gate still runs.

7. Pre-review: a frontend-build red skips every selected lane.

Each case must go red against the current scheduler. The implementer confirms this by reverting

## Decisions and trade-offs

Decided autonomously (full auto; recorded at adoption):

* **D1 (order):** Question: Does fail-fast require reordering the lanes by fastest failure? Chosen:
  keep the declared order, with mutation last. Rejected: frontend-coverage between rust-test and
  rust-coverage, because it saves about 15 s of measured time to red and reopens d-20261029-04's
  admission without new evidence. Reversal: measured lane durations that show a gap large enough to
  justify a new admission proof.
* **D2 (running work):** Question: Which lanes may finish once a sibling is red? Chosen: running
  commands finish under existing supervision, and a running multi-command lane stops at its next
  command boundary as `stopped`. Rejected: terminating running lanes, because it would lose receipts
  and cleanup guarantees, and policy §8 forbids only starts. Also rejected: letting multi-command
  lanes finish every command, because each further command is a gate start. Reversal: remove the
  boundary check for the latch.
* **D3 (scope):** Question: Does the latch apply to pre-review mode? Chosen: yes, because policy §8
  covers every batch runner and both modes share `runStep`/`runLane`. Rejected: a push-only latch,
  which would need a mode flag through shared helpers. Reversal: gate the latch on mode.

## Approach

### O1 Red latch

The first step or lane whose terminal status is `failed` latches the run. Advisory `warning`
results do not latch. Signals and cleanup errors keep their existing blocks. From that moment no
P0/P1 step, P2 lane or further lane command starts. The latch is recorded synchronously, as the
red task's terminal status is set and before that task's promise settles, so every `.then` chain
and every pre-start check observes it. Both modes get it because both use `runStep`/`runLane`.
This is the policy §8 sentence "After a red, start no further gate."

### O2 Not-started gates are reported as skipped

Every selected step or lane that does not start because of the latch records status `skipped`,
including the selected P0/P1 steps after a mutation-guard red, which today's guard-failure branch
omits. The status carries a reason that names the first red task (for example `rust-lint failed, so no further gate
started`). Signal and cleanup reasons keep precedence over the latch reason. Each selected gate
appears exactly once in the summary. The existing dependency-specific skip reasons (guard,
setup-rust, frontend-build) may stay or be folded into the latch, provided this reporting
contract holds.

### O3 Already-running work

A gate that is already running when the latch is set is not terminated and keeps its existing
supervision and cleanup. That covers a concurrent sibling such as contract or bundle beside a
Rust lane, and mutation that started concurrently with frontend-coverage. Policy §8 permits
concurrency inside one stage and only forbids new starts. A running multi-command lane finishes its
current command and starts no further command. It records the new status `stopped`, with a reason
that names the red task and no exit code. `stopped` is not a failure: it does not set the exit code,
and the summary prints it like `skipped`. When the lane's own command failed, the lane is `failed`
as today. When signals or cleanup errors cut a lane between commands, the lane keeps today's
outcome.

### O4 Order: light stage before heavy stage, and exit code

Policy §8 says "Run light gates first … Then run heavy gates". Push-mode P2 becomes two stages.
The light stage is contract, bundle and rust-lint, run concurrently as today, with rust-lint still
the first Rust lane. The heavy stage is rust-test, rust-coverage, frontend-coverage, e2e and
frontend-mutation. It starts only after every selected light-stage lane has terminated, so any
light red latches before a heavy start. Inside the heavy stage the existing order and admission
are kept: rust-test then rust-coverage serially. After them, frontend-coverage and e2e (which
waits for bundle and every Rust lane) start together and run concurrently, as they do today
(measured: both started at about 22:20:36). Mutation runs last unless the existing concurrency
thresholds apply, in which case it starts with them. Rust coverage keeps running before frontend-coverage. Moving
frontend-coverage between Rust test and Rust coverage would save about 15 s of mean time to red
(115 s vs 130 s measured) and reopen d-20261029-04's compiler/memory admission without new
evidence. Mutation (1703 s) stays last. On a green run the light stage costs about 88 s before
rust-test starts (measured contract minus rust-lint end). A `--frontend`-only run likewise waits for contract and bundle before frontend-coverage, about 2 min of contract time on a green run. A contract-only run has no heavy stage. P0/P1 (guard, eviction, setup-rust,
frontend-build, bindings-check) keep their serial order ahead of P2 as prerequisites. Pre-review
mode keeps its single concurrent lane stage. Exit-code precedence is unchanged: the first failed
P0/P1 step, else the first failed or interrupted lane in table order.

`pnpm gates:push` and `pnpm checks:pre-review` start no further gate after the first red step or
lane. Work that is already running ends normally, and every selected gate that never started
appears in the summary as skipped, with a reason that names the red gate. The push skill and the
gate-tooling rule describe this behaviour.

## MANDATE

f-20261102-05 (verbatim, ledger header and body):

* **Where:** the push gate scheduler behind `pnpm gates:push` (`scripts/run-push-gates.mjs`), documented in the push skill §2: "Ordinary Rust failures do not skip later selected lanes."
* **Defect:** a red lane does not stop queued lane starts, so the remaining Rust, coverage and mutation lanes run to completion before repair. The agent-kit push policy now requires fail-fast order (agent-kit f-20261102-06): light gates, then the fastest-failing heavy gates, and no further start after the first red.
* **Failure scenario:** a Rust lane fails early; the scheduler still starts every later Rust lane and the frontend coverage and mutation lanes, and every one of them has to run again after the repair because the repair changes the tree. The documented behaviour makes this certain on every red run.
* **Open question:** which lanes may finish once a sibling is red (e.g. the contract lane already running), and does mutation stay last?
* **Fix direction:** after the first red lane, start no queued lane (report them as skipped), keep running lanes' cleanup guarantees, and update the push skill §2 sentence.
* **Proof:** a scheduler test where an early lane fails shows no later lane started and the summary lists them as skipped.
* **Update (2026-11-02, later):** agent-kit released the fail-fast rule in 3fd5a27a: `references/push-review-policy.md` §8 "Fail-fast gate order" now requires light gates first, then the fastest-failing heavy gates, and no further gate start after a red, with project runners stopping queued starts. The Correction above no longer applies; this finding implements that adopted policy. The push skill §2 names this finding as the scheduler's known limitation until it is fixed.

Governing policy text (`~/.claude/references/push-review-policy.md` §8 "Fail-fast gate order"):
"Run light gates first: format, lint, typecheck, generator/contract drift. Then run heavy gates by
how fast they fail: unit suites before browser/E2E and full backend suites. Gates inside one stage
may run concurrently. After a red, start no further gate. … A project runner that schedules a
batch must stop queued starts after a red."

## Threat model and non-goals

Inputs are exit codes, spawn errors and signals from this repository's own gate commands. There is
no adversary. Environments are Felix's Linux machine under `agent-gate` and drain gate runs. CI does
not run this scheduler (`.github/workflows/**` does not reference it).

Non-goals: terminating gates that are already running, changing memory/CPU admission, changing
receipt contracts, changing which lanes a flag selects, and changing exit-code precedence.

## Approach

### O1 Red latch

The first step or lane whose terminal status is `failed` latches the run. Advisory `warning`
results do not latch. Signals and cleanup errors keep their existing blocks. From that moment no
P0/P1 step, P2 lane or further lane command starts. The latch is recorded synchronously, as the
red task's terminal status is set and before that task's promise settles, so every `.then` chain
and every pre-start check observes it. Both modes get it because both use `runStep`/`runLane`.
This is the policy §8 sentence "After a red, start no further gate."

### O2 Not-started gates are reported as skipped

Every selected step or lane that does not start because of the latch records status `skipped`,
including the selected P0/P1 steps after a mutation-guard red, which today's guard-failure branch
omits. The status carries a reason that names the first red task (for example `rust-lint failed, so no further gate
started`). Signal and cleanup reasons keep precedence over the latch reason. Each selected gate
appears exactly once in the summary. The existing dependency-specific skip reasons (guard,
setup-rust, frontend-build) may stay or be folded into the latch, provided this reporting
contract holds.

### O3 Already-running work

A gate that is already running when the latch is set is not terminated and keeps its existing
supervision and cleanup. That covers a concurrent sibling such as contract or bundle beside a
Rust lane, and mutation that started concurrently with frontend-coverage. Policy §8 permits
concurrency inside one stage and only forbids new starts. A running multi-command lane finishes its
current command and starts no further command. It records the new status `stopped`, with a reason
that names the red task and no exit code. `stopped` is not a failure: it does not set the exit code,
and the summary prints it like `skipped`. When the lane's own command failed, the lane is `failed`
as today. When signals or cleanup errors cut a lane between commands, the lane keeps today's
outcome.

### O4 Order: light stage before heavy stage, and exit code

Policy §8 says "Run light gates first … Then run heavy gates". Push-mode P2 becomes two stages.
The light stage is contract, bundle and rust-lint, run concurrently as today, with rust-lint still
the first Rust lane. The heavy stage is rust-test, rust-coverage, frontend-coverage, e2e and
frontend-mutation. It starts only after every selected light-stage lane has terminated, so any
light red latches before a heavy start. Inside the heavy stage the existing order and admission
are kept: rust-test then rust-coverage serially. After them, frontend-coverage and e2e (which
waits for bundle and every Rust lane) start together and run concurrently, as they do today
(measured: both started at about 22:20:36). Mutation runs last unless the existing concurrency
thresholds apply, in which case it starts with them. Rust coverage keeps running before frontend-coverage. Moving
frontend-coverage between Rust test and Rust coverage would save about 15 s of mean time to red
(115 s vs 130 s measured) and reopen d-20261029-04's compiler/memory admission without new
evidence. Mutation (1703 s) stays last. On a green run the light stage costs about 88 s before
rust-test starts (measured contract minus rust-lint end). A `--frontend`-only run likewise waits for contract and bundle before frontend-coverage, about 2 min of contract time on a green run. A contract-only run has no heavy stage. P0/P1 (guard, eviction, setup-rust,
frontend-build, bindings-check) keep their serial order ahead of P2 as prerequisites. Pre-review
mode keeps its single concurrent lane stage. Exit-code precedence is unchanged: the first failed
P0/P1 step, else the first failed or interrupted lane in table order.

`.claude/skills/push/SKILL.md` §2 replaces "Ordinary Rust failures do not skip later selected
lanes." and the known-limitation sentence with the fail-fast contract (O1–O3). The
`.claude/rules/gate-tooling.md` "Scheduling and placement" paragraph replaces the two old-behaviour

### O6 Verification

`scripts/run-push-gates-tests.mjs` rewrites the tests that pin the old behaviour (the three named
in Traced premises, plus any other that fails for this reason alone) to the new contract and adds
the cases below. Regression cases (R) must go red against the current scheduler. Preservation
cases (P) pin behaviour that must survive and may pass on both.

1. (R) A Rust lane red (rust-lint clippy) with `--rust --frontend`: rust-test, rust-coverage,
   frontend-coverage, e2e and mutation never start (no spawn event). The summary lists each as
   `skipped` with the red-gate reason, and the exit code is the red lane's.
2. (R) A P1 red (frontend-build) with all blocks: no lane starts, including contract. Every selected
   lane is `skipped`.
3. (P+R) A running concurrent sibling (contract held while rust-lint fails) runs to completion and
   its own result stands (P). After both end, no heavy-stage lane starts (R).
4. (R) A multi-command lane cut at a command boundary records `stopped`, the remaining commands never
   spawn, and the exit code is the red task's.
5. (P) An advisory `rust-target-eviction` warning does not latch, and every later gate still runs.
6. Frontend-coverage red inside the heavy stage. (R) With the mutation thresholds unmet,
   mutation is still queued behind frontend-coverage and e2e, so a frontend-coverage red means
   mutation never starts and is reported `skipped`. (P) With the thresholds met, mutation and e2e
   start alongside frontend-coverage and run to completion with their own results.
7. (R) Pre-review: a frontend-build red skips every selected lane.
8. (R) Mutation-guard red with all blocks: `mutation-guard` appears once as `failed` and supplies
   the exit code. Every subsequent selected P0/P1 step (eviction, setup-rust, frontend-build,
   bindings-check) and every selected lane appears exactly once as `skipped`, with a reason
   naming `mutation-guard`.
9. (R) Light stage: with contract held, no heavy-stage lane starts until contract ends. A contract
   red after rust-lint passed starts no heavy-stage lane.

The implementer reverts the scheduler change locally, confirms that every (R) case goes red, and
reports the observed failures.

## Decisions and trade-offs

Decided autonomously (full auto; recorded at adoption):

* **D1 (order):** Question: How does policy §8's light-then-fastest-failing order map onto the push
  gate? Chosen: a light stage (contract, bundle, rust-lint) that must terminate before the heavy
  stage starts. The heavy stage keeps its declared order and admission, with mutation last.
  Rejected: the unchanged single P2 stage, because heavy lanes start before contract's lint and
  contract checks finish (measured gap about 88 s), which §8 forbids. Also rejected:
  frontend-coverage between rust-test and rust-coverage, because it saves about 15 s of measured
  time to red and reopens d-20261029-04's admission without new evidence. Reversal: measured lane
  durations that justify a new admission proof, or removing the light-stage barrier.
* **D2 (running work):** Question: Which lanes may finish once a sibling is red? Chosen: running
  commands finish under existing supervision, and a running multi-command lane stops at its next
  command boundary as `stopped`. Rejected: terminating running lanes, because it would lose receipts
  and cleanup guarantees, and policy §8 forbids only starts. Also rejected: letting multi-command
  lanes finish every command, because each further command is a gate start. Reversal: remove the
  boundary check for the latch.
* **D3 (scope):** Question: Does the latch apply to pre-review mode? Chosen: yes, because policy §8
  covers every batch runner and both modes share `runStep`/`runLane`. Rejected: a push-only latch,
  which would need a mode flag through shared helpers. Reversal: gate the latch on mode.

## Risks / open questions

* `stopped` is a new status string. Consumers are `printSummary`, the exit-code loop and the tests.
  No other script reads the summary statuses (`git grep -l run-push-gates` lists only the
  scheduler, its tests, routing checker, gate-parallelism and run-frontend-mutation, and none of
  them parse statuses).
* Rewriting old-behaviour tests must not lose their unrelated assertions (ordering, logs, exit
  precedence, admission order on green runs). Those keep their own coverage.

## Not part of this task

Reordering lanes, terminating running gates, changes to memory/CPU admission, receipt reuse, CI
workflows, and agent-kit's shared policy text.
