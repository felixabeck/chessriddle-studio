## Approach

### O1 — Geometry and click target are one element

`playBoardMove` acquires a concrete board element (an `ElementHandle` from the `board` locator, or
an equivalent identity-preserving mechanism). It measures that element's non-null box and clicks
**that element** with the offset derived from that box. A click attempt that fails because the
element detached dispatched no event, so the helper re-acquires the board and redoes that same
click. Retries are bounded by a `expect.poll`/`toPass`-style timeout no longer than the existing
default expect timeout. Exhausting it fails with a message naming the square and "board kept
detaching".

### O2 — The source click is verified before the destination click

After the source click, the helper confirms chessground's `square.selected` inside that board
element is at the source square (white orientation, as `squarePosition` already assumes):

* no selected square at all → the click hit nothing movable (the observed b6 case). Re-acquire and
  re-measure, then redo the source click. This is safe because with no selection a click cannot
  submit a move.
* the source square is selected → proceed.
* a different square is selected → fail immediately, naming both squares. Never click again,
  because a second click could submit a move or toggle the selection off.

### O3 — The destination click is dispatched at most once

The destination click uses fresh geometry from the element whose selection O2 verified. If that
element detached before dispatch (O1's detach error), the selection died with it. The helper then
restarts from O2's source click on the new element; no destination event was dispatched. Once a
destination click has been dispatched, the helper never clicks again, whatever the board then
shows. Rejection and revert semantics stay the caller's to assert.

### O4 — Regression proof at the helper level

The existing stub-board test "playBoardMove waits for a measured board box" in
`e2e/new-game-to-database.spec.ts` keeps proving the null-box wait (f-20261030-21). It is extended,
or joined by sibling stub tests, so that each of these goes red against today's helper:

1. the first measured element detaches before the source click, and the replacement has a different
   size → the click lands at the replacement's square centre, not the stale offset;
2. the source click registers no selection → exactly one source re-click, then one destination click;
3. a different square is selected after the source click → the helper throws and dispatches no
   destination click;
4. after a dispatched destination click the helper issues no further click.

The stubs model only what the helper touches (element acquisition, box, click, selected-square
probe). Their shape is the executor's choice.

### O5 — No caller or product change

The 29 call sites keep their signatures and assertions. `dragBoard` and the renderer are unchanged.
The `_page` parameter stays, since callers pass it.

## Decisions and trade-offs

Decided autonomously (full auto, PLAN-ONLY):

* **Mechanism: test race in the e2e helper, not a renderer race.** The trace proves the tree had
  no move, so the save path took its documented validation exit. Rejected: changing the renderer
  save path or lengthening the origin poll timeout, because neither addresses a move that never
  happened.
* **Fix the shared helper, not this one spec.** Rejected: adding a `1. e4` assertion in the linked
  test only. It would turn the symptom into a clearer failure but would not stop the flake, and the
  same helper serves 28 other call sites.
* **Retry only clicks proven not to have submitted a move.** Rejected: a universal "move landed,
  else retry the pair" postcondition, because puzzle and practice callers legitimately get
  reverted moves and a retry would double-submit. Rejected: waiting for box stability alone, because
  in the trace the remount came about 1.2 s after measurement, so a stability window would have
  passed on the 192-px board.
* **`dragBoard` is out of scope.** It shares `boardBox`, but no failure has been observed (rule 4d).
  If O1 moves the measurement into a shared primitive, `dragBoard` may keep calling its current
  `boardBox` unchanged.

## Approach

### O1 — Geometry and click target are one element

`playBoardMove` acquires a concrete board element (an `ElementHandle` from the `board` locator, or
an equivalent identity-preserving mechanism). It measures that element's non-null box and clicks
**that element** with the offset derived from that box. Playwright's handle actions throw when the
element is not attached, before dispatching input. Only that not-attached failure counts as "no
event dispatched"; any other error propagates unchanged. Retries are bounded by a
`expect.poll`/`toPass`-style timeout no longer than the existing default expect timeout.
Exhausting it fails with a message naming the squares and "board kept detaching".

### O2 — A detach at either click restarts the pair on the new board

The source and destination clicks are dispatched on **one** acquired element. If that element
turns out to be detached at either click, the helper re-acquires the board, re-measures it and
restarts the pair from the source click. That is safe at both boundaries:

* detached at the source click → nothing was dispatched;
* detached at the destination click → no destination event was dispatched, and the earlier source
  selection died with the old chessground instance (a remount creates fresh state), so the
  replacement needs the source click again. Retrying only the destination on the replacement would
  reproduce the missing move.

The helper never inspects rendered selection. Chessground redraws through `requestAnimationFrame`,
which callers with a paused Playwright clock (`page.clock.pauseAt`, e.g. `workspace-tabs.spec.ts`,
`engine-gap.spec.ts`) do not advance until `playBoardMove` returns.

### O3 — The destination click is dispatched at most once

Once a destination click has been dispatched (the handle action returned or failed with anything
other than not-attached), the helper never clicks again, whatever the board then shows. Rejection
and revert semantics stay the caller's to assert.

### O4 — Regression proof at the helper level

The existing stub-board test "playBoardMove waits for a measured board box" in
`e2e/new-game-to-database.spec.ts` keeps proving the null-box wait (f-20261030-21). It is extended,
or joined by sibling stub tests.

Regression anchors (each goes red with only the `e2e/fixtures.ts` change reverted):

1. the first acquired element detaches at the source click, and the replacement has a different
   size → the source click lands at the replacement's square centre, computed from the
   replacement's box, never at the stale offset;
2. the element detaches after the source click and before the destination dispatch → the
   replacement receives the source click and then the destination click, in that order, and the
   stale element receives no destination click.

Preservation checks (pass before and after; they guard the safety contract):

3. after a dispatched destination click the helper issues no further click, including when the
   board then reports anything;
4. a non-detach click error propagates without a retry.

The stubs model only what the helper touches (element acquisition, box, click outcome). Their
shape is the executor's choice.

### O5 — No caller or product change

The 29 call sites keep their signatures and assertions. `dragBoard` and the renderer are unchanged.
The `_page` parameter stays, since callers pass it.

## Approach

### O1 — The helper acts only on an interactive board

`playBoardMove` narrows the caller's `board` locator to boards that are interactive, meaning inside
a chessground `.cg-wrap.manipulable`. It measures and clicks only that narrowed target. While the
caller's match is still a view-only board (the outgoing preview), it waits; the existing null-box
polling bounds that wait. If it never becomes interactive, the helper fails with a message saying
the board stayed view-only, instead of clicking it. Each click still measures right before it is
sent, as today.

### O2 — Withdrawn in r3 (detach-restart machinery)

The r2 obligation bound both clicks to one `ElementHandle` and restarted the pair on a
not-attached failure. That rested on reading the trace's detach as a remount of the game board. The
board that detached was the outgoing view-only preview (Traced premises), which O1 now excludes. No
remount of the interactive board between measurement and click has been observed. So the handle
machinery and its Playwright post-dispatch uncertainty are withdrawn (rule 4d, minimalism). The
rendered-selection probe withdrawn in r2 (PR-1) stays withdrawn.

### O3 — The destination click is dispatched at most once

The helper issues exactly one source click and one destination click on the interactive board, and
never repeats either. Rejection and revert semantics stay the caller's to assert. This holds today
and must survive the change.

### O4 — Regression proof

The existing stub-board test "playBoardMove waits for a measured board box" in
`e2e/new-game-to-database.spec.ts` keeps proving the null-box wait (f-20261030-21). It is adapted
only as far as O1's narrowing requires.

Regression anchor (goes red with only the `e2e/fixtures.ts` change reverted). This is a synthetic
page in a real Playwright browser, so the real Locator re-resolution behaviour is exercised. At
first the page holds only a view-only board: `.cg-wrap` without `manipulable`, about 192 px,
recording any click it receives. After a short delay that board is **removed** and an interactive
`.cg-wrap.manipulable` board of a different size (about 552 px), recording click positions, takes
its place. So `page.locator("cg-board").first()`, the caller's locator, names the preview at first
and the interactive board afterwards, as in the trace. `playBoardMove(…, "e2", "e4")` must
deliver exactly two clicks, both to the interactive board, at the e2 and then the e4 square centres
of that board's own size. The preview receives none. This also proves O1's waiting: while
the match is view-only, the helper neither clicks nor fails.

View-only rejection check (proves O1's failure contract): a page whose only board stays view-only.
`playBoardMove` must reject within a bounded time shorter than the test timeout, with the stated
view-only diagnostic, and the board must record zero clicks.

Preservation checks (pass before and after):

* exactly two clicks are dispatched per call (O3);
* a caller's locator that already names the interactive board works unchanged (any existing
  caller spec in the Phase 1 proof list).

The synthetic pages' markup and the delay mechanism are the executor's choice, provided both are
deterministic. A static page in which the view-only board remains first is not acceptable, because
`.first()` would never name the interactive board.

## Decisions and trade-offs

Decided autonomously (full auto, PLAN-ONLY):

* **Mechanism: test race in the e2e helper, not a renderer race.** The trace proves the tree had
  no move, so the save path took its documented validation exit. Rejected: changing the renderer
  save path or lengthening the origin poll timeout, because neither addresses a move that never
  happened.
* **Fix the shared helper, not this one spec.** Rejected: adding a `1. e4` assertion in the linked
  test only. It would turn the symptom into a clearer failure but would not stop the flake, and the
  same helper serves 28 other call sites.
* **Target the interactive board, with no retries.** The observed failure measured the outgoing
  view-only preview (PR-4). Rejected: an `ElementHandle` detach-and-restart scheme (r2 O1/O2),
  because the detach it handled was the preview's, O1 already excludes that, and the scheme carried
  an unproven Playwright post-dispatch premise. Rejected (PR-1): verifying the source click through
  rendered `square.selected`, because redraw runs on `requestAnimationFrame` and paused-clock callers
  never advance it during the helper. Rejected: a universal "move landed,
  else retry the pair" postcondition, because puzzle and practice callers legitimately get
  reverted moves and a retry would double-submit. Rejected: waiting for box stability alone, because
  the preview was stable at 192 px for about 1.2 s before it detached, so a stability window would
  have passed on the wrong board.
* **`dragBoard` is out of scope.** It shares `boardBox`, but no failure has been observed (rule 4d).
  If O1 moves the measurement into a shared primitive, `dragBoard` may keep calling its current
