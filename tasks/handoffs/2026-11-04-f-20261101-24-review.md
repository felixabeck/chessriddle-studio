## Approach

### O1 — Batch identity path treats an unparsable game like the projection does (class repair)

Quotes MANDATE: "an unparsable game fails the whole batch … the collection index elsewhere
already treats unparsable games as omitted."

In `append_absent`'s account branch and in `record_download`, a range that cannot be read within the bounded range read
(`Error::ResourceLimit` from `read_range_bytes`) or that does not parse to exactly one game
(`One(None)|Empty|Remainder|Err(_)` other than cancellation) no longer aborts the batch. The
single rule for "which range is an identity-usable game" must be shared by the projection in
`linked_collections.rs::refresh`, `record_download` and `append_absent` — one classifier (e.g. a helper returning `Option<TempGame>`
or a typed outcome) that both call, so the two paths cannot diverge again
(async-resource-invariants: second similar implementation is extracted). Cancellation and real
I/O errors still propagate unchanged.

* **Unparsable source occurrence:** inserted into no identity row that can match a batch
  fingerprint. It is still copied verbatim into the target (the whole source is copied, as today)
  and stays counted as `omitted` by the projection. If its provider game ID is readable
  (`provider_game_id`) and **no parsable source occurrence carries ID X**, a batch game carrying
  ID X is treated as present: not appended, no conflict raised. When a parsable source
  occurrence with ID X exists, the batch game X goes through the unchanged identity processing
  (fingerprint disagreement still conflicts); the omitted duplicate never suppresses that check.
  Suppressed batch occurrences are removed from identity processing **before**
  `legacy::revalidate` runs (they never enter `Batch`), so an omitted source occurrence that
  earlier acquired `Evidence` for ID X cannot make `legacy.rs:71-73` raise a conflict for a
  parsable batch game with ID X; that `Evidence` row is left unchanged (not rebound). Conflicts
  between parsable games keep their current semantics. Ordinals of all other source rows keep
  their range index so legacy `Evidence.Ordinal` joins stay valid.
* **Unparsable batch occurrence:** not inserted into `Batch`, never appended, and does not abort.
  The append loop skips ordinals that have no `Batch` row. The count of skipped batch games is
  logged (`log::info!`/`warn!` with counts only, no PGN content); `AppendOutcome` and generated
  bindings are unchanged.
* Every existing conflict (ambiguous IDs, ID/fingerprint disagreement, legacy revalidation)
  keeps its current semantics for parsable games.
* **Receipt (`record_download`):** an unparsable range no longer refuses the receipt. Its
  readable provider ID still enters `provider_ids`; it contributes no start time to
  `newest_start_ms` (conservative: the Chess.com cursor can only stay lower, which re-fetches
  overlap that the ID dedup absorbs). A receipt over a file with zero indexable games, including
  an empty file, is recorded with `newest_start_ms = None` (cursor = `since`), exactly as
  `account_sync_cursor` already defines. Date/time conflicts for parsable games are unchanged.
* The non-account path (`account.is_none()`) is unchanged.

### O2 — Chess.com staging keeps only games the app models (root at the provider boundary)

Quotes MANDATE: "filter unsupported variants at staging (`rules` not chess/chess960)".

`ArchiveGame` gains an optional `rules` field. A game whose `rules` is present and not
`"chess"` or `"chess960"` is not staged (no bytes counted against `MAX_PGN_BYTES`). A game with
absent `rules` is staged as today (O1 covers it if unparsable). The "empty requested game
archive" check keeps applying to the raw list, so a month holding only variant games is not an
error. A download whose filtered result has zero games publishes an empty PGN; its receipt is
recorded (O1 receipt rule) and appending it to the account collection appends 0 games, clears
the pending batch and introduces no new error. This path is newly reachable (BASE never stages
zero games because a requested archive with an empty raw list is an error) and is verified by O4. The download receipt/coverage
cursor is unchanged: filtered games are deliberately never imported.

### O3 — Recovery of an already-stuck pending batch

Quotes MANDATE: "what discard/recovery action does a stuck pending batch get?"

No new action. With O1 the pending batch's own staged file (which still contains the variant
game) appends successfully, so the existing Retry button (`LinkedCollection.tsx`) completes it,
`finish_pending` clears it, and the next Download proceeds. Verified by O4's stuck-batch test.

## Decisions and trade-offs

Decided autonomously (full auto):

* **Both O1 and O2, not one.** Q: filter at staging, or tolerate in the batch path? Chosen: both.
  Rejected: staging filter alone — it does not unstick a collection whose pending batch already
  holds a variant game (the pending input is reused, `batch.rs:256-279`), and does not cover an
  unparsable game already inside the collection PGN. Rejected: batch tolerance alone — a
  crazyhouse game without drops parses as standard chess and would be appended mislabelled.
  Reason: O1 removes the mechanism (one game fails the batch), O2 stops importing games the app
  cannot model. Reversal: drop O2's filter if variant support is added.
* **Allowlist `chess` + `chess960` for Chess.com.** Rejected: standard-only like
  `ACCOUNT_EXPORT_PERFS` — Chess.com chess960 games are staged today and the importer supports
  Chess960 (pgn-scanning rule), so excluding them would remove games users currently receive.
  Rejected: denylist of crazyhouse/bughouse — new Chess.com variants would re-open the defect.
  Reversal: extend the allowlist.
* **No new discard action for a pending batch.** Rejected: a Discard button — a new user-visible
  control (rule 33) whose only evidenced trigger, the unparsable game, O1 removes; genuine
  identity conflicts are deliberately preserved for reconciliation. Reversal: add a discard
  command if a non-parse stuck batch is observed.
* **No `AppendOutcome.skipped` field.** Rejected: surfacing a skipped count — changes Specta
  bindings and UI copy for a case the Lichess path already handles silently. Reversal: add the
  field and a `Collections.*` string.
