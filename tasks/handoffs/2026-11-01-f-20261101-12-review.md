## Decided autonomously (record through `record-decision` at adoption)

The plan's `## Decisions and trade-offs`, items 1–6, carries each question, the chosen and rejected options, the reason and the reversal path:

1. Scanner stays the boundary authority. The parser ends a game at a blank line only after its termination marker, and any remaining disagreement is refused (precedent d-20261023-09).
2. A `[%clk …]` line at the start of a movetext line stays a parser boundary, and the range is refused.
3. Remainder rule: any byte that a further `read_game` would see is refused. Only whitespace and `%` lines may follow.
4. The refusal crosses IPC as `Error::InvalidInput`. Both renderer consumers treat it as fail-closed.
5. The file list shows an activatable, renderer-only `Files.GameUnreadable` row without delete.
6. `write_game_core` refuses to replace a range that is not exactly one game.

## Approach

### A. Shared movetext boundary: a blank line ends a game only after its termination marker

The vendored parser stops treating a blank line inside movetext as a game end unless the current
game's termination marker (`1-0`, `0-1`, `1/2-1/2`, `*`) has already been read **outside comments
and outside variations**. A `[`-prefixed line still ends movetext exactly as today. The rule holds
identically in `read_movetext` and `skip_movetext` (normal and `Skip(true)` visitors, and variations
skipped through `skip_variation`). Normal and skip mode must give the same game count and the same
game ends on every fixture. The marker recognition is one private mechanism used by both modes,
not two copies. The scanner is not changed.

Consequences, stated once:
* `[Event "A"]\n\n1. e4 e5\n\n2. Nf3 Nc6 *` (LF and CRLF) is one parser game, matching the one scanner range.
* `{intro}\n\n1. e4 *` is one parser game. That fixes the collection `empty` cleanup deleting it.
* Tagless `1. e4 *\n\n1. d4 *` stays two parser games, so the DB import is unchanged. The scanner
  still gives one range, and obligation B refuses it.
* Tagless games with no termination markers and only a blank line between them
  (`1. e4 e5\n\n1. d4 d5`) become one parser game. That matches the scanner's one range. Known
  limit, recorded under Risks.
* A `[%clk 0:01]` line still ends the parser game. The scanner range stays one, and obligation B refuses it.

The vendor's patch notes, `src-tauri/vendor/pgn-reader/CHESSFABLE.md`, record the transition and its
required regressions in the same style as the existing entries.

### B. A scanner range is read as exactly one game, or refused

One application helper reads a game from a range's bytes with any `Visitor`. It then checks that
the rest of the input contains no further parser game with any visitor content: a header, a SAN,
a NAG, a comment, a variation or an outcome. Trailing whitespace, `%` escape lines and `;`
comments that produce no visitor callback are allowed. When further content is found, the helper
returns a typed refusal, which is distinct from a generic parse error. Cancellation keeps its
precedence. The probe of the remainder is bounded by the range bytes already in memory and adds no
whole-file read.

Every application site that interprets one scanner range as one game goes through this helper:

* `lex_pgn_cancellable`: the refusal maps to `Error::InvalidInput` with a message saying that the
  text contains more than one game. That is the same category as today's lexer parse error, so the
  error contract and generated bindings stay unchanged. Pasted or typed PGN in `PgnInput` gets the
  same refusal.
* linked projection (`linked_collections.rs` ≈2361): a refused range counts as omitted, as today's
  parse failures do.
* collection `Cleanup` (≈2973): a refused range is never omitted, under `empty` or `duplicates`. It is
  copied unchanged, and the cleanup continues.
* provider export (≈867) and `parse_identity_game` (`batch.rs`): a refused range keeps their
  existing `Conflict` error.

### C. The file game list survives a refused game

`GameSelector`'s page loader must not lose a whole page to one game that cannot be lexed. A
per-row parse failure that is not a cancellation yields a row labelled with a new localized string
`Files.GameUnreadable`, a sibling of the existing `Files.GameTooLarge` omission row. Every other row of
the page still loads. Cancellation still aborts the page as today. Opening that row shows the
existing open-failure notification, carrying obligation B's message. The new key gets a
translation in every `src/translation/*.json` file through `pnpm i18n:extract` and per-language text.

## Approach

### A. Shared movetext boundary: a blank line ends a game only after its termination marker

The vendored parser stops treating a blank line inside movetext as a game end unless the current
game's termination marker (`1-0`, `0-1`, `1/2-1/2`, `*`) has already been read **outside comments
and outside variations**. A `[`-prefixed line still ends movetext exactly as today.

One newline-boundary lookahead serves every movetext path: `read_movetext`, `skip_movetext`
(`end_headers → Skip(true)`) and `skip_variation` (`begin_variation → Skip(true)`). Today
`skip_variation` (`reader.rs:444-495`) has its own copy of the blank-line/`[`/`%` lookahead with
a different CRLF test. That copy is removed and routed through the shared lookahead, so all three
paths treat `\r` the same way. Termination-marker recognition is one private mechanism used by
both visitor modes. In skip mode it recognises the same tokens with the same delimiters as
`read_movetext`, including `\r` as a token end, and it adds no second token grammar. Normal and
skip mode give the same game count and the same game ends on every fixture, in LF and CRLF. The
scanner is not changed.

Consequences, stated once:
* `[Event "A"]\n\n1. e4 e5\n\n2. Nf3 Nc6 *` (LF and CRLF) is one parser game, matching the one scanner range.
* `{intro}\n\n1. e4 *` is one parser game.
* A `*` inside a variation, followed by a blank line, does not end the game or the variation.
* Tagless `1. e4 *\n\n1. d4 *` stays two parser games, so the DB import is unchanged. The scanner
  still gives one range, and obligation B refuses it.
* Tagless games with no termination markers and only a blank line between them
  (`1. e4 e5\n\n1. d4 d5`) become one parser game. That matches the scanner's one range. Known
  limit, recorded under Risks.
* A `[%clk 0:01]` line still ends the parser game. The scanner range stays one, and obligation B refuses it.

The vendor's patch notes, `src-tauri/vendor/pgn-reader/CHESSFABLE.md`, record the transition and its
required regressions in the same style as the existing entries.

### B. A scanner range is read as exactly one game, or refused

One application helper in `src-tauri/src/pgn.rs` reads a game from a range's bytes with the
caller's `Visitor`. It then checks the rest of the input. If a further `read_game` would return
`Some`, the helper returns a typed refusal: any byte that `read_game`'s own whitespace and `%`
skipping does not consume counts, independent of visitor or skip mode. That covers a second game,
a `{comment}`, a `;` comment and stray tokens. Only whitespace and `%` escape lines may follow the
game. The refusal is a distinct helper result, so callers can match it without matching every
error. Cancellation and I/O errors stay terminal on every caller and are never treated as a
refusal. The check works on range bytes already in memory and adds no whole-file read.

Every application site that interprets one existing scanner range as one game goes through this helper:

* `lex_pgn_cancellable`: the refusal maps to `Error::InvalidInput` with a message saying that the
  text contains more than one game. The lexer reads through the existing `CancellableRead`, so
  cancellation during the remainder check returns `Error::Cancellation`. Pasted or typed PGN in
  `PgnInput` gets the same refusal.
* `write_game_core` / `commit_pgn_mutation` (save over an existing range): the save is refused with
  `Error::InvalidInput`, and the file stays byte-identical, when the range being replaced is not
  exactly one game. This makes "no save deletes the rest of a range" a property of the save
  itself. It holds whatever produced the tree, including a tree held from before this change.
  Appending a new game (`n == games.len()`) is unaffected.
* linked projection (`linked_collections.rs` ≈2361): the refusal counts as omitted. Cancellation stays terminal.
* collection `Cleanup` (≈2973): a refused range is never omitted, under `empty` or `duplicates`. It is
  copied unchanged, and the cleanup continues. Other errors keep their current propagation.
* provider export (≈867) and `parse_identity_game` (`batch.rs`): the refusal maps to their
  existing `Conflict` error, never to `InvalidInput`.

On the renderer, `lex_pgn`'s `invalid-input` category already means "unavailable" to
`FileFreshnessGate` (`isUnavailableFileError`, `FileFreshnessGate.tsx:53-59`). A file game that an
external edit turns into a refused range therefore moves the tab to the fail-closed `unavailable`
state, the same as today's lexer parse errors. The panel message stays the existing
`FileFreshness.GameNoLongerInFile`. That is a known message imprecision shared with parse errors,
not a new state.

### C. The file game list survives a refused game

`GameSelector`'s page loader must not lose a whole page to one game that cannot be lexed. Any
per-row `parsePGN` failure that is not a cancellation yields a row labelled with a new localized
string `Files.GameUnreadable`. That includes obligation B's refusal and any other lexer parse
error. Every other row of the page still loads. A cancellation (the pinned cancellation payload or
an aborted signal) still aborts the page as today.

The unreadable row is a renderer-only row state. It is not a `StampedGame.omission` value, so the
bindings are unchanged. Unlike `Files.GameTooLarge`, the row stays activatable: clicking it runs
the existing open path, which shows the existing failure notification with obligation B's
message. The row carries no `identity`, so its delete action stays disabled, and deleting from the
list can never remove a multi-game range the user sees as one entry. The new key gets a
translation in every `src/translation/*.json` file through `pnpm i18n:extract` and per-language text.

## Goal

A save never replaces a file range with a tree that covers less than that range. The scanner
and the vendored parser agree on where a game ends for movetext with blank lines. Every remaining
disagreement (a second game inside one range) is refused with a typed error before a tree can be
built from part of the range. No save can then silently delete the rest of a range.

## Approach

### A. Shared movetext boundary: a blank line ends a game only after its termination marker

The vendored parser stops treating a blank line inside movetext as a game end unless the current
game's termination marker (`1-0`, `0-1`, `1/2-1/2`, `*`) has already been read **outside comments
and outside variations**. A `[`-prefixed line still ends movetext exactly as today.

One newline-boundary lookahead serves every movetext path: `read_movetext`, `skip_movetext`
(`end_headers → Skip(true)`) and `skip_variation` (`begin_variation → Skip(true)`). Today
`skip_variation` (`reader.rs:444-495`) has its own copy of the blank-line/`[`/`%` lookahead with
a different CRLF test. That copy is removed and routed through the shared lookahead, so all three
paths treat `\r` the same way. The shared lookahead keeps today's
cursor contract for every exit: when a line ends the game or the variation (a `[`-prefixed line,
or a blank line after the marker), the newline before it stays unconsumed or is otherwise left so
that the enclosing `read_movetext` / `skip_movetext` and the next `read_game` still see the
boundary. An unclosed variation followed by a tagged game must not let the next game's `[Event`
line be consumed as movetext. Termination-marker recognition is one private mechanism used by
both visitor modes. `skip_movetext`, which today has no `(`/`)` handling, tracks variation depth
so that "outside variations" means the same in both modes. In skip mode it recognises the same tokens with the same delimiters as
`read_movetext`, including `\r` as a token end, and it adds no second token grammar. Normal and
skip mode give the same game count and the same game ends on every fixture, in LF and CRLF. The
scanner is not changed.

Consequences, stated once:
* `[Event "A"]\n\n1. e4 e5\n\n2. Nf3 Nc6 *` (LF and CRLF) is one parser game, matching the one scanner range.
* `{intro}\n\n1. e4 *` is one parser game.
* A `*` inside a variation, followed by a blank line, does not end the game or the variation.
* Tagless `1. e4 *\n\n1. d4 *` stays two parser games, so the DB import is unchanged. The scanner
  still gives one range, and obligation B refuses it.
* Tagless games with no termination markers and only a blank line between them
  (`1. e4 e5\n\n1. d4 d5`) become one parser game. That matches the scanner's one range. Known
  limit, recorded under Risks.
* A `[%clk 0:01]` line still ends the parser game. The scanner range stays one, and obligation B refuses it.

The vendor's patch notes, `src-tauri/vendor/pgn-reader/CHESSFABLE.md`, record the transition and its
required regressions in the same style as the existing entries.

### B. A scanner range is read as exactly one game, or refused

One application helper in `src-tauri/src/pgn.rs` reads a game from a range's bytes with the
caller's `Visitor`. It then checks the rest of the input. If a further `read_game` would return
`Some`, the helper returns a typed refusal: any byte that `read_game`'s own whitespace and `%`
skipping does not consume counts, independent of visitor or skip mode. That covers a second game,
a `{comment}`, a `;` comment and stray tokens. Only whitespace and `%` escape lines may follow the
game. The refusal is a distinct helper result, so callers can match it without matching every
error. Cancellation and I/O errors stay terminal on every caller and are never treated as a
refusal. The check works on range bytes already in memory and adds no whole-file read.

Every application site that interprets one existing scanner range as one game goes through this helper:

* `lex_pgn_cancellable`: the refusal maps to `Error::InvalidInput` with a message saying that the
  text contains more than one game. The lexer reads through the existing `CancellableRead`, so
  cancellation during the remainder check returns `Error::Cancellation`. Pasted or typed PGN in
  `PgnInput` gets the same refusal.
* `write_game_core` / `commit_pgn_mutation` (save over an existing range): the save is refused with
  `Error::InvalidInput`, and the file stays byte-identical, when the range being replaced is not
  exactly one game. This makes "no save deletes the rest of a range" a property of the save
  itself for every range the parser cannot read as one game, whatever produced the tree. A
  truncated tree held from before this change cannot reach it: tab trees live in
  `sessionStorage`, which does not survive the app restart an upgrade requires (measured
  2026-09-22, cited in f-20261101-13). Appending a new game (`n == games.len()`) is unaffected. The
  refusal reaches the renderer's existing save-failure mapping for `invalid-input`
  (`src/utils/tabs.ts` ≈1240-1257). The save fails closed and the file is unchanged, with no new
  renderer branch.
* linked projection (`linked_collections.rs` ≈2361): the refusal counts as omitted. Cancellation stays terminal.
* collection `Cleanup` (≈2973): only `empty` judges a parsed game. A refused range is never
  omitted as empty: it is copied unchanged, and the cleanup continues. `duplicates` already compares
  the whole range's stamp (`linked_collections.rs:2988-2997`) and is unchanged. Other errors keep
  their current propagation.
* provider export (≈867) and `parse_identity_game` (`batch.rs`): the refusal maps to their
  existing `Conflict` error, never to `InvalidInput`.

On the renderer, `lex_pgn`'s `invalid-input` category already means "unavailable" to
`FileFreshnessGate` (`isUnavailableFileError`, `FileFreshnessGate.tsx:53-59`). A file game that an
external edit turns into a refused range therefore moves the tab to the fail-closed `unavailable`
state, the same as today's lexer parse errors. The panel message stays the existing
`FileFreshness.GameNoLongerInFile`. That is a known message imprecision shared with parse errors,
not a new state.

### C. The file game list survives a refused game

`GameSelector`'s page loader must not lose a whole page to one game that cannot be lexed. Any
per-row `parsePGN` failure that is not a cancellation yields a row labelled with a new localized
string `Files.GameUnreadable`. That includes obligation B's refusal and any other lexer parse
error. Every other row of the page still loads. A cancellation (the pinned cancellation payload or
an aborted signal) still aborts the page as today.

The unreadable row is a renderer-only row state. It is not a `StampedGame.omission` value, so the
bindings are unchanged. Unlike `Files.GameTooLarge`, the row stays activatable: clicking it runs
the existing open path, which shows the existing failure notification with obligation B's
message. The row carries no `identity`, so its delete action stays disabled, and deleting from the
list can never remove a multi-game range the user sees as one entry. The new key gets a
translation in every `src/translation/*.json` file through `pnpm i18n:extract` and per-language text.

## Decisions and trade-offs

Decided autonomously under full auto (to be recorded through `record-decision` by the adopter):

1. **Question:** Which side adopts which movetext boundary? **Chosen:** the scanner stays the index
   authority (precedent d-20261023-09). The parser stops ending a game at a blank line before the
   termination marker, and any remaining disagreement is refused in one range-reading helper.
   **Rejected:** (a) the scanner adopting the parser's blank-line/`[` boundaries. That changes game
   counts and indexes of existing files, and it turns `2. Nf3 Nc6 *` into a headerless fragment
   game. (b) A scanner tokenizer that splits tagless games at termination markers. That is a
   second copy of movetext tokenisation in the scanner, which d-20261023-09 rejected. (c) Blank
   lines never ending a parser game. That merges tagless terminated games in the DB import.
   (d) Only the lexer refusal, without the parser change. Then ordinary files with a blank line
   inside movetext could not be opened at all. **Reason:** this fixes the common shape without
   index churn, keeps DB import of tagless terminated files unchanged, and makes every remaining
   gap fail closed. **Reversal:** revert the reader transition with V-A proof. The helper alone
   then still prevents data loss.
2. **Question:** What happens to a `[%clk …]` line at the start of a movetext line? **Chosen:** it
   stays a parser boundary and the range is refused. **Rejected:** teaching the parser the
   scanner's tag-pair grammar. The reader's movetext would then drop `[%clk 0:01]` as an
   unparseable token, so the save would still delete it, only more quietly. **Reason:** refusal
   loses nothing, and the shape is non-standard (clock annotations belong inside `{}`).
3. **Question:** How strict is the remainder check? **Chosen:** any byte that a further
   `read_game` would see is refused, including a comment-only or `;`-only remainder. Only
   whitespace and `%` escape lines may follow. **Rejected:** classifying the remainder by visitor
   callbacks. Skip-mode reading emits no callbacks for SAN or outcomes, so a skipping probe would
   pass a second game. It would also need an allowlist that adds machinery without protecting
   anything. **Reason:** fail closed with the smallest mechanism. Against it: a range whose result
   is followed by a blank line and a free comment can no longer be opened. That shape was
   previously truncated on save.
4. **Question:** How is the refusal typed across IPC? **Chosen:** `Error::InvalidInput` with a
   specific message, the category of the existing lexer parse error. Natively it is a distinct
   helper result, matched by callers. **Rejected:** a new `Error` variant or category. The only
   renderer consumers that branch on the category treat `invalid-input` as fail-closed:
   `FileFreshnessGate` (lexer refusal on reconcile) moves the tab to `unavailable`, and the save
   mapping in `src/utils/tabs.ts` (save refusal) does the same or reports a failure. That is
   correct for a range that can no longer be represented. A different category would route the refusal to a path that only sets a message.
   Known limit: the gate's message for this case is the existing "game no longer in file" text.
5. **Question:** Does the file list show a refused game? **Chosen:** an activatable, renderer-only
   `Files.GameUnreadable` row without delete, for any non-cancellation per-row parse failure.
   **Rejected:** failing the whole page (today's behaviour for any parse error), which hides valid
   games. That would happen far more often once ranges are refused. Also rejected: reusing the
   `tooLarge` omission. It would make the row unclickable and need a bindings change.

## Approach

### A. Shared movetext boundary: a blank line ends a game only after its termination marker

The vendored parser stops treating a blank line inside movetext as a game end unless the current
game's termination marker (`1-0`, `0-1`, `1/2-1/2`, `*`) has already been read **outside comments
and outside variations**. A `[`-prefixed line still ends movetext exactly as today.

One newline-boundary lookahead serves every movetext path: `read_movetext`, `skip_movetext`
(`end_headers → Skip(true)`) and `skip_variation` (`begin_variation → Skip(true)`). Today
`skip_variation` (`reader.rs:444-495`) has its own copy of the blank-line/`[`/`%` lookahead with
a different CRLF test. That copy is removed and routed through the shared lookahead, so all three
paths treat `\r` the same way. The shared lookahead keeps today's
cursor contract for every exit: when a line ends the game or the variation (a `[`-prefixed line,
or a blank line after the marker), the newline before it stays unconsumed or is otherwise left so
that the enclosing `read_movetext` / `skip_movetext` and the next `read_game` still see the
boundary. An unclosed variation followed by a tagged game must not let the next game's `[Event`
line be consumed as movetext. Termination-marker recognition is one private mechanism used by
both visitor modes. `skip_movetext`, which today has no `(`/`)` handling, tracks variation depth
so that "outside variations" means the same in both modes. In skip mode it recognises the same tokens with the same delimiters as
`read_movetext`, including `\r` as a token end, and it adds no second token grammar. Normal and
skip mode give the same game count and the same game ends on every fixture, in LF and CRLF. The
scanner is not changed.

Consequences, stated once:
* `[Event "A"]\n\n1. e4 e5\n\n2. Nf3 Nc6 *` (LF and CRLF) is one parser game, matching the one scanner range.
* `{intro}\n\n1. e4 *` is one parser game.
* A `*` inside a variation, followed by a blank line, does not end the game or the variation.
* Tagless `1. e4 *\n\n1. d4 *` stays two parser games, so the DB import is unchanged. The scanner
  still gives one range, and obligation B refuses it.
* Tagless games with no termination markers and only a blank line between them
  (`1. e4 e5\n\n1. d4 d5`) become one parser game. That matches the scanner's one range. Known
  limit, recorded under Risks.
* A `[%clk 0:01]` line still ends the parser game. The scanner range stays one, and obligation B refuses it.

The vendor's patch notes, `src-tauri/vendor/pgn-reader/CHESSFABLE.md`, record the transition and its
required regressions in the same style as the existing entries.

### B. A scanner range is read as exactly one game, or refused

One application helper in `src-tauri/src/pgn.rs` reads a game from a range's bytes with the
caller's `Visitor`. It then checks the rest of the input. If a further `read_game` would return
`Some`, the helper returns a typed refusal: any byte that `read_game`'s own whitespace and `%`
skipping does not consume counts, independent of visitor or skip mode. That covers a second game,
a `{comment}`, a `;` comment and stray tokens. Only whitespace and `%` escape lines may follow the
game. The refusal is a distinct helper result, so callers can match it without matching every
error. Cancellation and I/O errors stay terminal on every caller and are never treated as a
refusal. The check works on range bytes already in memory and adds no whole-file read.

Every application site that interprets one existing scanner range as one game goes through this helper:

* `lex_pgn_cancellable`: the refusal maps to `Error::InvalidInput` with a message saying that the
  text contains more than one game. The lexer reads through the existing `CancellableRead`, so
  cancellation during the remainder check returns `Error::Cancellation`. Pasted or typed PGN in
  `PgnInput` gets the same refusal.
* `write_game_core` / `commit_pgn_mutation` (save over an existing range): the save is refused with
  `Error::InvalidInput`, and the file stays byte-identical, when the range being replaced is not
  exactly one game. This makes "no save deletes the rest of a range" a property of the save
  itself for every range the parser cannot read as one game, whatever produced the tree. A
  truncated tree held from before this change cannot reach it: tab trees live in
  `sessionStorage`, which does not survive the app restart an upgrade requires (measured
  2026-09-22, cited in f-20261101-13). Appending a new game (`n == games.len()`) is unaffected. The
  refusal reaches the renderer's existing save-failure mapping for `invalid-input`
  (`src/utils/tabs.ts` ≈1240-1257). The save fails closed and the file is unchanged, with no new
  renderer branch.
* linked projection (`linked_collections.rs` ≈2361): the refusal counts as omitted. Cancellation stays terminal.
* collection `Cleanup` (≈2973): only `empty` judges a parsed game. A refused range is never
  omitted as empty: it is copied unchanged, and the cleanup continues. `duplicates` already compares
  the whole range's stamp (`linked_collections.rs:2988-2997`) and is unchanged. Other errors keep
  their current propagation.
* provider export (≈867) and `parse_identity_game` (`batch.rs`): the refusal maps to their
  existing `Conflict` error, never to `InvalidInput`.

On the renderer, `lex_pgn`'s `invalid-input` category already means "unavailable" to
`FileFreshnessGate` (`isUnavailableFileError`, `FileFreshnessGate.tsx:53-59`). A file game that an
external edit turns into a refused range therefore moves the tab to the fail-closed `unavailable`
state, the same as today's lexer parse errors. The panel message stays the existing
`FileFreshness.GameNoLongerInFile`. That is a known message imprecision shared with parse errors,
not a new state.

### C. The file game list survives a refused game

`GameSelector`'s page loader must not lose a whole page to one game that cannot be lexed. Any
per-row `parsePGN` failure that is not a cancellation yields a row labelled with a new localized
string `Files.GameUnreadable`. That includes obligation B's refusal and any other lexer parse
error. Every other row of the page still loads. A cancellation (the pinned cancellation payload or
an aborted signal) still aborts the page as today.

The unreadable row is a renderer-only row state. It is not a `StampedGame.omission` value, so the
bindings are unchanged. Unlike `Files.GameTooLarge`, the row stays activatable: clicking it runs
the existing open path, which shows the existing failure notification with obligation B's
message. The row carries no `identity`, so its delete action stays disabled, and deleting from the
list can never remove a multi-game range the user sees as one entry. The new key gets a
translation in every `src/translation/*.json` file through `pnpm i18n:extract` and per-language text.

## Decisions and trade-offs

Decided autonomously under full auto (to be recorded through `record-decision` by the adopter):

1. **Question:** Which side adopts which movetext boundary? **Chosen:** the scanner stays the index
   authority (precedent d-20261023-09). The parser stops ending a game at a blank line before the
   termination marker, and any remaining disagreement is refused in one range-reading helper.
   **Rejected:** (a) the scanner adopting the parser's blank-line/`[` boundaries. That changes game
   counts and indexes of existing files, and it turns `2. Nf3 Nc6 *` into a headerless fragment
   game. (b) A scanner tokenizer that splits tagless games at termination markers. That is a
   second copy of movetext tokenisation in the scanner, which d-20261023-09 rejected. (c) Blank
   lines never ending a parser game. That merges tagless terminated games in the DB import.
   (d) Only the lexer refusal, without the parser change. Then ordinary files with a blank line
   inside movetext could not be opened at all. **Reason:** this fixes the common shape without
   index churn, keeps DB import of tagless terminated files unchanged, and makes every remaining
   gap fail closed. **Reversal:** revert the reader transition with V-A proof. The helper alone
   then still prevents data loss.
2. **Question:** What happens to a `[%clk …]` line at the start of a movetext line? **Chosen:** it
   stays a parser boundary and the range is refused. **Rejected:** teaching the parser the
   scanner's tag-pair grammar. The reader's movetext would then drop `[%clk 0:01]` as an
   unparseable token, so the save would still delete it, only more quietly. **Reason:** refusal
   loses nothing, and the shape is non-standard (clock annotations belong inside `{}`).
3. **Question:** How strict is the remainder check? **Chosen:** any byte that a further
   `read_game` would see is refused, including a comment-only or `;`-only remainder. Only
   whitespace and `%` escape lines may follow. **Rejected:** classifying the remainder by visitor
   callbacks. Skip-mode reading emits no callbacks for SAN or outcomes, so a skipping probe would
   pass a second game. It would also need an allowlist that adds machinery without protecting
   anything. **Reason:** fail closed with the smallest mechanism. Against it: a range whose result
   is followed by a blank line and a free comment can no longer be opened. That shape was
   previously truncated on save.
4. **Question:** How is the refusal typed across IPC? **Chosen:** `Error::InvalidInput` with a
   specific message, the category of the existing lexer parse error. Natively it is a distinct
   helper result, matched by callers. **Rejected:** a new `Error` variant or category. The only
   renderer consumers that branch on the category treat `invalid-input` as fail-closed:
   `FileFreshnessGate` (lexer refusal on reconcile) moves the tab to `unavailable`, and the save
   mapping in `src/utils/tabs.ts` (save refusal) does the same or reports a failure. That is
   correct for a range that can no longer be represented. A different category would route the refusal to a path that only sets a message.
   Known limit: the gate's message for this case is the existing "game no longer in file" text.
5. **Question:** Does the file list show a refused game? **Chosen:** an activatable, renderer-only
   `Files.GameUnreadable` row without delete, for any non-cancellation per-row parse failure.
   **Rejected:** failing the whole page (today's behaviour for any parse error), which hides valid
   games. That would happen far more often once ranges are refused. Also rejected: reusing the
   `tooLarge` omission. It would make the row unclickable and need a bindings change.
6. **Question:** Is the save itself guarded? **Chosen:** yes. `write_game_core` refuses to replace a
   range that is not exactly one game. **Rejected:** relying only on the lexer refusal at open. The
   MANDATE failure is the save. A tree from any source other than a refusing lex of the same
   range would still delete the rest of the range. **Reason:** the range bytes are already read for the stamp check, so the guard
   costs one bounded parse.

## Risks / open questions

* Tagless games without termination markers that are separated only by a blank line become one
  parser game in the DB import (`1. e4 e5\n\n1. d4 d5` imports as one four-move game). That
  matches the scanner and the PGN standard, which requires a termination marker per game. Such
  files are rare.
* A range that the new refusal blocks could be opened before (truncated). It now shows an error.
  The user can still edit the file outside the app.
* Termination recognition in `skip_movetext` must not slow the skip path measurably. It stays a
  single pass over bytes already buffered.
* The Files card's `GamePreview` still shows its existing `Common.Error` notification when the
  active row is a refused game. That is the open-failure surface for that game, not the list loader.
