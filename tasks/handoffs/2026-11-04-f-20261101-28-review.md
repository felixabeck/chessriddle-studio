# Plan: Workspace trash — every trashed item can be listed, restored to its folder, and purged

## Goal

Every item in a collection's trash can be seen, restored to the folder it came from, or deleted
permanently from the app, after a restart too. The user can empty the whole trash. Restoring or
purging an item leaves no empty bucket behind. Authority records for trashed entries that no
longer exist are released, so they stop using the fixed registry capacity.

## MANDATE

f-20261101-28 (native-fs, entry build, impact ux) — "Workspace trash keeps everything unbounded,
and only the last trashed item can be restored from the app":

* **Where:** `src/components/files/useFileWorkspace.tsx:108,409,708` (single unpersisted `trashed`
  slot replaced on each trash), `src-tauri/src/file_workspace.rs:707,979` (listings skip
  `TRASH_DIRECTORY`), `src-tauri/src/infra/path_authority/mod.rs:5122-5133` (trashed authority
  records never pruned), `file_workspace.rs:1390-1393` (empty UUID buckets removed only on
  rollback), `MAX_AUTHORITY_IDS = 4_096` (`mod.rs:225`).
* **Defect:** no UI or command lists, restores or purges earlier trashed items; trash disk use and
  authority records grow without bound (violates the bounded-retention rule).
* **Failure scenario:** trash folder A, then file B or restart: A is hidden in
  `.en-croissant-trash/<uuid>/` with no way to restore or purge it in the app. The 4,096-id cap
  being reached this way is plausible but not observed.
* **Open question:** what owns the trash: a native trash listing with restore and purge, auto-purge
  of older buckets (when), or both; plus pruning of authority records and empty buckets?
* **Correction (records review, 2026-11-01):** authority records are bounded by
  `check_registry_growth`, which refuses growth past the identifier and serialized-size limits.
  The defect is that unpruned trash records consume that fixed capacity until new grants are
  refused, not unbounded growth of the registry itself. Trash disk use remains unbounded.

Same-area obligation (next-finding §4, same files this run read), f-20261101-31 (native-fs, entry
build, impact ux) — "Restoring an item trashed from a subfolder puts it in the collection root":

* **Defect:** the original parent is never recorded; no decision records restore-to-root as
  intended.
* **Failure scenario:** trash `Archive/Najdorf.pgn` and click Restore: it reappears as
  `<root>/Najdorf.pgn`; if the root already has `Najdorf.pgn`, restore fails with "name already
  used".
* **Fix shape:** record the original parent locator at trash time and restore into it, falling back
  to the root only if it is gone.
* **Open question:** where is a trashed entry's original parent recorded so restore can return it
  there (native authority record, bucket-local origin record, or a renderer-supplied parent
  handle), and should it be settled together with f-20261101-28's trash listing/purge design?

## Threat model and non-goals

* Input sources: the renderer (handles it was given by native listings, never paths), the user's
  collection directory on disk (any content, including files and buckets left by older builds,
  hand-edited or truncated origin records, symlinks placed in the trash directory), and a
  concurrent external process renaming or deleting entries between listing and mutation.
* The existing path-authority guarantees stay in force: descriptor-relative, no-follow traversal
  under the retained root descriptor (d-20260914-01), identity-checked removal, and the
  `check_registry_growth` bounds. No pathname from disk content is ever joined and opened by
  string. An origin record is untrusted input: it is parsed with a size bound and resolved component
  by component under the root.
* Non-goals: automatic time- or size-based purging; changing the system trash integration (the app
  has none); cross-collection trash; renaming `TRASH_DIRECTORY`; changing the behaviour of the
  existing "Moved X to trash. Undo / Delete permanently" banner beyond routing it through the
  same commands.

## Traced premises

* `trash_entry` (`src-tauri/src/file_workspace.rs:2205`) creates `.en-croissant-trash/<uuid-v4>/`
  through retained descriptors and moves the entry (and its `.info` sidecar via
  `paired_rename_inner`) in under its own leaf. Nothing records the original parent.
* `restore_entry` (`file_workspace.rs:2292`) requires the source path to be under
  `root/.en-croissant-trash` and moves it to `root.path().join(&source.leaf)` with a no-replace
  rename. The bucket stays behind, empty.
* `permanently_delete_entry_blocking` (`file_workspace.rs:2405`) removes the entry with
  `remove_entry_at_counted` and the sidecar, calls `remove_workspace_entry`, and hands dropped
  engine `PathRef`s to `retire_executables` (d-20261007-23, restated by d-20261007-25). The
  bucket stays behind, empty.
* The workspace listing walk filters `TRASH_DIRECTORY` at every depth (`file_workspace.rs:707`), so
  no listed entry, and therefore no renderer handle, can ever be named `.en-croissant-trash`.
  `validate_name` (`file_workspace.rs:153`) also refuses that name for create and rename.
* `workspace_listing_snapshot` (`infra/path_authority/mod.rs:5123`) excludes the trash prefix, so a
  successful listing never releases trashed records (d-20261003-11 governs which ids a listing
  releases).
* Renderer: `useFileWorkspace.tsx` (consumed by `src/components/library/LibraryPage.tsx`) keeps one unpersisted `trashed: UsableEntry | null`. The trash
  banner offers Undo (restore) and Delete permanently for that one entry only. Restore and purge
  confirms go through `runTrashMutationWithRefresh` / `runDestructiveWithRefresh` and
  `clearTrashAndRelist` (d-20261025-13, d-20261025-16, d-20261026-03).
* Trashed linked collections carry the `trashed` status and are reconciled after trash, restore
  and permanent delete through `reconcile_workspace_collections` (d-20261030-07).

## Approach

### O1 — Origin record written at trash time

Quoting MANDATE (f-20261101-31): "record the original parent locator at trash time".
`trash_entry` writes one small origin record into the new bucket before the entry moves in. The
record holds the entry's parent locator relative to the workspace root (path components, not a
string path), the trashed leaf, and the trash time. It is written descriptor-relatively and synced
with the bucket. Its file name is `TRASH_DIRECTORY` itself. That name is filtered from every listing
level and refused by `validate_name`, so it can never collide with a trashed leaf or its sidecar.
If the origin record cannot be written, the trash fails before the move and the existing bucket
compensation removes the bucket. The origin record is bucket-local, so it survives a restart and a
lost or reset authority record, and is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. The
`restore_workspace_entry` signature does not change.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in is removed with its origin record, identity-checked,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Native trash listing

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned". A new Specta command `list_workspace_trash(workspace)` returns
the top-level entries of every bucket (the entry, not its descendants). Each item carries a
handle, kind, name, original folder label (the origin locator rendered for display, empty for the
root or a legacy bucket), trash time (origin record, or the bucket's modification time for a
legacy bucket), and an unreadable flag for a bucket it could not read. The walk uses the same
descriptor-relative primitives as the workspace listing, depth 2 under the trash directory, and the
same entry-count bound. Handles are prepared and committed through a trash-scoped listing snapshot.
That snapshot covers records strictly under the trash prefix, so a successful trash listing
releases records of trashed entries that no longer exist, under the same rules d-20261003-11 sets
for the workspace listing. Descendant records of a trashed directory stay as long as the directory
exists (d-20261030-07 needs them for restore). A missing trash directory returns an empty list
without creating it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory, including empty and legacy buckets. It goes through one shared removal core with
`permanently_delete_entry`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. The
result is the existing committed-removal result type, so the renderer's error mapping does not
change. The trash directory itself stays.

### O6 — Trash panel in the Files page

Quoting MANDATE: "trash folder A, then file B or restart: A is hidden … with no way to restore or
purge it in the app". The Files page gets a Trash view fed by `list_workspace_trash`. Each row shows
the name, its original folder, and the trash time, with Restore and Delete permanently. The view
also has Empty trash with a confirm. The existing banner stays for the latest trash. Restore,
purge and empty use the existing confirm and refresh flows (`runTrashMutationWithRefresh`,
`runDestructiveWithRefresh`, the d-20261026-03 durability behaviour). After each one, both the
workspace listing and the trash listing are refreshed. The trash listing is not persisted in web
storage. It is re-fetched from native state (async-resource rule: renderer state is not
authoritative). New strings go through i18next in all 16 catalogues (`pnpm i18n:extract`). The
layout follows `DESIGN.md` and the existing Files page components.

### O7 — Verification

* Rust unit tests in `file_workspace.rs` tests: a subfolder trash/restore round trip returns to the
  subfolder (f-20261101-31 scenario, including the root-conflict case); a fallback to root when the
  origin folder was removed, renamed, replaced by a file or symlink, and for a legacy bucket without
  an origin record or with a malformed one; restore and purge leave no bucket; listing returns every
  trashed item across several trashes and after a fresh `AppState` (restart), and releases records
  of trash entries removed outside the app; empty trash removes all buckets, records and the
  linked-collection records, and retires a trashed engine executable; a symlinked bucket or entry
  inside the trash is refused or skipped, never followed.
* Renderer: `FilesPage.test.tsx` / Vitest for the trash view, its actions and refresh, and the
  error paths; Playwright e2e for the trash view at the standard and 320px/200% sizes with
  committed snapshots under d-20260829-01; `pnpm verify:app` drives the real app through trash →
  restart → restore to subfolder.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record name.** Chosen: the `TRASH_DIRECTORY` name, which every listing level filters and
  `validate_name` refuses, so no trashed leaf or sidecar can collide with it.
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* The trash listing adds records for trashed entries that had none (legacy buckets). These are
  bounded by the listing entry bound and by `check_registry_growth`, and they are released when the
  entry leaves the trash.
* Bucket cleanup after a committed restore runs in the same mutation-lock scope. A concurrent
  external writer adding a file to the bucket makes the non-recursive bucket removal fail. That is
  logged, and the bucket shows up in the next listing.

## Not part of this task

* f-20260830-09 (unlink by name on Linux), f-20261101-25, f-20261104-01: same area, different
  file sets and causes.
* System trash integration, auto-purge, cross-collection trash.

## Approach

### O1 — Origin record written at trash time

Quoting MANDATE (f-20261101-31): "record the original parent locator at trash time".
`trash_entry` writes one small origin record for the new bucket before the entry moves in. The
record holds the entry's parent locator relative to the workspace root (path components, not a
string path), the trashed leaf, and the trash time. It lives **beside** the bucket, in the trash
directory, under a name derived from the bucket's UUID (for example `<uuid>.origin`), never inside
the bucket. The trash directory holds only names the app creates, so the record cannot collide
with a trashed leaf or its sidecar on any filesystem, including case-insensitive ones (I5). It is
created descriptor-relatively, exclusively (no replace), synced, and its identity is captured.

Ownership and cleanup (I1): the origin record belongs to the bucket. Every trash exit path that
removes the bucket also removes the record, identity-checked, and removes the record before the
bucket. That covers a failure after the record is written but before the move (the move never
happened, so the existing post-move compensation is not reached and this path needs its own
cleanup) and the existing rollback after a reversed move (`remove_empty_directory_at` still sees an
empty bucket because the record is outside it). If the record cannot be written, the trash fails
before the move. The record is bucket-scoped, so it survives a restart and a lost or reset
authority record, and it is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record (beside the bucket, O1) with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. The
`restore_workspace_entry` signature does not change.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in and its origin record (O1) are removed, identity-checked, record first,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Native trash listing

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned". A new Specta command `list_workspace_trash(workspace, cursor)`
returns one page of trashed items, newest first, plus the count of older items and a cursor for the
next older page (I2). Each item is a bucket's top-level entry (not its descendants) and carries a
handle, kind, name, original folder label (the origin locator rendered for display, empty for the
root or a legacy bucket), and trash time (origin record, or the bucket's modification time for a
legacy bucket). A bucket that cannot be read is returned as an unreadable row carrying the same
typed failure category the workspace listing uses for `WorkspaceUnread` (I4), so the renderer maps
it to the existing per-category messages.

Capacity (I2):
* The scan of the trash directory is descriptor-relative and no-follow, checks the cancellation
  token, and keeps only the current page in memory (a bounded page size well under
  `MAX_DIRECTORY_LISTING_ENTRIES`) while counting the rest. A trash holding more buckets than one
  page, or more than `MAX_DIRECTORY_LISTING_ENTRIES`, still lists. The listing never fails because
  the trash is large. Every item is reachable by paging.
* Handles are admitted only for the returned page.
* Before admission, every authority record under the trash prefix whose bucket or entry no longer
  exists, or whose identity no longer matches, is released, independent of the page. This is how
  trashed records stop consuming registry capacity (MANDATE correction). The release follows the
  identity rules d-20261003-11 sets for the workspace listing. Descendant records of a trashed
  directory stay as long as the directory exists (d-20261030-07 needs them for restore).
* If admission for the page fails because the registry is full, the listing returns the typed
  `ResourceLimit` error after the release step. Empty trash (O5) needs no per-item handle, so it
  still works in that state.

A missing trash directory returns an empty page without creating it. Origin records and empty or
legacy buckets are not items. An empty bucket is skipped, and Empty trash removes it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory and every origin record, including empty and legacy buckets. It walks the trash directory
with the same unbounded-count scan as O4 and needs no per-item handle. It goes through one shared removal core with
`permanently_delete_entry`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. The first failure is returned after all
buckets were tried, and executables collected from every committed removal are retired on that
error exit as well (I7). The
result is the existing committed-removal result type, so the renderer's error mapping does not
change. The trash directory itself stays.

### O6 — Trash panel in the Files page

Quoting MANDATE: "trash folder A, then file B or restart: A is hidden … with no way to restore or
purge it in the app". The Files page gets a Trash view fed by `list_workspace_trash`. Each row shows
the name, its original folder, and the trash time, with Restore and Delete permanently. Unreadable
rows show the category message. When older items exist, the view offers loading the next older
page. The view
also has Empty trash with a confirm. The existing banner stays for the latest trash. Restore,
purge and empty use the existing confirm and refresh flows (`runTrashMutationWithRefresh`,
`runDestructiveWithRefresh`, the d-20261026-03 durability behaviour). After each one, both the
workspace listing and the trash listing are refreshed. The trash listing is not persisted in web
storage. It is re-fetched from native state (async-resource rule: renderer state is not
authoritative). New strings go through i18next in all 16 catalogues (`pnpm i18n:extract`). The
layout follows `DESIGN.md` and the existing Files page components.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record location.** Chosen: beside the bucket in the trash directory, named from the
  bucket UUID. Rejected: inside the bucket under the `TRASH_DIRECTORY` name, because a
  case-insensitive filesystem lets a differently cased directory collide with it (I5).
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* The trash listing adds records for trashed entries that had none (legacy buckets). These are
  bounded by the listing entry bound and by `check_registry_growth`, and they are released when the
  entry leaves the trash.
* Bucket cleanup after a committed restore runs in the same mutation-lock scope. A concurrent
  external writer adding a file to the bucket makes the non-recursive bucket removal fail. That is
  logged, and the bucket shows up in the next listing.

string path), the trashed leaf, and the trash time. It lives **beside** the bucket, in the trash
directory, under a name derived from the bucket's UUID (for example `<uuid>.origin`), never inside
the bucket. The trash directory holds only names the app creates, so the record cannot collide
with a trashed leaf or its sidecar on any filesystem, including case-insensitive ones (I5). It is
created descriptor-relatively, exclusively (no replace), synced, and its identity is captured.

Ownership and cleanup (I1): the origin record belongs to the bucket. Every trash exit path that
removes the bucket also removes the record, identity-checked, and removes the record before the
bucket. That covers a failure after the record is written but before the move (the move never
happened, so the existing post-move compensation is not reached and this path needs its own
cleanup) and the existing rollback after a reversed move (`remove_empty_directory_at` still sees an
empty bucket because the record is outside it). If the record cannot be written, the trash fails
before the move. The record is bucket-scoped, so it survives a restart and a lost or reset
authority record, and it is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record (beside the bucket, O1) with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. In Phase 1 this
lands behind the existing `restore_workspace_entry`. O4 moves the command surface to trash item ids,
and the restore core stays one function.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in and its origin record (O1) are removed, identity-checked, record first,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Trash items are addressed by bucket, and listing them admits no records

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned … unpruned trash records consume that fixed capacity until new
grants are refused".

**Trash item identity (I2).** A trashed item is addressed by an opaque `TrashItemId`, the bucket's
UUID, never by a path-authority handle. Native code accepts an id only if it parses as a UUID, and
resolves it as a direct, no-follow child of the trash directory under the retained root descriptor.
Listing, restore and permanent delete therefore never admit a new authority record. They work
unchanged when the registry is at `MAX_AUTHORITY_IDS` and stay usable at any trash size. The
command surface becomes:
* `trash_workspace_entry(workspace, entry)` returns the new item's `TrashItemId`. The latest-trash
  banner uses it.
* `list_workspace_trash(workspace, cursor)` returns one page of items, newest first, the count of
  older items, and a cursor for the next older page.
* `restore_workspace_trash_item(workspace, item)` replaces `restore_workspace_entry`, through the O2
  restore core.
* `delete_workspace_trash_item(workspace, item)` replaces `permanently_delete_workspace_entry`,
  through the shared removal core (O5). Permanent delete is only offered for trashed items today
  (the banner's Delete permanently), so no other caller loses a door. The `verify-app` deletion
  fixture trashes its entry first and then deletes the item.
* The two replaced commands are removed from `collect_commands!`, from the dispatch-shape test list
  in `src-tauri/src/main.rs`, from the bindings, and from every renderer, test and `verify-app`
  consumer, so `ipc:consumers:check` holds.

**Records already in the trash.** `trash_entry` keeps rebinding the entry's record and its
descendants' records into the bucket, as today (d-20261030-07 needs them while the item is trashed).
Restore rebinds every record stored under the bucket path to the restored location. Permanent
delete and Empty trash remove every record stored under the removed bucket path through the
`remove_workspace_entry` policy, collecting dropped engine executables. A trash listing also releases
every record under the trash prefix whose bucket or entry no longer exists, or whose identity no
longer matches, under the identity rules d-20261003-11 sets for the workspace listing. That release
is the only registry write a listing makes.

**Listing content and bounds.** Each item is a bucket's top-level entry (not its descendants) and
carries its `TrashItemId`, kind, name, original folder label (the origin locator rendered for
display, empty for the root or a legacy bucket), and trash time (origin record, or the bucket's
modification time for a legacy bucket). A bucket that cannot be read is an unreadable row carrying
the same typed failure category the workspace listing uses for `WorkspaceUnread` (I4). The scan is
descriptor-relative and no-follow, checks the cancellation token, keeps only the current page in
memory (a bounded page size well under `MAX_DIRECTORY_LISTING_ENTRIES`) and counts the rest, so a
trash larger than one page or than `MAX_DIRECTORY_LISTING_ENTRIES` still lists, and every item is
reachable by paging. A missing trash directory returns an empty page without creating it. Origin
records and empty buckets are not items. An empty bucket is skipped, and Empty trash removes it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory and every origin record, including empty and legacy buckets. It walks the trash directory
with the same unbounded-count scan as O4 and needs no per-item handle. It goes through one shared removal core with
`delete_workspace_trash_item`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. Executables collected from every
committed removal are retired on every exit, the error exit included (I7). Outcome precedence
(I8): if any bucket or origin record remains after the batch, the result is the existing
`PartialRemoval` with the removed count, whatever the other buckets' outcomes were. That way the
renderer never shows the "saved, do not retry" durability message while items remain. A durability
error is returned only when every bucket was removed. The
result uses the existing committed-removal error variants, so the renderer's error mapping does not
change. The trash directory itself stays.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record location.** Chosen: beside the bucket in the trash directory, named from the
  bucket UUID. Rejected: inside the bucket under the `TRASH_DIRECTORY` name, because a
  case-insensitive filesystem lets a differently cased directory collide with it (I5).
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* Replacing `restore_workspace_entry` and `permanently_delete_workspace_entry` is an IPC signature

### plan-r4.md

# Plan: Workspace trash — every trashed item can be listed, restored to its folder, and purged

## Goal

Every item in a collection's trash can be seen, restored to the folder it came from, or deleted
permanently from the app, after a restart too. The user can empty the whole trash. Restoring or
purging an item leaves no empty bucket behind. Authority records for trashed entries that no
longer exist are released, so they stop using the fixed registry capacity.

## Approach

### O1 — Origin record written at trash time

Quoting MANDATE (f-20261101-31): "record the original parent locator at trash time".
`trash_entry` writes one small origin record for the new bucket before the entry moves in. The
record holds the entry's parent locator relative to the workspace root (path components, not a
string path), the trashed leaf, and the trash time. It lives **beside** the bucket, in the trash
directory, under a name derived from the bucket's UUID (for example `<uuid>.origin`), never inside
the bucket. The trash directory holds only names the app creates, so the record cannot collide
with a trashed leaf or its sidecar on any filesystem, including case-insensitive ones (I5). It is
created descriptor-relatively, exclusively (no replace), synced, and its identity is captured.

Ownership and cleanup (I1): the origin record belongs to the bucket. Every trash exit path that
removes the bucket also removes the record, identity-checked, and removes the record before the
bucket. That covers a failure after the record is written but before the move (the move never
happened, so the existing post-move compensation is not reached and this path needs its own
cleanup) and the existing rollback after a reversed move (`remove_empty_directory_at` still sees an
empty bucket because the record is outside it). If the record cannot be written, the trash fails
before the move. The record is bucket-scoped, so it survives a restart and a lost or reset
authority record, and it is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record (beside the bucket, O1) with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. In Phase 1 this
lands behind the existing `restore_workspace_entry`. O4 moves the command surface to trash item ids,
and the restore core stays one function.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in and its origin record (O1) are removed, identity-checked, record first,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Trash items are addressed by bucket, and listing them admits no records

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned … unpruned trash records consume that fixed capacity until new
grants are refused".

**Trash item identity (I2).** A trashed item is addressed by an opaque `TrashItemId`, the bucket's
UUID, never by a path-authority handle. Native code accepts an id only if it parses as a UUID, and
resolves it as a direct, no-follow child of the trash directory under the retained root descriptor.
Listing, restore and permanent delete therefore never admit a new authority record. They work
unchanged when the registry is at `MAX_AUTHORITY_IDS` and stay usable at any trash size. The
command surface becomes:
* `trash_workspace_entry(workspace, entry)` returns the new item's `TrashItemId`. The latest-trash
  banner uses it.
* `list_workspace_trash(workspace, cursor)` returns one page of items, newest first, the count of
  older items, and a cursor for the next older page.
* `restore_workspace_trash_item(workspace, item)` replaces `restore_workspace_entry`, through the O2
  restore core.
* `delete_workspace_trash_item(workspace, item)` replaces `permanently_delete_workspace_entry`,
  through the shared removal core (O5). Permanent delete is only offered for trashed items today
  (the banner's Delete permanently), so no other caller loses a door. The `verify-app` deletion
  fixture trashes its entry first and then deletes the item.
* The two replaced commands are removed from `collect_commands!`, from the dispatch-shape test list
  in `src-tauri/src/main.rs`, from the bindings, and from every caller `git grep` finds, so
  `ipc:consumers:check` holds and the test binary compiles (I11). That covers renderer and
  `verify-app` consumers and Rust tests: `src-tauri/src/db/linked_collections/tests.rs` calls
  `restore_workspace_entry` and must keep the `TrashItemId` that `trash_workspace_entry` returns. The
  callers of the restore core `restore_entry` (`db/linked_collections/tests.rs`, `pgn.rs` tests)
  move with it whenever its signature changes, in either phase.

**Records already in the trash.** `trash_entry` keeps rebinding the entry's record and its
descendants' records into the bucket, as today (d-20261030-07 needs them while the item is trashed).
Restore rebinds every record stored under the bucket path to the restored location. Permanent
delete and Empty trash remove every record stored under the removed bucket path through the
`remove_workspace_entry` policy, collecting dropped engine executables. A trash listing also releases
every `PgnFile` and `PgnWorkspace` record under the trash prefix whose bucket or entry no longer
exists, or whose identity no longer matches. Those are the same purposes and identity rules
d-20261003-11 sets for the workspace listing (`workspace_listing_snapshot`). A listing never
releases a record of any other purpose. In particular it never releases an engine executable
record, which only permanent delete and Empty trash drop, and which they always pass to
`retire_executables` (d-20261007-25, I12). That release is the only registry write a listing
makes.

**Listing content and bounds.** Each item is a bucket's top-level entry (not its descendants) and
carries its `TrashItemId`, kind, name, original folder label (the origin locator rendered for
display, empty for the root or a legacy bucket), and trash time (origin record, or the bucket's
modification time for a legacy bucket). A bucket that cannot be read is an unreadable row carrying
the same typed failure category the workspace listing uses for `WorkspaceUnread` (I4). The scan is
descriptor-relative and no-follow, checks the cancellation token, keeps only the current page in
memory (a bounded page size well under `MAX_DIRECTORY_LISTING_ENTRIES`) and counts the rest, so a
trash larger than one page or than `MAX_DIRECTORY_LISTING_ENTRIES` still lists, and every item is
reachable by paging. A missing trash directory returns an empty page without creating it. Origin
records and empty buckets are not items. An empty bucket is skipped, and Empty trash removes it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory and every origin record, including empty and legacy buckets. It walks the trash directory
with the same unbounded-count scan as O4 and needs no per-item handle. It goes through one shared removal core with
`delete_workspace_trash_item`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. Executables collected from every
committed removal are retired on every exit, the error exit included (I7). Outcome precedence
(I8): if any bucket or origin record remains after the batch, the result is the existing
`PartialRemoval` with the removed count, whatever the other buckets' outcomes were. That way the
renderer never shows the "saved, do not retry" durability message while items remain. A durability
error is returned only when every bucket was removed. The
result uses the existing committed-removal error variants, so the renderer's error mapping does not
change. The trash directory itself stays.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record location.** Chosen: beside the bucket in the trash directory, named from the
  bucket UUID. Rejected: inside the bucket under the `TRASH_DIRECTORY` name, because a
  case-insensitive filesystem lets a differently cased directory collide with it (I5).
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* Replacing `restore_workspace_entry` and `permanently_delete_workspace_entry` is an IPC signature
  change. Every consumer is in this repository (`useFileWorkspace.tsx`, `FilesPage.test.tsx`,

### plan-r5.md

# Plan: Workspace trash — every trashed item can be listed, restored to its folder, and purged

## Goal

Every item in a collection's trash can be seen, restored to the folder it came from, or deleted
permanently from the app, after a restart too. The user can empty the whole trash. Restoring or
purging an item leaves no empty bucket behind. Authority records for trashed entries that no
longer exist are released, so they stop using the fixed registry capacity.

Closes f-20261101-28 and the same-area obligation f-20261101-31.

## MANDATE

and only the last trashed item can be restored from the app":

* **Where:** `src/components/files/useFileWorkspace.tsx:108,409,708` (single unpersisted `trashed`
  slot replaced on each trash), `src-tauri/src/file_workspace.rs:707,979` (listings skip

## Threat model and non-goals

* Input sources: the renderer (handles it was given by native listings, never paths), the user's
  collection directory on disk (any content, including files and buckets left by older builds,
  hand-edited or truncated origin records, symlinks placed in the trash directory), and a
  concurrent external process renaming or deleting entries between listing and mutation.
* The existing path-authority guarantees stay in force: descriptor-relative, no-follow traversal
  under the retained root descriptor (d-20260914-01), identity-checked removal, and the
  `check_registry_growth` bounds. No pathname from disk content is ever joined and opened by
  string. An origin record is untrusted input: it is parsed with a size bound and resolved component
  by component under the root.
* Non-goals: automatic time- or size-based purging; changing the system trash integration (the app
  has none); cross-collection trash; renaming `TRASH_DIRECTORY`; changing the behaviour of the
  existing "Moved X to trash. Undo / Delete permanently" banner beyond routing it through the
  same commands.

## Approach

### O1 — Origin record written at trash time

Quoting MANDATE (f-20261101-31): "record the original parent locator at trash time".
`trash_entry` writes one small origin record for the new bucket before the entry moves in. The
record holds the entry's parent locator relative to the workspace root (path components, not a
string path), the trashed leaf, and the trash time. It lives **beside** the bucket, in the trash
directory, under a name derived from the bucket's UUID (for example `<uuid>.origin`), never inside
the bucket. The trash directory holds only names the app creates, so the record cannot collide
with a trashed leaf or its sidecar on any filesystem, including case-insensitive ones (I5). It is
created descriptor-relatively, exclusively (no replace), synced, and its identity is captured.

Ownership and cleanup (I1): the origin record belongs to the bucket. Every trash exit path that
removes the bucket also removes the record, identity-checked, and removes the record before the
bucket. That covers a failure after the record is written but before the move (the move never
happened, so the existing post-move compensation is not reached and this path needs its own
cleanup) and the existing rollback after a reversed move (`remove_empty_directory_at` still sees an
empty bucket because the record is outside it). If the record cannot be written, the trash fails
before the move. The record is bucket-scoped, so it survives a restart and a lost or reset
authority record, and it is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record (beside the bucket, O1) with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. In Phase 1 this
lands behind the existing `restore_workspace_entry`. O4 moves the command surface to trash item ids,
and the restore core stays one function.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in and its origin record (O1) are removed, identity-checked, record first,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Trash items are addressed by bucket, and listing them admits no records

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned … unpruned trash records consume that fixed capacity until new
grants are refused".

**Trash item identity (I2).** A trashed item is addressed by an opaque `TrashItemId`, the bucket's
UUID, never by a path-authority handle. Native code accepts an id only if it parses as a UUID, and
resolves it as a direct, no-follow child of the trash directory under the retained root descriptor.
Listing, restore and permanent delete therefore never admit a new authority record. They work
unchanged when the registry is at `MAX_AUTHORITY_IDS` and stay usable at any trash size. The
command surface becomes:
* `trash_workspace_entry(workspace, entry)` returns the new item's `TrashItemId`. The latest-trash
  banner uses it.
* `list_workspace_trash(workspace, cursor)` returns one page of items, newest first, the count of
  older items, and a cursor for the next older page.
* `restore_workspace_trash_item(workspace, item)` replaces `restore_workspace_entry`, through the O2
  restore core.
* `delete_workspace_trash_item(workspace, item)` replaces `permanently_delete_workspace_entry`,
  through the shared removal core (O5). Permanent delete is only offered for trashed items today
  (the banner's Delete permanently), so no other caller loses a door. The `verify-app` deletion
  fixture trashes its entry first and then deletes the item.
* The two replaced commands are removed from `collect_commands!`, from the dispatch-shape test list
  in `src-tauri/src/main.rs`, from the bindings, and from every caller `git grep` finds, so
  `ipc:consumers:check` holds and the test binary compiles (I11). That covers renderer and
  `verify-app` consumers and Rust tests: `src-tauri/src/db/linked_collections/tests.rs` calls
  `restore_workspace_entry` and must keep the `TrashItemId` that `trash_workspace_entry` returns. The
  callers of the restore core `restore_entry` (`db/linked_collections/tests.rs`, `pgn.rs` tests)
  move with it whenever its signature changes, in either phase.

**Records already in the trash.** `trash_entry` keeps rebinding the entry's record and its
descendants' records into the bucket, as today (d-20261030-07 needs them while the item is trashed).
Restore rebinds every record stored under the bucket path to the restored location. Permanent
delete and Empty trash remove every record stored under the removed bucket path through the
`remove_workspace_entry` policy, collecting dropped engine executables. A trash listing also releases
every `PgnFile` and `PgnWorkspace` record under the trash prefix whose bucket or entry no longer
exists, or whose identity no longer matches. Those are the same purposes and identity rules
d-20261003-11 sets for the workspace listing (`workspace_listing_snapshot`). A listing never
releases a record of any other purpose. In particular it never releases an engine executable
record, which only permanent delete and Empty trash drop, and which they always pass to
`retire_executables` (d-20261007-25, I12). That release is the only registry write a listing
makes.

**Listing content and bounds.** Each item is a bucket's top-level entry (not its descendants) and
carries its `TrashItemId`, kind, name, original folder label (the origin locator rendered for
display, empty for the root or a legacy bucket), and trash time (origin record, or the bucket's
modification time for a legacy bucket). A bucket that cannot be read is an unreadable row carrying
the same typed failure category the workspace listing uses for `WorkspaceUnread` (I4). The scan is
descriptor-relative and no-follow, checks the cancellation token, keeps only the current page in
memory (a bounded page size well under `MAX_DIRECTORY_LISTING_ENTRIES`) and counts the rest, so a
trash larger than one page or than `MAX_DIRECTORY_LISTING_ENTRIES` still lists, and every item is
reachable by paging. A missing trash directory returns an empty page without creating it. Origin
records and empty buckets are not items. An empty bucket is skipped, and Empty trash removes it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory and every origin record, including empty and legacy buckets. It walks the trash directory
with the same unbounded-count scan as O4 and needs no per-item handle. It goes through one shared removal core with
`delete_workspace_trash_item`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. Executables collected from every
committed removal are retired on every exit, the error exit included (I7). Outcome precedence
(I8): if any bucket or origin record remains after the batch, the result is the existing
`PartialRemoval` with the removed count, whatever the other buckets' outcomes were. That way the
renderer never shows the "saved, do not retry" durability message while items remain. A durability
error is returned only when every bucket was removed. The
result uses the existing committed-removal error variants, so the renderer's error mapping does not
change. The trash directory itself stays.

### O6 — Trash panel in the Files page

Quoting MANDATE: "trash folder A, then file B or restart: A is hidden … with no way to restore or
purge it in the app". The Files page gets a Trash view fed by `list_workspace_trash`. Each row shows
the name, its original folder, and the trash time, with Restore and Delete permanently. Unreadable
rows show the category message. When older items exist, the view offers loading the next older
page. The view
also has Empty trash with a confirm. The existing banner stays for the latest trash and addresses it by the `TrashItemId` that
`trash_workspace_entry` returned. Restore,
purge and empty use the existing confirm and refresh flows (`runTrashMutationWithRefresh`,
`runDestructiveWithRefresh`, the d-20261026-03 durability behaviour). After each one, both the
workspace listing and the trash listing are refreshed. The trash listing is not persisted in web
storage. It is re-fetched from native state (async-resource rule: renderer state is not
authoritative). New strings go through i18next in all 16 catalogues (`pnpm i18n:extract`). The
layout follows `DESIGN.md` and the existing Files page components.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record location.** Chosen: beside the bucket in the trash directory, named from the
  bucket UUID. Rejected: inside the bucket under the `TRASH_DIRECTORY` name, because a
  case-insensitive filesystem lets a differently cased directory collide with it (I5).
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* Replacing `restore_workspace_entry` and `permanently_delete_workspace_entry` is an IPC signature
  change. Every consumer is in this repository (`useFileWorkspace.tsx`, `FilesPage.test.tsx`,
  `scripts/verify-app.mjs`, the `main.rs` dispatch test) and moves in the same phase.
* Bucket cleanup after a committed restore runs in the same mutation-lock scope. A concurrent
  external writer adding a file to the bucket makes the non-recursive bucket removal fail. That is
  logged, and the bucket shows up in the next listing.

* **Defect:** the original parent is never recorded; no decision records restore-to-root as
  intended.
* **Failure scenario:** trash `Archive/Najdorf.pgn` and click Restore: it reappears as
  `<root>/Najdorf.pgn`; if the root already has `Najdorf.pgn`, restore fails with "name already
  used".
* **Fix shape:** record the original parent locator at trash time and restore into it, falling back
  to the root only if it is gone.
* **Open question:** where is a trashed entry's original parent recorded so restore can return it
  there (native authority record, bucket-local origin record, or a renderer-supplied parent
  handle), and should it be settled together with f-20261101-28's trash listing/purge design?

## Threat model and non-goals

* Input sources: the renderer (handles it was given by native listings, never paths), the user's
  collection directory on disk (any content, including files and buckets left by older builds,
  hand-edited or truncated origin records, symlinks placed in the trash directory), and a
  concurrent external process renaming or deleting entries between listing and mutation.
* The existing path-authority guarantees stay in force: descriptor-relative, no-follow traversal
  under the retained root descriptor (d-20260914-01), identity-checked removal, and the
  `check_registry_growth` bounds. No pathname from disk content is ever joined and opened by
  string. An origin record is untrusted input: it is parsed with a size bound and resolved component
  by component under the root.
* Non-goals: automatic time- or size-based purging; changing the system trash integration (the app
  has none); cross-collection trash; renaming `TRASH_DIRECTORY`; changing the behaviour of the
  existing "Moved X to trash. Undo / Delete permanently" banner beyond routing it through the
  same commands.

## Traced premises

* `trash_entry` (`src-tauri/src/file_workspace.rs:2205`) creates `.en-croissant-trash/<uuid-v4>/`
  through retained descriptors and moves the entry (and its `.info` sidecar via
  `paired_rename_inner`) in under its own leaf. Nothing records the original parent.
* `restore_entry` (`file_workspace.rs:2292`) requires the source path to be under
  `root/.en-croissant-trash` and moves it to `root.path().join(&source.leaf)` with a no-replace

* `permanently_delete_entry_blocking` (`file_workspace.rs:2405`) removes the entry with

* The workspace listing walk filters `TRASH_DIRECTORY` at every depth (`file_workspace.rs:707`), so

* `workspace_listing_snapshot` (`infra/path_authority/mod.rs:5123`) excludes the trash prefix, so a

* Renderer: `useFileWorkspace.tsx` (consumed by `src/components/library/LibraryPage.tsx`) keeps one unpersisted `trashed: UsableEntry | null`. The trash

* Trashed linked collections carry the `trashed` status and are reconciled after trash, restore

## Approach

### O1 — Origin record written at trash time

Quoting MANDATE (f-20261101-31): "record the original parent locator at trash time".
`trash_entry` writes one small origin record for the new bucket before the entry moves in. The
record holds the entry's parent locator relative to the workspace root (path components, not a
string path), the trashed leaf, and the trash time. It lives **beside** the bucket, in the trash
directory, under a name derived from the bucket's UUID (for example `<uuid>.origin`), never inside
the bucket. The trash directory holds only names the app creates, so the record cannot collide
with a trashed leaf or its sidecar on any filesystem, including case-insensitive ones (I5). It is
created descriptor-relatively, exclusively (no replace), synced, and its identity is captured.

Ownership and cleanup (I1): the origin record belongs to the bucket. Every trash exit path that
removes the bucket also removes the record, identity-checked, and removes the record before the
bucket. That covers a failure after the record is written but before the move (the move never
happened, so the existing post-move compensation is not reached and this path needs its own
cleanup) and the existing rollback after a reversed move (`remove_empty_directory_at` still sees an
empty bucket because the record is outside it). If the record cannot be written, the trash fails
before the move. The record is bucket-scoped, so it survives a restart and a lost or reset
authority record, and it is deleted with the bucket.

### O2 — Restore returns the entry to its original folder

Quoting MANDATE (f-20261101-31): "restore into it, falling back to the root only if it is gone".
`restore_entry` reads the bucket's origin record (beside the bucket, O1) with a size bound. It resolves the parent locator
component by component, no-follow, from the retained root descriptor. Each component must be an
existing directory that is not under the trash. If the record is missing (buckets from older
builds), unreadable, malformed, or any component is gone or not a directory, the target is the root,
which is today's behaviour. A name conflict at the resolved target keeps the existing
no-replace refusal and its error. The rebind uses the resolved parent's identity. In Phase 1 this
lands behind the existing `restore_workspace_entry`. O4 moves the command surface to trash item ids,
and the restore core stays one function.

### O3 — Restore and permanent delete remove the bucket they emptied

Quoting MANDATE: "empty UUID buckets removed only on rollback". After a committed restore or
permanent delete, the bucket the entry lived in and its origin record (O1) are removed, identity-checked, record first,
through the existing descriptor-relative removal helpers. A failed bucket cleanup after the
committed operation is logged and does not turn the committed operation into a failure (same
policy as the collection cleanup after permanent delete). The next trash listing (O4) skips an
empty bucket, and Empty trash (O5) removes it.

### O4 — Trash items are addressed by bucket, and listing them admits no records

Quoting MANDATE: "no UI or command lists, restores or purges earlier trashed items" and "trashed
authority records never pruned … unpruned trash records consume that fixed capacity until new
grants are refused".

**Trash item identity (I2).** A trashed item is addressed by an opaque `TrashItemId`, the bucket's
UUID, never by a path-authority handle. Native code accepts an id only if it parses as a UUID, and
resolves it as a direct, no-follow child of the trash directory under the retained root descriptor.
Listing, restore and permanent delete therefore never admit a new authority record. They work
unchanged when the registry is at `MAX_AUTHORITY_IDS` and stay usable at any trash size. The
command surface becomes:
* `trash_workspace_entry(workspace, entry)` returns the new item's `TrashItemId`. The latest-trash
  banner uses it.
* `list_workspace_trash(workspace, cursor)` returns one page of items, newest first, the count of
  older items, and a cursor for the next older page.
* `restore_workspace_trash_item(workspace, item)` replaces `restore_workspace_entry`, through the O2
  restore core.
* `delete_workspace_trash_item(workspace, item)` replaces `permanently_delete_workspace_entry`,
  through the shared removal core (O5). Permanent delete is only offered for trashed items today
  (the banner's Delete permanently), so no other caller loses a door. The `verify-app` deletion
  fixture trashes its entry first and then deletes the item.
* The two replaced commands are removed from `collect_commands!`, from the dispatch-shape test list
  in `src-tauri/src/main.rs`, from the bindings, and from every caller `git grep` finds, so
  `ipc:consumers:check` holds and the test binary compiles (I11). That covers renderer and
  `verify-app` consumers and Rust tests: `src-tauri/src/db/linked_collections/tests.rs` calls
  `restore_workspace_entry` and must keep the `TrashItemId` that `trash_workspace_entry` returns. The
  callers of the restore core `restore_entry` (`db/linked_collections/tests.rs`, `pgn.rs` tests)
  move with it whenever its signature changes, in either phase.

**Records already in the trash.** `trash_entry` keeps rebinding the entry's record and its
descendants' records into the bucket, as today (d-20261030-07 needs them while the item is trashed).
Restore rebinds every record stored under the bucket path to the restored location. Permanent
delete and Empty trash remove every record stored under the removed bucket path through the
`remove_workspace_entry` policy, collecting dropped engine executables. A trash listing also releases
every `PgnFile` and `PgnWorkspace` record under the trash prefix whose bucket or entry no longer
exists, or whose identity no longer matches. Those are the same purposes and identity rules
d-20261003-11 sets for the workspace listing (`workspace_listing_snapshot`). A listing never
releases a record of any other purpose. In particular it never releases an engine executable
record, which only permanent delete and Empty trash drop, and which they always pass to
`retire_executables` (d-20261007-25, I12). That release is the only registry write a listing
makes.

**Listing content and bounds.** Each item is a bucket's top-level entry (not its descendants) and
carries its `TrashItemId`, kind, name, original folder label (the origin locator rendered for
display, empty for the root or a legacy bucket), and trash time (origin record, or the bucket's
modification time for a legacy bucket). A bucket that cannot be read is an unreadable row carrying
the same typed failure category the workspace listing uses for `WorkspaceUnread` (I4). The scan is
descriptor-relative and no-follow, checks the cancellation token, keeps only the current page in
memory (a bounded page size well under `MAX_DIRECTORY_LISTING_ENTRIES`) and counts the rest, so a
trash larger than one page or than `MAX_DIRECTORY_LISTING_ENTRIES` still lists, and every item is
reachable by paging. A missing trash directory returns an empty page without creating it. Origin
records and empty buckets are not items. An empty bucket is skipped, and Empty trash removes it.

### O5 — Empty trash

Quoting MANDATE: "trash disk use … grow[s] without bound" and the open question's "purge". A new
Specta command `empty_workspace_trash(workspace)` permanently deletes every bucket under the trash
directory and every origin record, including empty and legacy buckets. It walks the trash directory
with the same unbounded-count scan as O4 and needs no per-item handle. It goes through one shared removal core with
`delete_workspace_trash_item`: the same identity-checked recursive removal, `remove_workspace_entry`
for every removed trashed entry, the same `PartialRemoval` / durability contract (d-20260830-04),
dropped engine executables collected on every exit path and passed to `retire_executables`, and
collection reconciliation afterwards. A failure on one bucket is recorded and the rest continue. Executables collected from every
committed removal are retired on every exit, the error exit included (I7). Outcome precedence
(I8): if any bucket or origin record remains after the batch, the result is the existing
`PartialRemoval` with the removed count, whatever the other buckets' outcomes were. That way the
renderer never shows the "saved, do not retry" durability message while items remain. A durability
error is returned only when every bucket was removed. The
result uses the existing committed-removal error variants, so the renderer's error mapping does not
change. The trash directory itself stays.

### O6 — Trash panel in the Files page

Quoting MANDATE: "trash folder A, then file B or restart: A is hidden … with no way to restore or
purge it in the app". The Files page gets a Trash view fed by `list_workspace_trash`. Each row shows
the name, its original folder, and the trash time, with Restore and Delete permanently. Unreadable
rows show the category message. When older items exist, the view offers loading the next older
page. The view
also has Empty trash with a confirm. The existing banner stays for the latest trash and addresses it by the `TrashItemId` that
`trash_workspace_entry` returned. Restore,
purge and empty use the existing confirm and refresh flows (`runTrashMutationWithRefresh`,
`runDestructiveWithRefresh`, the d-20261026-03 durability behaviour). After each one, both the
workspace listing and the trash listing are refreshed. The trash listing is not persisted in web
storage. It is re-fetched from native state (async-resource rule: renderer state is not
authoritative). New strings go through i18next in all 16 catalogues (`pnpm i18n:extract`). The
layout follows `DESIGN.md` and the existing Files page components.

## Decisions and trade-offs

### Decided autonomously

* **What owns the trash?** Chosen: a native trash listing with per-item restore and permanent
  delete, plus Empty trash. Rejected: auto-purge of older buckets by age or size, either alone or
  combined. Reason: the filed defect is that items cannot be reached. The listing and Empty trash
  give the user control over every item and bound disk use by the user's own action, as the
  existing Delete permanently already does for one item. A timer that deletes user files
  unannounced would be a new promise to users about data retention. The defect does not need it, so
  this run does not create that product question. Reversal path: add an age-based purge inside
  the O5 core later. The bucket timestamps from O1 already carry the trash time.
* **Where is the original parent recorded?** Chosen: a bucket-local origin record (O1). Rejected:
  a field on the path-authority record, because it changes the persisted registry schema and is
  lost when the record is released or the registry is reset, while the bucket and its data
  survive; and a renderer-supplied parent handle, because it changes the `restore_workspace_entry`
  binding and the renderer no longer holds that handle after a restart. Reversal path: read the
  locator from another source in O2 and keep the fallback.
* **Origin record location.** Chosen: beside the bucket in the trash directory, named from the
  bucket UUID. Rejected: inside the bucket under the `TRASH_DIRECTORY` name, because a
  case-insensitive filesystem lets a differently cased directory collide with it (I5).
* **Missing origin folder.** Chosen: restore to the root, as the MANDATE's fix shape says, not
  recreating the folder chain. Recreating it would bring back folders the user deliberately removed.

## Risks / open questions

* Replacing `restore_workspace_entry` and `permanently_delete_workspace_entry` is an IPC signature
  change. Every consumer is in this repository (`useFileWorkspace.tsx`, `FilesPage.test.tsx`,
  `scripts/verify-app.mjs`, the `main.rs` dispatch test) and moves in the same phase.
* Bucket cleanup after a committed restore runs in the same mutation-lock scope. A concurrent
  external writer adding a file to the bucket makes the non-recursive bucket removal fail. That is
  logged, and the bucket shows up in the next listing.

  file sets and causes.
* System trash integration, auto-purge, cross-collection trash.
